# outline — 第1記事

Single thesis: **AI で開発が楽になるはずなのに、なぜ人間が AI の管理者になっていくのか。**

配分の目安（本文の分量ベース）:
- 問題・気づき（1〜3章）: 約 40%
- 設計思想（4〜6章）: 約 25%（rig の名前は出るが、機能説明ではなく判断の話）
- rig のまとまった説明（7章）: 約 25%
- 締めと CTA（8章）: 約 10%

→ rig そのものの説明は 7 章に集約し、全体の 30〜40% を超えないようにする。

---

## 0. リード（見出しなし・3〜5文）

役割: 読者が自分の話だと気づく。一般論・テーマ紹介から入らない。
内容: Claude Code を使い込んだ結果として増えた確認作業を、名前を付けずに描写してから、
「これは AI に任せているのか、AI の面倒を見ているのか」という問いを1つ立てる。
禁止: 「この記事では〜を解説します」型の宣言。

## 1. 資産は増えた。判断は減らなかった

役割: 問題の解像度を上げる。読者の手元にあるものを名指しする。
内容:
- CLAUDE.md / Skills / Subagents / reviewer / worktree / rules / Knowledge が増える
- それぞれに価値がある（不要とは言わない = non-goal 遵守）
- しかし「選ぶ / 組み合わせる / 状態を見る / 結果を見る / 再実行を指示する / 最後に品質を判断する」は人間のまま
- 増えたのは資産で、減らなかったのは判断の回数
着地: これは AI に任せている状態ではなく、AI チームの管理業務をやっている状態。
分量: 中。ここが記事の核なので長めに書いてよい。

## 2. 生成が揺れるのは、たぶん問題じゃない

役割: 論点を1つに絞り込む。安易な「AI は信用できない」論に落とさない。
内容:
- 同じ prompt でも結果が変わるのは LLM の性質。ここを直そうとしていない
- rig も生成を決定的にしようとはしていない（`skills/engine/SKILL.md:12` の determinism-by-gate）
- 困るのは、生成ではなく**評価**まで非決定的なこと
- 「問題ありません」「LGTM」「実装完了しました」は、品質の根拠として弱い
着地: 管理業務が消えないのは、評価の最終判断が毎回人間に戻ってくるから。
分量: 短め（2〜3段落）。

## 3. 「AI に聞かないと分からないこと」と「聞かなくても分かること」

役割: 気づきから設計へ橋を渡す。ここが記事の転換点。
内容:
- 評価には、AI reviewer の判断が要る部分と、機械で見れば済む部分がある
- 後者の例（すべて sources.md §3 に根拠あり）: tests が通るか、無関係な差分が混じっていないか、
  secret が漏れていないか、破壊的なコマンドが差分に書かれていないか、
  gate 定義や CI workflow 自体が書き換えられていないか
- 後者を AI の感想に任せているのが、そもそもおかしかった
着地: 機械で判断できるものを機械に返せば、人間に戻ってくる判断は減る。
分量: 中。

## 4. reviewer と Skill を、使う側から測る側へ

役割: 設計思想②。ここは「疑い」を書く章で、機能紹介にしない。
内容:
- 「Senior Reviewer」という名前の persona が、実際にバグを見つけられるとは限らない
- 公開されている Skill も同じ。「入れると品質が上がる」と書いてあることと、有効であることは別
- なので Skill / Persona / Reviewer 自体を測定対象にしたかった
- rig には `/rig:drill`（既知のバグの種を使い捨て diff に注入して答案キーと突き合わせる）と
  `/rig:go stats`（reject 0 の reviewer をゴム印候補として警告する）がある — いずれも Beta
- **数値は書かない**。README のスコアは説明用サンプルであって実測値ではない（sources.md §6 の注意）
着地: 測った結果はこの記事には無い。次の記事で自分の reviewer を測る。
分量: 中。

## 5. context も毎回自分で選びたくない

役割: 設計思想③。
内容:
- ルール・Skills・Knowledge を全部常時読み込ませるのではなく、task ごとに必要なものだけ構成したい
- rig は起動時に persona / instruction / pattern / recipe を合成する（PARSE→RESOLVE→COMPOSE→RUN）
- 実作業は subagent に投げ、親は dispatch と集約と gate 判断だけ持つ（context-minimal）
- ただし rig が計測できるのは rig 自身が印字した stdout だけで、セッション全体ではない
  （`/rig:go context`。この限界はレポート自身に書かれる）
着地: 「context を減らせる」とは言わない。「どこまでを自分の責任範囲と言えるか」を切ったという話。
分量: 短め。

## 6. 仕組みにしたら rig になった

役割: ここで初めて rig をまとめて説明する。記事で唯一の機能説明章。
内容:
- 概念図（Task → classify → compose → isolated worktree → implementation →
  independent verification → deterministic acceptance gates → 人間の accept / discard）
- 実際に打つコマンドは3つ（`/rig:go "<task>"` / `/rig:go diff` / `/rig:go accept`）
- accept が拒否される条件（failed / pending の gate が1つでもあれば止まる）
- `--force` で越えられるのは soft な gate だけで、構造的前提は越えられない。越えたら監査ログに残る
- verifier は read-only で起動し、生成側の自己申告ではなく git diff を一次証拠にする
- 明示する制約: rig は AI を賢くしない。安全のために速度とトークンを払う設計（README.ja.md:22）
- shipped / Beta の区別を本文中で明示する
分量: 記事全体の 25% 程度。これを超えたら削る。

## 7. まだできていないこと

役割: 標語で終わらせないための章。宣伝色を下げる。
内容:
- drill / stats / board は Beta で出力形式が変わりうる
- drill や stats の数値を自動公開する CI は無い（README.ja.md:425 が未実装と明記）
- gate を通ったから正しい、ではない。基準を書くのは人間の仕事のまま
分量: 短い。

## 8. 締めと CTA

役割: 標語で閉じず、一番小さい具体で終える。
内容:
- 結論の芯: AI を信用できるように教育し続けるより、信用しなくても任せられる構造を作りたかった
  （ただし標語として1行で置かず、直前の具体に混ぜる）
- CTA: Star ではなく、「同じように AI の面倒を見ている人が、どの確認作業を手放せずにいるか」を
  Issue で知りたい、という形。reviewer / Skill を測ってみたい人向けの入口も1行だけ添える
- 最後の一文は、次に自分が測るつもりの具体（自分の reviewer persona を drill にかける）で終える
禁止: 「いかがでしたか」「〜してみてはいかがでしょうか」、対句、各章末のまとめ。
