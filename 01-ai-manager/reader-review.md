## 反応の要点

**刺さった箇所**: リード（「実装ではなく確認でした」「減らなかったのは、見る回数です」）。
ここは自分の話だと感じたと明言している。

**白けた箇所**: 資産の棚卸し（「CLAUDE.md を書き、Skill を足し…」）から6項目の箇条書きへ、
エッセイの語りがチェックリストに切り替わるところ。「製品紹介の前振りだな」と身構えると。

**主要な批判**:

1. 28行目以降が事実上 README の日本語要約になっている。同じ主張（rig が自動で構成する）を
   散文・コマンド出力・ASCII 図の三重で説明していて、そこで読むモードが切り替わる
2. 「AI チームの管理業務」「管理職が増えた」は個人開発の粒度に対して誇張。
   記事の芯（機械判定できるものを機械に返す）を安っぽく見せている
3. 「捨てる話ではありません」と「rig が persona/instruction/pattern/recipe を組み合わせる」の
   関係が未定義。既存資産と rig が共存するのか、rig に吸収されるのか読者が判断できない
4. 論点が gate / drill / stats / context 合成 / worktree / cross-provider に拡散し、
   「一言で言うと何をするツールか」が一つに収束しない
5. `PARSE → RESOLVE → COMPOSE → RUN` が説明なしの専門用語として1回だけ出てくる
6. GitHub を見に行く動機が立たない。予防線（Beta・未計測・「減るとは書けません」）を
   自分で積み上げて期待値を下げ切っているため

- 「gate リスト出力を削れ」: 記事で唯一の、コマンドを打てば読者が自分で再現できる一次証拠。
  README の転記に見えるという指摘は理解するが、削ると evidence_grounded を落とす

- reviewer が残債として挙げた README 側の要約粒度の見直しは、この記事のスコープ外

## GitHub への動機

前回より少し上がった、との判定。理由は末尾の呼びかけが具体化したこと
（決定的に判定できるなら基準に足せる／落とせないなら reviewer 側の仕事だと分かる）。
ただし記事全体は自己抑制的なトーンのままで、「使ってみたい」より
「誠実な人が作っている」という信頼感が残る記事、という評価。
これは intent の non-goal（宣伝にしない）と整合するので、そのまま受ける。
