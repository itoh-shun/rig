# Claude Codeで楽になるはずが、気づけばAIの面倒を見ていた

実装は AI に投げています。それでも一日の終わりに何をしていたか思い出すと、実装ではなく確認でした。進捗を見て、テストの結果を見て、差分を見て、レビューの指摘を読んで、直させて、また見る。

書く量は確かに減りました。減らなかったのは、見る回数です。

AI に任せているのか、AI の面倒を見ているのか。しばらく前から、後ろのほうが正しい気がしています。

## 資産は増えた。判断は減らなかった

Claude Code を使い込むと、手元の資産が増えます。CLAUDE.md を書き、Skill を足し、reviewer 用の subagent を分け、worktree を切り、別のモデルにもレビューさせ、プロジェクト固有のルールと Knowledge を溜める。

どれも効きます。捨てる話ではありません。私も使っています。

ただ、増えた資産を動かすのは人間のままでした。

- 今回のタスクにどの Skill を効かせるか選ぶ
- どの reviewer を当てるか組み合わせる
- いくつ走っていて、どれが終わったのかを見る
- 返ってきた結果を読む
- 気に入らなければ再実行を指示する
- 最後に、これをマージしていいか判断する

この6つはどれも AI に任せていません。任せられるようにも作っていませんでした。実装を任せた分だけ、実装以外の仕事が手元に残った、というだけです。

AI に任せている状態ではなく、AI チームの管理業務をやっている状態。楽になるはずだったのに管理職が増えたのは、たぶんそういうことでした。

## 生成が揺れるのは、たぶん問題じゃない

同じ prompt を二度投げて違うコードが返るのは、そういうものだと思っています。そこを直そうとはしていません。

困るのは、生成が揺れることではなく、評価まで揺れることでした。

「問題ありません」
「LGTM」
「実装完了しました」

これは出力であって、根拠ではありません。同じ diff にもう一度レビューさせれば違うことを言う可能性があるものを、受け入れの理由にしていた。管理業務が消えないのは、最終判断が毎回こちらに戻ってくるからで、戻ってくるのは、返ってきた文が判断の材料にならないからです。

## AI に聞かないと分からないことと、聞かなくても分かること

評価と一口に言っても、中身は同じではありません。

この抽象は後で困らないか。この設計はこの機能に合っているか。ここは読んで考えるしかない部分です。

一方で、こういうものがあります。テストが通ったか。差分に無関係なファイルが混ざっていないか。秘密の値が入っていないか。`rm -rf` や `DROP DATABASE` のような破壊的なコマンドが差分に書き込まれていないか。そして、gate の定義や CI の workflow そのものが書き換えられていないか。

これらは読んで判断する必要がありません。走らせれば分かります。

rig ではここを基準の一覧として持たせました。全 task 種別に共通で乗る `standard` プリセットの中身は、実行して確認できます。

```bash
python3 scripts/workbench.py gates
```

```
### standard
  - task_intent_satisfied
  - no_unrelated_diff
  - diff_summary_written
  - risk_summary_written
  - tests_pass_or_explained
  - no_type_errors_or_explained
  - no_secret_leak
  - no_gate_tampering
  - no_injection_markers
  - no_destructive_operation
```

このリストの正本はドキュメントではなくこのコマンドの出力です。`no_secret_leak` はシークレットスキャン、`no_destructive_operation` は破壊的コマンドのスキャン、`no_gate_tampering` は `.rig/gates.json` や `.rig/recipes/` や CI workflow の編集を見ています。AI が「秘密は入っていません」と言ったかどうかは見ていません。

プロジェクト側から基準を足すこともできますが、加算だけです。組み込みの基準を消したり緩めたりするキーは拒否されます。gate を弱める変更をリポジトリの中のファイルで行えてしまうと、gate ではなくなるからです。

機械で判断できるものを機械に返すと、こちらに戻ってくる判断はその分だけ減ります。減らないのは、読んで考えるしかない部分だけ。それは減らなくていいと思っています。

## reviewer と Skill を、使う側から測る側へ

もう一つ、以前から疑っていたことがあります。

「Senior Reviewer」という名前を付けた persona が、本当にバグを見つけているのか。名前は入力であって、性能ではありません。公開されている Skill も同じで、「これを入れると品質が上がる」と書いてあることと、実際に上がることは別の話です。

使う側にいる限り、この区別はつきません。測る側に回りたかった。

rig には `/rig:drill` があります。既知のバグの種を使い捨ての worktree の diff に注入して review fan-out を走らせ、reviewer には見せない答案キーと突き合わせる。出てくるのは persona ごとの検出・見逃し・誤検出です。本物のコードには触れません。`--replay` を付けると、persona を編集したあとに過去の diff へ再実行して、判定がどう変わったかを差分で見られます。

`/rig:go stats` のほうは、run の履歴を集計します。落ちがちな gate、accept と discard の比率、そして一度も reject していない reviewer をゴム印の疑いとして出します。

どちらも Beta です。それから、README に載っているスコアの例は説明用のサンプル出力であって、実測値ではありません。自分の reviewer をこれにかけた数字を、まだ記事にできる形で持っていません。次に書くのはそれです。

## context も毎回自分で選びたくない

ルールも Skill も Knowledge も、増えるほど「全部読ませておく」が無理になります。かといって毎回手で選ぶなら、それも管理業務です。

rig は起動のたびに persona と instruction と pattern と recipe を組み合わせて、そのタスク用のハーネスを作ります。固定のワークフローを流すのではなく、PARSE → RESOLVE → COMPOSE → RUN の順で毎回組み立て直す。実作業は subagent に投げて、親は dispatch と集約と gate の判断だけを持ちます。長い diff やログを親のコンテキストに引き込まない、というのがハードルールとして書いてあります。

ここは正直に書いておきたいところがあります。rig が計測できるのは、rig 自身が親セッションへ印字した stdout だけです。

```bash
python3 scripts/workbench.py context
```

セッション全体のコンテキストも、会話も、あなたが自分で読んだファイルも、rig からは見えません。だから「rig を使うとコンテキスト消費が減る」とは書けません。レポート自身にも、何を測っていないかが書かれます。測っていないものを測ったことにする数字を出すほうが、数字が無いより悪いと思っています。

## 仕組みにしたら rig になった

ここまでのものを1本の流れにすると、こうなりました。

```
自然文のタスク
   ↓
task の分類
   ↓
必要な context / recipe / persona を合成
   ↓
隔離された worktree で実装
   ↓
read-only の verifier が独立に検証
   ↓
決定的な acceptance gate
   ↓
人間が accept / discard
```

普段打つのは3つです。

```bash
/rig:go "ログインバグを直して"
/rig:go diff
/rig:go accept
```

`/rig:go` にタスクを渡すと、種別を判定して recipe を選び、いま作業しているツリーとは別の git worktree を切って、そこで実装します。手元のファイルには触りません。失敗しても、途中でやめても、作業ツリーは最初のままです。

`accept` は無条件には通りません。failed か pending の gate が1つでも残っていれば止まります。`--force` はありますが、越えられるのは soft な未達だけで、worktree があるか、base branch が記録されているか、diff サマリが生成されているかという構造的な前提は `--force` でも越えられません。越えた場合は `.rig/audit.jsonl` に残ります。反映も staged までで、コミットは人間がやります。

検証する側は、実装した側とは別プロセスで、読み取り専用のツールだけを渡して起動します。`claude --allowedTools Read,Grep,Glob` や `codex --sandbox read-only` の形です。お願いではなく、起動時の制約として。判定の一次証拠は、生成側が書いた「できました」レポートではなく worktree の実際の git diff のほうです。実装を Claude、検証を Codex のように分けられるのは、同じクラスのモデルが自分の成果物を採点する状況を避けたかったからです。

rig は AI を賢くしません。品質を自動的に生むものでもありません。基準を書くのは人間の仕事のままで、rig がやるのはそれを AI に無視させないことと、通ったかどうかを記録することです。そのために速度とトークンを払います。とにかく速くコードを書かせたいだけなら、モデルに直接頼んだほうが速いです。

## まだできていないこと

drill も stats も board も Beta で、出力の形は変わりえます。

そして、drill や stats の数字を自動で公開する仕組みがありません。マージのたびにスコアを再生成して貼り出す CI は、まだ書いていない。いまの「測っている」は、メンテナがローカルで実行して結果を貼る運用のことで、継続更新される公開スコアではありません。README にもそう書いてあります。

gate を通ったから正しい、でもありません。gate は「あなたが書いた基準を満たした」としか言っていない。基準が甘ければ甘いまま通ります。

## それで、何を教えてほしいか

AI を信用できるところまで教育し続けるより、信用しなくても任せられる形にしたい、というのがここまでの動機です。教育のほうは終わりが見えませんが、機械で判断できるものを機械に返すのは終わりがあります。

聞きたいのは、みなさんがまだ手放せずにいる確認作業のほうです。テストの結果は自動で見ているけれど、これだけは毎回自分の目で見ている、というものがあると思います。それがどういう種類の確認なのかを知りたい。決定的に判定できる形に落とせるなら、gate の基準として足せます。

reviewer や Skill を測ってみたい人も歓迎です。バグの種のカタログは増やせるほど精度が上がるので、「この観点の見逃しが怖い」という種の提案は、そのまま実装の材料になります。

- https://github.com/itoh-shun/rig

私が次にやるのは、自分で書いた reviewer persona を `/rig:drill` にかけて、検出率を見ることです。名前を「strict」にしただけの persona だったら、それはそれで記事になります。
