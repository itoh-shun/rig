RIG

AI に仕事を任せるときの、隔離と検証のしくみ。
はじめての人が三十分で全体をつかむための資料です。

今日の地図

  • 第一部　rig を知る何をする道具か。なぜ安全と言えるのか。日常で使う三つのコマンド。
  • 第二部　pack で知識層を拡張する専用領域の知識を、配布物として渡す方法です。

典拠：README.ja.md / docs/packs.md / skills/engine/SKILL.md

困るのは、AI が間違えることではありません

間違えたことに誰も気づかないまま、本体に混ざってしまうことです。

rig はそこだけを構造で塞ぎます。自然文でタスクを頼むと、種類を判定し、部品を組み合わせてハーネスを作り、隔離された git worktree の中で作業します。明示的な基準で検証し、あなたが accept と言うまで本体には触れません。

最初に外しておく誤解

  • 品質を自動的に生む道具ではありませんあなたが決めた品質基準を、AI に無視させないための道具です。基準を作るのは人間の仕事のままで、rig の仕事は強制と測定です。
  • そのかわり、対価があります隔離と検証と記録のために、速度とトークンをわざと払っています。速く書かせたいだけなら、直接頼むほうが速いです。
  • 効いてくる場面失敗したときのコストが、速度より高い場面です。

直接頼む場合と、何が違うか

直接頼むrig 経由
失敗した変更作業ツリーに残るworktree ごと破棄、本体は無傷
「できました」信じるしかないacceptance-gate の合否が根拠
レビューの質不明検出率を実測できます
何が起きたかチャットログrun log と監査証跡

第一部

隔離

入口は二つ。中身は同じエンジン

Claude Code の中では、プラグイン

/plugin marketplace add itoh-shun/sito-plugins
/plugin install rig@sito-plugins

それ以外の場所では、rig-wb CLI

pipx install git+https://github.com/itoh-shun/rig.git
rig-wb version

CI やスクリプト、別のアシスタント（Codex / Cursor）から同じ recipe とゲートを回すためのものです。両方は要りません。

最初の三十秒。設定はゼロで始められます

/rig:go "ログインバグを直して"
/rig:go "このPRを厳しめにレビューして"
/rig:go "今の変更が安全か確認して"

manifest も gates.json も persona 設定も要りません。すべて後から足せます。

なぜその段取りになったかを、先に宣言します

▸ rig
task:     ログインバグを直して
detected: bugfix
recipe:   bugfix — 「バグ」「直して」を検出
mode:     isolated worktree
gate:     standard + bugfix

そして、確認して、決める

/rig:go diff       # 何が変わったか、なぜ安全か
/rig:go accept     # 作業ツリーへ反映（gate 未達なら拒否される）
/rig:go discard    # 破棄（作業ツリーは最初から触られていない）

日常で使うのは、この三つだけです。

rig が安全だと言える四つの理由

安全だと言えるのは、次の四つが文章ではなく配線として入っているからです。

  • 一　隔離された worktree
  • 二　acceptance-gate
  • 三　read-only な検証役
  • 四　明示的な accept と、消えない記録

一　隔離された worktree

タスクごとに専用の worktree と使い捨てブランチを作ります。rig があなたの作業ツリーに直接書き込むことはありません。

<repoの親>/rig-worktrees/<repo名>/rig-20260704-153012-login-fix/
<repo>/.rig/runs/rig-20260704-153012-login-fix/
    task.json        入力 / task_type / recipe / base branch / status
    acceptance.json  基準ごとの合否と根拠
    diff.md          Summary / Risk / Tests / Unrelated diff

隔離がタスクごとに閉じているので、複数タスクを同時に走らせても安全です。並列プロセス同士がファイルを取り合うこともありません。

二　acceptance-gate

モデルが「完了しました」と言っただけでは完了になりません。無関係な差分は混じっていないか。テストと型は通るか。リスクは書かれたか。秘密情報は漏れていないか。ここを機械が確認します。

failed か pending が一件でも残っていれば、accept は機械的に拒否されます。

ゲートは standard ＋ 種別プリセット

preset基準の例
standardno_unrelated_diff / risk_summary_written / tests_pass_or_explained / no_secret_leak / no_gate_tampering / no_injection_markers / no_destructive_operation
bugfixbug_cause_identified / fix_is_minimal / regression_test_added_or_explained
featureimplementation_matches_requirement / tests_added_or_explained / public_api_changes_documented
refactorno_unintended_behavior_change / tests_confirm_behavior_preserved
securityauthn_authz_impact_checked / user_input_flow_checked / dependency_risk_checked

自己申告ではなく、機械センサーが裏づけます

  • 秘密情報スキャン ／ インジェクション・マーカー検出
  • 破壊的コマンド検出 ／ ゲート改竄の検出 ／ OpenAPI スキーマ差分

プロジェクト側で基準を足せます（.rig/gates.json）。ただし足す方向だけです。削除キーと緩和キーは、その場で拒否されます。

リポジトリの中のファイルが、そのリポジトリを守るゲートを弱めることはできません。

三　read-only な検証役

実装する AI と検証する AI を分け、検証側はプロセスレベルで読み取り専用に固定します。お願いではなく、強制です。

claude --allowedTools Read,Grep,Glob
codex  --sandbox read-only

見て、grep して、指摘を書くことはできます。編集も commit も、formatter による書き換えもできません。

検証役が読むのは、レポートではありません

判定の一次証拠は worktree の実際の git diff です。生成側が書いた自己申告レポートは、「未検証の主張」というラベルつきで渡されるだけです。

同系統のモデルが自分の成果物をレビューする状況を、構造として避けるための設計です。

四　明示的な accept と、消えない記録

  • accept は staged で止まりますsquash merge で未コミットのまま反映します。コミットは常に人間が打ちます。
  • discard しても run log は残ります何を試して、なぜ捨てたかを後から辿れます。
  • 構造的な前提は --force でも通りませんdiff.md が無ければ accept できません。例外はありません。

効果を測っていないゲートは、
回っているかどうかも分かりません。

中身は四種類のブリック

  • persona誰が判定するか
  • instruction何をするか
  • patternどう分配し、どうゲートするか
  • recipestep の束です（bugfix / feature / review-only / release-flow …）

/rig:go はこの組み立てを自動でやります。/rig:dev は同じエンジンを、recipe・step・flag をすべて自分で指定して使う入口です。

レビュアーの実力は測れます

/rig:drill は既知のバグを使い捨ての diff に仕込んでレビューを走らせ、reviewer には見せない答案キーと突き合わせて採点します。

# Drill Result — strict_senior_engineer
Detection rate:    82%
False positive:    12%
Severity accuracy: 76%

## Missed Issues
1. SQL injection risk in search query (src/search.py:88)
2. Missing authorization check (src/api/users.py:120)

形だけのレビューも名指しします

Verifier behavior:
- strict_senior_engineer: 14 runs, 6 rejects
- product_reviewer:        6 runs, 0 rejects

Warning:
product_reviewer has 0 rejects across 6 runs.
Possible rubber-stamp behavior.

レビューが儀式になっていることは、こうやって初めて見えます。

第二部

PACK

知識層とは何か

subagent のプロンプトに注入される、ドメイン知識のことです。

「この会社ではバックアップをこう定義している」「この製品のユビキタス言語はこれだ」。こうしたコードを読んでも出てこない事実を、レビュアーや実装役に持たせるための層です。

実体は二種類あって、性格がはっきり違います

セッション知識層pack
作り方/rig:knowledgerig-wb pack
配布できませんzip / git で配れる
版と改竄管理しないversion・sha256・lock
品質本人の目承認済み評価ケースが必須
向く場面今すぐ効かせたいときチームに同じ知識を効かせたいとき

手元で育てるなら前者で十分です。他人に渡すときに要るのが後者です。誰が書いたか、いつ見直したか、根拠は何か、途中で書き換わっていないか。この四つを構造として持っています。

知識の中心は wiki で、persona はそれを参照します

# persona: house-authenticity
inject: ["[[genre-house]]", "[[music-era-90s]]"]

一つの概念につき、一枚の正準ページを書きます。事実を persona の本文には埋め込みません。

埋め込むと知識が暗黙知になります。参照にしておけば、ページを一枚直すだけで、参照している全 persona の判断が同時に更新されます。

[[slug]] は tier で解決されます

  • 1　project overlay　<repo>/.claude/rig/knowledge/wiki/
  • 2　global　~/.claude/rig/knowledge/wiki/
  • 3　org　チームで共有する層
  • 4　pack 同梱　<pack>/facets/knowledge/<slug>.md
  • 5　shipped　rig が最初から持っているページ

pack の persona は、まず自分の pack の中を見ます。pack は必要なページを同梱して持ち歩きます。同じ slug をプロジェクト側に置けば、これまでどおり上書きできます。

type が決めるのは権限です

type持てるものホストのコマンドを走らせるか
knowledgewiki・resource・評価ケースいいえ
policy上記 ＋ policyいいえ
reviewer上記 ＋ persona・output-contractいいえ
skill / workflowすべてのプロンプト種別いいえ
toolすべてはい

既定値は持たせていません。既定値を置くと、その決定を「決めなかった人」に渡してしまうからです。

右端の列が、この型モデルがある理由です

recipe に checks:（ホスト上で実行されるシェルコマンド）を書けるのは tool だけです。

チームのドメイン知識を足すことが、そのままコマンド実行権限を渡すことになってはいけません。他の型が運ぶのは、プロバイダが読むテキストだけです。

紛らわしい kind（core / official / domain / project）は tier 順を決めるだけで、権限ではありません。

pack を作る。最短の一周

$ rig-wb pack init my-domain --type knowledge --kind domain --root .rig/packs
initialized: .rig/packs/my-domain

next:
  1. write an asset          my-domain/facets/knowledge/<name>.md
  2. rig-wb pack sync .rig/packs/my-domain
  3. rig-wb pack validate .rig/packs/my-domain

pack.yaml は手で編集しません

マニフェストは全アセットをパスと sha256 で宣言し、検証のときに正準形とバイト単位で比較されます。つまり生成物であって、手書きするものではありません。

$ vi .rig/packs/my-domain/facets/knowledge/backup-policy.md
$ rig-wb pack sync .rig/packs/my-domain
  + facets/knowledge/backup-policy.md
pack sync: 1 asset(s) declared and hashed

sync はディレクトリを鏡写しにします。消したファイルは宣言からも消えます。書き換わるのは assets と hashes だけです。

valid は「完成」という意味ではありません

空の pack もスキーマは満たすので valid と出ます。嘘ではないのですが、完成と読み違えやすいところです。その状態は doctor が名指ししてくれます。

$ rig-wb pack doctor .rig/packs/my-domain
pack doctor: warning
- empty_pack: .rig/packs/my-domain

doctor は警告では exit 0 を返します。failed だけがエラーです。

wiki を入れると、評価ゲートが立ちます

wiki はプロンプト素材です。プロバイダに見せるテキストだからです。そのため wiki を持つ pack には、承認済みの評価ケースが最低一件必要になります。

$ rig-wb pack validate .rig/packs/my-domain
[ERROR] prompt-bearing pack requires at least one evaluation case

会社の知識ページも、他のプロンプト面と同じ規律で扱われます。事故ではなく、意図された挙動です。

承認はフラグを立てる作業ではありません

# draft は pack の外（プロジェクト側）に書く
#   .rig/evals/drafts/<case-id>/case.json
#   prompt_surfaces に ["wiki:backup-policy"] と面を名指しする
$ rig-wb eval run <case-id> --repo . --phase baseline --provider ...
$ rig-wb eval run <case-id> --repo . --phase current  --provider ...
$ rig-wb eval compare --baseline ... --current ... --repo .
$ rig-wb eval promote <case-id> ... --into .rig/packs/my-domain
$ rig-wb pack sync .rig/packs/my-domain
$ rig-wb pack validate .rig/packs/my-domain
valid: my-domain@0.1.0

promote は、閾値を満たさない証拠を拒否します。結果には署名がつくので、編集された結果は閾値の前に落ちます。

忘れやすい一手：entrypoint

ケースが実際に走るには、prompt_entrypoint がマニフェストの宣言する entrypoint を名指しする必要があります。知識 pack では、それはページ自身です。

entrypoints:
  - id: backup-policy
    kind: wiki
    target: backup-policy

書き忘れても pack validate は通ります。ただし pack test は structural_only と報告します。ケースは同梱され、ハッシュされ、それでも誰にも実行されません。

その pack は何について書かれているのか

knowledge:
  scope: ["company"]
  topics: ["access-control", "backup", "encryption"]
  owner: "Corp IT"
  evidence: ["情報セキュリティ規程", "運用設計書"]
  reviewed_at: "2026-08-01T00:00:00+00:00"

ブロック自体は任意です。ただし半分だけ書かれたブロックは許されません。置いたなら五つとも必須で、理由は reviewed_at にあります。見直し日のない知識宣言こそ、誰にも気づかれずに古びていくからです。

evidence だけは、ソートを求められません

人が書いた文書の題名を、書いた言語のまま並べるからです。コードポイント順は誰にも予測できません（運用設計書 は 情報セキュリティ規程 の後に来ます）。

そして順序そのものが意味を運びます。引用リストは、主に依拠している文書から始まります。

重複は拒否されます。同じ文書を二度引くと、答えの裏づけの厚さを水増しすることになるからです。

質問の側から、答えられる pack を探します

rig-wb pack knowledge                     # このスコープの全宣言
rig-wb pack knowledge --topic backup
rig-wb pack knowledge --topic backup --scope product

「バックアップは取っていますか」には、会社としての正解と、ある製品としての正解と、その下のインフラとしての正解が別々にあります。そして質問した側は、どれのつもりだったかを決めていないことが多いのです。

選び出しますが、決めはしません

$ rig-wb pack knowledge --topic backup
company-security@0.1.0   company             Corp IT   reviewed 2026-08-01
  evidence: 情報セキュリティ規程, 運用設計書
product-security@0.1.0   product:northwind-one  Northwind    reviewed 2026-07-15
  evidence: サービス仕様書
scope is ambiguous: company, product:northwind-one
  — narrow with --scope before treating any of these as the answer

どちらのつもりだったかは質問した人についての事実で、どの pack にも書かれていません。だから rig は推測せず、問いが開いているという事実と、選択肢の正確な集合を返します。

影に隠れたページも、ラベルつきで並べます

wiki: pack://user/company-security/facets/knowledge/backup-policy.md
        [shadowed by product-security]

隠せば「ファイルはどこへ行った」と言わせることになりますし、黙って引用すれば、誰も読まないテキストの背後に答えを置くことになります。

pack を渡す

$ rig-wb pack bundle .rig/packs/my-domain
bundled: my-domain@0.1.0 (3 file(s)) -> dist/my-domain-0.1.0.zip
  sha256: 7ef9b1a3...

$ rig-wb pack install dist/my-domain-0.1.0.zip --scope project

バイト列は再現可能です。毎回変わる zip は毎回「変わりました」と報告することになり、それは何も報告していないのと同じです。

rig は資格情報を一切持ちません

rig-wb pack source add product --scheme git+ssh \
    --url git@github.com:acme/rig-pack-{pack}.git
rig-wb pack install product:northwind@1.4.0 --scope project
rig-wb pack verify-sources --scope project

git を呼ぶだけで、認証はすでに設定済みのもの（SSH agent・credential helper・CI secret）が答えます。トークンを埋め込んだ URL は拒否されます。

lock が記録するのはソースの名前と commit で、URL は記録しません。だから rig が書くファイルは、資格情報を運びようがありません。

info と explain は別の問いに答えます

  • info身元と来歴です。出所・digest・engine・依存。lock が知っていることを答えます。
  • explainそのアセットが tier 争いに勝っているかどうか。resolver しか知らないことを答えます。

pack はインストール済みで valid なのに、完全に影へ隠れている状態です。「override したのに何も起きない」の正体は、たいていこれです。

引っかかりやすいところ（1／2）

  • valid は完成ではありませんdoctor の empty_pack 警告を見てください
  • pack.yaml は手で書きません「たまたま一致する」か「間違っている」かにしかなりません
  • 署名した pack は sync できません署名を外し、sync してから、署名し直してください
  • install しただけではコマンドになりませんcommand アセットは、明示登録を扱えるホスト向けの資料です

引っかかりやすいところ（2／2）

  • project pack は初回に同意が要りますRIG_ALLOW_PROJECT_PACKS=1 で同意します。同意は内容ハッシュに紐づきます
  • user / org は品質検証を回避できません--allow-unverified が使えるのは project スコープだけです
  • mock は品質の証拠になりません結果は non_quality_mock と明示されます
  • digest は「誰が」を答えません出所を答えるのは署名と trust root です。private であることは、その代わりになりません

明日からの順番

  • 1　/rig:go と diff / accept / discard だけ使ってみてください。ゲートに一度落ちて、なぜ落ちたかを読むところまで来れば、rig が何をする道具かは体で分かります。
  • 2　/rig:knowledge でページを一枚書き、persona の inject: から参照させます。
  • 3　効くと確信できてから pack init --type knowledge で配布物に格上げします。

順番を逆にすると、まだ効くか分からないものに評価ケースを書くことになります。
