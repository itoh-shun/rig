RIG

AI に仕事を任せるための、隔離と検証の層。
ゼロから知るための三十分。

今日の地図

  • 第一部 — rig を知る何をする道具か。なぜ安全と言えるのか。日常の三コマンド。
  • 第二部 — pack で知識層を拡張する専用領域の知識を、配布物として渡す方法。

典拠：README.ja.md / docs/packs.md / skills/engine/SKILL.md

危ないのは、AI が間違えることではない

間違えたことに誰も気づかないまま、本体に混ざることだ。

rig はそこだけを構造で潰す。自然文でタスクを頼むと、種類を判定し、部品を組み合わせてハーネスを合成し、隔離された git worktree の中で作業し、明示的な基準で検証し、あなたが accept と言うまで本体に触れない。

最初に誤解を外す

  • 品質を自動的に生む道具ではないあなたが定義した品質基準を、AI に無視させないための道具。基準を作るのは人間の仕事のまま。rig の仕事は強制と測定。
  • 対価がある隔離・検証・記録のために、速度とトークンを意図的に払う。速く書かせたいだけなら直接頼むほうが速い。
  • 効いてくる場面失敗したときのコストが、速度より高いとき。

直接頼む場合と、何が違うか

直接頼むrig 経由
失敗した変更作業ツリーに残るworktree ごと破棄、本体は無傷
「できました」信じるしかないacceptance-gate の合否が根拠
レビューの質不明検出率を実測できる
何が起きたかチャットログrun log と監査証跡

第一部

隔離

入口は二つ。中身は同じエンジン

Claude Code の中では、プラグイン

/plugin marketplace add itoh-shun/sito-plugins
/plugin install rig@sito-plugins

それ以外の場所では、rig-wb CLI

pipx install git+https://github.com/itoh-shun/rig.git
rig-wb version

CI・スクリプト・別のアシスタント（Codex / Cursor）から同じ recipe とゲートを回すためのもの。両方は要らない。

最初の三十秒。設定はゼロでいい

/rig:go "ログインバグを直して"
/rig:go "このPRを厳しめにレビューして"
/rig:go "今の変更が安全か確認して"

manifest も gates.json も persona 設定も要らない。すべて後から足す opt-in。

なぜその段取りになったかを、先に宣言する

▸ rig
task:     ログインバグを直して
detected: bugfix
recipe:   bugfix — 「バグ」「直して」を検出
mode:     isolated worktree
gate:     standard + bugfix

そして、確認して、決める

/rig:go diff       # 何が変わったか、なぜ安全か
/rig:go accept     # 作業ツリーへ反映（gate 未達なら拒否される）
/rig:go discard    # 破棄（作業ツリーは最初から触られていない）

日常操作はこの三つがすべて。

「安全です」は主張にすぎない

rig が安全なのは、次の四つが文章ではなく配線として入っているからだ。

  • 一　隔離された worktree
  • 二　acceptance-gate
  • 三　read-only な検証役
  • 四　明示的な accept と、消えない記録

一　隔離された worktree

タスクごとに専用の worktree と使い捨てブランチ。rig はあなたの作業ツリーに直接書き込まない。

<repoの親>/rig-worktrees/<repo名>/rig-20260704-153012-login-fix/
<repo>/.rig/runs/rig-20260704-153012-login-fix/
    task.json        入力 / task_type / recipe / base branch / status
    acceptance.json  基準ごとの合否と根拠
    diff.md          Summary / Risk / Tests / Unrelated diff

隔離がタスク単位で閉じているので、複数タスクの同時実行が構造的に安全。並列プロセス同士がファイルを取り合わない。

二　acceptance-gate

モデルが「完了しました」と言っただけでは完了にならない。無関係な差分は混じっていないか。テストと型は通るか。リスクは書かれたか。秘密情報は漏れていないか。

failed か pending が一件でも残っていれば、accept は機械的に拒否される。

ゲートは standard ＋ 種別プリセット

preset基準の例
standardno_unrelated_diff / risk_summary_written / tests_pass_or_explained / no_secret_leak / no_gate_tampering / no_injection_markers / no_destructive_operation
bugfixbug_cause_identified / fix_is_minimal / regression_test_added_or_explained
featureimplementation_matches_requirement / tests_added_or_explained / public_api_changes_documented
refactorno_unintended_behavior_change / tests_confirm_behavior_preserved
securityauthn_authz_impact_checked / user_input_flow_checked / dependency_risk_checked

自己申告ではなく、機械センサーが裏づける

  • 秘密情報スキャン ／ インジェクション・マーカー検出
  • 破壊的コマンド検出 ／ ゲート改竄の検出 ／ OpenAPI スキーマ差分

プロジェクト側で基準を足せる（.rig/gates.json）。ただし加算のみ。削除と緩和キーは即座に拒否される。

リポジトリの中のファイルが、そのリポジトリを守るゲートを弱めることはできない。

三　read-only な検証役

実装する AI と検証する AI を分離し、検証側はプロセスレベルで読み取り専用に固定する。お願いではなく、強制として。

claude --allowedTools Read,Grep,Glob
codex  --sandbox read-only

見て、grep して、指摘は書ける。編集・commit・formatter による書き換えはできない。

検証役が読むのは、レポートではない

判定の一次証拠は worktree の実際の git diff。生成側が書いた自己申告レポートは、「未検証の主張」というラベルつきで渡されるだけだ。

同系統のモデルが自分の成果物をレビューする状況を、構造的に避けるための設計。

四　明示的な accept と、消えない記録

  • accept は staged で止まるsquash merge で未コミット反映。コミットは常に人間が打つ。
  • discard しても run log は残る何を試みて、なぜ捨てたかは後から必ず辿れる。
  • 構造的な前提は --force でも通らないdiff.md が無ければ accept できない。例外なし。

測れないゲートは、
願望にすぎない。

中身は四種類のブリック

  • persona誰が判定するか
  • instruction何をするか
  • patternどう分配し、どうゲートするか
  • recipestep の束（bugfix / feature / review-only / release-flow …）

/rig:go はこの組み立てを自動でやる。/rig:dev は同じエンジンを recipe・step・flag すべて明示して使う入口。

レビュアーは、測れる

/rig:drill は既知のバグを使い捨ての diff に注入し、レビューを走らせ、reviewer には見せない答案キーと突き合わせて採点する。

# Drill Result — strict_senior_engineer
Detection rate:    82%
False positive:    12%
Severity accuracy: 76%

## Missed Issues
1. SQL injection risk in search query (src/search.py:88)
2. Missing authorization check (src/api/users.py:120)

そして、ゴム印を名指しする

Verifier behavior:
- strict_senior_engineer: 14 runs, 6 rejects
- product_reviewer:        6 runs, 0 rejects

Warning:
product_reviewer has 0 rejects across 6 runs.
Possible rubber-stamp behavior.

レビューが儀式になっていることは、こうやって初めて見える。

第二部

PACK

知識層とは何か

subagent のプロンプトに注入される、ドメイン記述知識のこと。

「この会社ではバックアップをこう定義している」「この製品のユビキタス言語はこれだ」——コードを読んでも出てこない事実を、レビュアーや実装役に持たせるための層。

実体は二種類。性格がはっきり違う

セッション知識層pack
作り方/rig:knowledgerig-wb pack
配布できないzip / git で配れる
版と改竄管理しないversion・sha256・lock
品質本人の目承認済み評価ケースが必須
向く場面今すぐ効かせたいチームに同じ知識を効かせたい

手元で育てるなら前者で十分。他人に渡した瞬間に必要になるのが後者——誰が書いたか、いつ見直したか、根拠は何か、途中で書き換わっていないか。

知識の中心は wiki。persona は参照する

# persona: house-authenticity
inject: ["[[genre-house]]", "[[music-era-90s]]"]

一つの概念につき一枚の正準ページ。事実を persona の本文に埋め込まない。

埋め込むと知識が暗黙知になる。参照にしておけば、ページを一枚直すだけで、参照している全 persona の判断が同時に更新される。

[[slug]] は tier 解決される

  • 1　project overlay　<repo>/.claude/rig/knowledge/wiki/
  • 2　global　~/.claude/rig/knowledge/wiki/
  • 3　org　チームで共有する層
  • 4　pack 同梱　<pack>/facets/knowledge/<slug>.md
  • 5　shipped　rig が最初から持つページ

pack の persona は、まず自分の pack の中を見る。pack は必要なページを同梱して持ち歩く。同じ slug をプロジェクト側に置けば、従来どおり上書きできる。

type が決めるのは、権限

type持てるものホストのコマンドを走らせるか
knowledgewiki・resource・評価ケースいいえ
policy上記 ＋ policyいいえ
reviewer上記 ＋ persona・output-contractいいえ
skill / workflowすべてのプロンプト種別いいえ
toolすべてはい

既定値を持たない。既定値を置くと、その決定を「決めなかった人」に渡してしまうから。

右端の列が、この型モデルの存在理由

recipe に checks:（ホスト上で実行されるシェルコマンド）を書けるのは tool だけ。

チームのドメイン知識を追加することが、同時にコマンド実行権限を渡すことになってはいけない。他の型が運ぶのは、プロバイダが読むテキストだけだ。

紛らわしい kind（core / official / domain / project）は tier 順を決めるだけで、権限ではない。

作る — 最短の一周

$ rig-wb pack init my-domain --type knowledge --kind domain --root .rig/packs
initialized: .rig/packs/my-domain

next:
  1. write an asset          my-domain/facets/knowledge/<name>.md
  2. rig-wb pack sync .rig/packs/my-domain
  3. rig-wb pack validate .rig/packs/my-domain

pack.yaml は手で編集しない

マニフェストは全アセットをパスと sha256 で宣言し、検証時に正準形とバイト比較される。だから生成物であって、手書きの対象ではない。

$ vi .rig/packs/my-domain/facets/knowledge/backup-policy.md
$ rig-wb pack sync .rig/packs/my-domain
  + facets/knowledge/backup-policy.md
pack sync: 1 asset(s) declared and hashed

sync はディレクトリを鏡写しにする。消したファイルは宣言からも消える。書き換えるのは assets と hashes だけ。

valid は「完成」ではない

空の pack もスキーマは満たすので valid と出る。それは真実だが、完成と読み違えやすい。doctor がその状態を名指しする。

$ rig-wb pack doctor .rig/packs/my-domain
pack doctor: warning
- empty_pack: .rig/packs/my-domain

doctor は警告では exit 0 を返す。failed だけがエラー。

wiki を入れた瞬間、評価ゲートが立つ

wiki はプロンプト素材だ——プロバイダに見せるテキストである。だから wiki を持つ pack には、承認済みの評価ケースが最低一件必要になる。

$ rig-wb pack validate .rig/packs/my-domain
[ERROR] prompt-bearing pack requires at least one evaluation case

会社の知識ページも、他のプロンプト面と同じ規律で統治される。事故ではなく意図された挙動。

承認は、フラグで立てるものではない

# draft は pack の外（プロジェクト側）に書く
#   .rig/evals/drafts/<case-id>/case.json
#   prompt_surfaces に ["wiki:backup-policy"] と面を名指しする
$ rig-wb eval run <case-id> --repo . --phase baseline --provider ...
$ rig-wb eval run <case-id> --repo . --phase current  --provider ...
$ rig-wb eval compare --baseline ... --current ... --repo .
$ rig-wb eval promote <case-id> ... --into .rig/packs/my-domain
$ rig-wb pack sync .rig/packs/my-domain
$ rig-wb pack validate .rig/packs/my-domain
valid: my-domain@0.1.0

promote は閾値を満たさない証拠を拒否する。結果には署名がつくので、編集された結果は閾値を見る前に落ちる。

忘れやすい一手：entrypoint

ケースが実際に走るには、prompt_entrypoint がマニフェストの宣言する entrypoint を名指ししていなければならない。知識 pack では、それはページ自身だ。

entrypoints:
  - id: backup-policy
    kind: wiki
    target: backup-policy

書き忘れても pack validate は通る。だが pack test は structural_only と報告する——ケースは同梱され、ハッシュされ、そして誰にも実行されない。

その pack は、何について書かれているのか

knowledge:
  scope: ["company"]
  topics: ["access-control", "backup", "encryption"]
  owner: "Corp IT"
  evidence: ["情報セキュリティ規程", "運用設計書"]
  reviewed_at: "2026-08-01T00:00:00+00:00"

ブロック自体は任意。だが半分だけ書かれたブロックは許されない。置いた以上は五つとも必須で、理由は reviewed_at にある——見直し日のない知識宣言こそ、誰にも気づかれずに腐る。

evidence だけは、ソートを要求されない

人が書いた文書の題名で、しかも書いた言語のままだからだ。コードポイント順は誰にも予測できない（運用設計書 は 情報セキュリティ規程 の後に来る）。

そして順序自体が意味を運ぶ。引用リストは、主に依拠している文書から始まる。

重複は拒否される。同じ文書を二度引くと、答えの裏づけの厚さを水増しすることになるから。

質問の側から、答えうる pack を探す

rig-wb pack knowledge                     # このスコープの全宣言
rig-wb pack knowledge --topic backup
rig-wb pack knowledge --topic backup --scope product

「バックアップは取っていますか」には、会社としての正解と、ある製品としての正解と、その下のインフラとしての正解が別々にある。そして質問した側は、どれのつもりだったかを決めていないことが多い。

選び出すが、決めはしない

$ rig-wb pack knowledge --topic backup
company-security@0.1.0   company             Corp IT   reviewed 2026-08-01
  evidence: 情報セキュリティ規程, 運用設計書
product-security@0.1.0   product:northwind-one  Northwind    reviewed 2026-07-15
  evidence: サービス仕様書
scope is ambiguous: company, product:northwind-one
  — narrow with --scope before treating any of these as the answer

どちらのつもりだったかは質問者についての事実で、どの pack にも書かれていない。だから rig は推測せず、問いが開いているという事実と、選択肢の正確な集合を返す。

影に隠れたページは、ラベルつきで列挙される

wiki: pack://user/company-security/facets/knowledge/backup-policy.md
        [shadowed by product-security]

隠せば「ファイルはどこへ行った」と言わせることになり、黙って引用すれば誰も読まないテキストの背後に答えを置くことになる。

渡す

$ rig-wb pack bundle .rig/packs/my-domain
bundled: my-domain@0.1.0 (3 file(s)) -> dist/my-domain-0.1.0.zip
  sha256: 7ef9b1a3...

$ rig-wb pack install dist/my-domain-0.1.0.zip --scope project

バイト列は再現可能。毎回変わる zip は毎回「変わりました」と報告することになり、つまり何も報告しないのと同じになる。

rig は資格情報を一切持たない

rig-wb pack source add product --scheme git+ssh \
    --url git@github.com:acme/rig-pack-{pack}.git
rig-wb pack install product:northwind@1.4.0 --scope project
rig-wb pack verify-sources --scope project

git を呼ぶだけで、認証はすでに設定済みのもの（SSH agent・credential helper・CI secret）が答える。トークンを埋めた URL は拒否される。

lock が記録するのはソースの名前と commit であって URL ではない。rig が書くファイルは、資格情報を運びようがない。

info と explain は別の問いに答える

  • info身元と来歴。出所・digest・engine・依存。lock が知っていること。
  • explainそのアセットが tier 争いに勝っているか。resolver しか知らないこと。

pack がインストール済みで、valid で、しかし完全に影に隠れている——「override したのに何も起きない」の正体はたいていこれ。

引っかかりやすいところ（1／2）

  • valid は完成ではないdoctor の empty_pack 警告を見る
  • pack.yaml を手で書かない「たまたま一致する」か「間違っている」かにしかならない
  • 署名した pack は sync できない署名を外し、sync し、署名し直す
  • install しただけではコマンドにならないcommand アセットは明示登録を扱えるホスト向けの資料

引っかかりやすいところ（2／2）

  • project pack は初回に同意が要るRIG_ALLOW_PROJECT_PACKS=1。同意は内容ハッシュに紐づく
  • user / org は品質検証を回避できない--allow-unverified は project スコープだけ
  • mock は品質の証拠ではない結果は non_quality_mock と明示される
  • digest は「誰が」を答えない出所を答えるのは署名と trust root。private であることは代わりにならない

明日からの順番

  • 1　/rig:go と diff / accept / discard だけ使う。ゲートに一度落ちて、なぜ落ちたかを読むところまで来れば、rig が何を売っているかは体で分かる。
  • 2　/rig:knowledge でページを一枚書き、persona の inject: から参照させる。
  • 3　効くと確信できてから pack init --type knowledge で配布物に格上げする。

順番を逆にすると、まだ効くか分からないものに評価ケースを書く羽目になる。
