RIG

AI に仕事をおまかせするときの、隔離と検証のしくみ。
はじめての人が、三十分で全体をつかむための資料です。

今日の流れ

  • 第一部　rig を知る何をする道具なのか。なぜ安全と言えるのか。ふだん使う三つのコマンド。
  • 第二部　pack で知識層を拡張する自分の領域の知識を、配布物として渡す方法です。

典拠：README.ja.md / docs/packs.md / skills/engine/SKILL.md

困るのは、AI が間違えることではないんです

間違えたことに誰も気づかないまま、本体に混ざってしまうこと。そこが怖いところです。

rig が塞ぐのは、そこだけです。ふつうの言葉でタスクを頼むと、種類を見分けて、部品を組み合わせてハーネスを作り、隔離された git worktree の中で作業します。決めておいた基準でたしかめて、あなたが accept と言うまで本体には触れません。

先に外しておきたい誤解

  • 品質そのものを生む道具ではありませんあなたが決めたルールを、AI に飛ばさせないための道具です。ルールを決めるのは人の仕事のまま。rig がやるのは、守らせることと測ることだけです。
  • そのかわり、払うものがあります隔離と検証と記録のために、速さとトークンをわざと差し出しています。とにかく速く書かせたいだけなら、直接お願いするほうが早いです。
  • 効いてくる場面失敗したときの痛手が、速さより大きい場面です。

直接頼む場合と、何が違うか

直接頼むrig 経由
失敗した変更作業ツリーに残るworktree ごと破棄、本体は無傷
「できました」信じるしかないacceptance-gate の合否が根拠
レビューの質不明検出率を実測できます
何が起きたかチャットログrun log と監査証跡

第一部

隔離

入口は二つ。中身は同じエンジン

Claude Code の中では、プラグイン

/plugin marketplace add itoh-shun/sito-plugins
/plugin install rig@sito-plugins

それ以外の場所では、rig-wb CLI

pipx install git+https://github.com/itoh-shun/rig.git
rig-wb version

CI やスクリプト、ほかのアシスタント（Codex / Cursor）から同じ recipe とゲートを回すためのものです。両方そろえる必要はありません。

最初の三十秒。設定はゼロのままで大丈夫です

/rig:go "ログインバグを直して"
/rig:go "このPRを厳しめにレビューして"
/rig:go "今の変更が安全か確認して"

manifest も gates.json も persona の設定も要りません。ぜんぶ後から足せます。

どうしてその段取りにしたのかを、先に見せてくれます

▸ rig
task:     ログインバグを直して
detected: bugfix
recipe:   bugfix — 「バグ」「直して」を検出
mode:     isolated worktree
gate:     standard + bugfix

あとは確認して、決めるだけ

/rig:go diff       # 何が変わったか、なぜ安全か
/rig:go accept     # 作業ツリーへ反映（gate 未達なら拒否される）
/rig:go discard    # 破棄（作業ツリーは最初から触られていない）

ふだん使うのは、この三つだけです。

rig が安全だと言える、四つの理由

安全だと言えるのは、次の四つが文章ではなく仕組みとして組み込まれているからです。

  • ①　隔離された worktree
  • ②　acceptance-gate
  • ③　read-only な検証役
  • ④　明示的な accept と、消えない記録

一　隔離された worktree

タスクごとに、専用の worktree と使い捨てのブランチを作ります。rig があなたの作業ツリーに直接書き込むことはありません。

<repoの親>/rig-worktrees/<repo名>/rig-20260704-153012-login-fix/
<repo>/.rig/runs/rig-20260704-153012-login-fix/
    task.json        入力 / task_type / recipe / base branch / status
    acceptance.json  基準ごとの合否と根拠
    diff.md          Summary / Risk / Tests / Unrelated diff

タスクごとに閉じているので、何本か同時に走らせても大丈夫です。プロセス同士がファイルを取り合うこともありません。

二　acceptance-gate

モデルが「完了しました」と言っただけでは、終わったことになりません。関係ない差分は混じっていないか。テストと型は通るか。リスクは書かれたか。秘密情報は漏れていないか。ここを機械が見ます。

failed か pending が一件でも残っていれば、accept ははじかれます。

ゲートは standard ＋ 種別プリセット

preset基準の例
standardno_unrelated_diff / risk_summary_written / tests_pass_or_explained / no_secret_leak / no_gate_tampering / no_injection_markers / no_destructive_operation
bugfixbug_cause_identified / fix_is_minimal / regression_test_added_or_explained
featureimplementation_matches_requirement / tests_added_or_explained / public_api_changes_documented
refactorno_unintended_behavior_change / tests_confirm_behavior_preserved
securityauthn_authz_impact_checked / user_input_flow_checked / dependency_risk_checked

基準は、機械が裏づけてくれます

  • 秘密情報スキャン ／ インジェクション・マーカー検出
  • 破壊的コマンド検出 ／ ゲート改竄の検出 ／ OpenAPI スキーマ差分

プロジェクト側で基準を足せます（.rig/gates.json）。ただし足す方向だけです。消したりゆるめたりするキーは、その場ではじかれます。

リポジトリの中のファイルが、そのリポジトリを守っているゲートをゆるめることはできません。

三　read-only な検証役

書く AI と、たしかめる AI を分けます。たしかめる側はプロセスの段階で読み取り専用に固定されます。お願いではなく、そうとしか動けない状態です。

claude --allowedTools Read,Grep,Glob
codex  --sandbox read-only

見て、grep して、指摘を書くことはできます。編集も commit も、formatter での書き換えもできません。

たしかめる側が読むのは、レポートではありません

いちばんの根拠は worktree の実際の git diff です。書いた側のレポートは「まだ確かめていない主張」というラベルつきで渡るだけです。

似たモデルが自分の成果物をレビューしてしまう状況を、仕組みのうえで避けるための設計です。

四　明示的な accept と、消えない記録

  • accept は staged で止まりますsquash merge で、コミット前の状態まで反映します。コミットするのはいつも人です。
  • discard しても run log は残ります何を試して、なぜ捨てたのかを後から追えます。
  • 土台になる前提は --force でも通りませんdiff.md が無ければ accept できません。例外はありません。

測っていないゲートは、
効いているかどうかも分かりません。

中身は四種類のブリック

  • persona誰が判定するか
  • instruction何をするか
  • patternどう分配し、どうゲートするか
  • recipestep の束です（bugfix / feature / review-only / release-flow …）

/rig:go はこの組み立てを自動でやってくれます。/rig:dev のほうは、recipe も step も flag も自分で指定したい人向けの入口です。

レビュアーの実力は、ちゃんと測れます

/rig:drill は、わざと仕込んだバグを使い捨ての diff に入れてレビューを走らせ、reviewer には見せていない答え合わせ用のキーと照らして採点します。

# Drill Result — strict_senior_engineer
Detection rate:    82%
False positive:    12%
Severity accuracy: 76%

## Missed Issues
1. SQL injection risk in search query (src/search.py:88)
2. Missing authorization check (src/api/users.py:120)

形だけのレビューも、ちゃんと教えてくれます

Verifier behavior:
- strict_senior_engineer: 14 runs, 6 rejects
- product_reviewer:        6 runs, 0 rejects

Warning:
product_reviewer has 0 rejects across 6 runs.
Possible rubber-stamp behavior.

レビューがただの儀式になっていることは、こうやって初めて見えてきます。

第二部

PACK

知識層とは何か

subagent のプロンプトに差し込まれる、「その領域の知識」のことです。

「うちの会社ではバックアップをこう呼んでいる」「この製品ではこの言葉をこう使う」。こういうコードを読んでも出てこない事実を、レビュアーや実装役に持たせておくための層です。

中身は二種類。性格がはっきり違います

セッション知識層pack
作り方/rig:knowledgerig-wb pack
配布できませんzip / git で配れる
版と改竄管理しないversion・sha256・lock
品質本人の目承認済み評価ケースが必須
向く場面今すぐ効かせたいときチームに同じ知識を効かせたいとき

手元で育てるなら、前者でじゅうぶんです。人に渡すときに出番が来るのが後者。誰が書いたか、いつ見直したか、根拠は何か、途中で書き換わっていないか。この四つをちゃんと構造として持っています。

中心にあるのは wiki。persona はそれを見にいきます

# persona: house-authenticity
inject: ["[[genre-house]]", "[[music-era-90s]]"]

一つの概念につき、正しいページを一枚だけ書きます。事実を persona の本文に書き写すことはしません。

書き写してしまうと、その知識は誰にも見えない暗黙知になります。参照にしておけば、ページを一枚直すだけで、見にきている persona 全員の判断がいっぺんに新しくなります。

[[slug]] は tier で解決されて、上の層が勝ちます

  • 1　project overlay　<repo>/.claude/rig/knowledge/wiki/
  • 2　global　~/.claude/rig/knowledge/wiki/
  • 3　org　チームで共有する層
  • 4　pack 同梱　<pack>/facets/knowledge/<slug>.md
  • 5　shipped　rig にはじめから入っているページ

pack の persona は、まず自分の pack の中をのぞきます。pack は要るページを一緒に持ち歩くからです。同じ slug をプロジェクト側に置けば、これまでどおり上書きできます。

type が決めているのは、権限です

type持てるものホストのコマンドを走らせるか
knowledgewiki・resource・評価ケースいいえ
policy上記 ＋ policyいいえ
reviewer上記 ＋ persona・output-contractいいえ
skill / workflowすべてのプロンプト種別いいえ
toolすべてはい

初期値は用意していません。置いてしまうと、大事な判断を「何も決めなかった人」に押しつけることになるからです。

右端の列こそ、この型モデルがある理由です

recipe に checks:（手元のマシンで動くシェルコマンド）を書けるのは tool だけです。

チームの知識を足すことが、そのままコマンドを動かす権限を渡すことになってはいけません。ほかの型が運ぶのは、プロバイダが読むテキストだけです。

まぎらわしい kind（core / official / domain / project）は tier の順番を決めるだけで、権限ではありません。

pack を作ってみる。最短の一周

$ rig-wb pack init my-domain --type knowledge --kind domain --root .rig/packs
initialized: .rig/packs/my-domain

next:
  1. write an asset          my-domain/facets/knowledge/<name>.md
  2. rig-wb pack sync .rig/packs/my-domain
  3. rig-wb pack validate .rig/packs/my-domain

pack.yaml は手で書きません

マニフェストは中身をぜんぶパスと sha256 で宣言していて、検証のときに一字一句くらべられます。つまり自動で作られるものなので、手で書く場所ではないんです。

$ vi .rig/packs/my-domain/facets/knowledge/backup-policy.md
$ rig-wb pack sync .rig/packs/my-domain
  + facets/knowledge/backup-policy.md
pack sync: 1 asset(s) declared and hashed

sync はフォルダをそのまま写します。消したファイルは宣言のほうからも消えます。書き換わるのは assets と hashes だけです。

valid は「できあがり」ではありません

中身が空の pack でもスキーマは満たすので、valid と出てしまいます。嘘ではないのですが、できあがりと読み違えやすいところです。その状態は doctor が教えてくれます。

$ rig-wb pack doctor .rig/packs/my-domain
pack doctor: warning
- empty_pack: .rig/packs/my-domain

doctor は警告なら exit 0 を返します。failed だけがエラー扱いです。

wiki を入れたとたん、評価ゲートが立ちます

wiki はプロンプト素材です。プロバイダに見せるテキストだからですね。なので wiki を持つ pack には、承認ずみの評価ケースが最低ひとつ要ります。

$ rig-wb pack validate .rig/packs/my-domain
[ERROR] prompt-bearing pack requires at least one evaluation case

会社の知識ページも、ほかのプロンプト面とおなじルールで扱われます。うっかりそうなったのではなく、そう決めています。

承認はフラグを立てるだけでは済みません

# draft は pack の外（プロジェクト側）に書く
#   .rig/evals/drafts/<case-id>/case.json
#   prompt_surfaces に ["wiki:backup-policy"] と面を名指しする
$ rig-wb eval run <case-id> --repo . --phase baseline --provider ...
$ rig-wb eval run <case-id> --repo . --phase current  --provider ...
$ rig-wb eval compare --baseline ... --current ... --repo .
$ rig-wb eval promote <case-id> ... --into .rig/packs/my-domain
$ rig-wb pack sync .rig/packs/my-domain
$ rig-wb pack validate .rig/packs/my-domain
valid: my-domain@0.1.0

promote は、しきい値に届かない証拠を受けつけません。結果には署名がつくので、手を入れた結果はしきい値より先にはじかれます。

entrypoint を書き忘れると、走りません

ケースが実際に走るには、prompt_entrypoint にマニフェストが宣言している entrypoint を書いておく必要があります。知識 pack なら、それはページ自身です。

entrypoints:
  - id: backup-policy
    kind: wiki
    target: backup-policy

書き忘れても pack validate は通ってしまいます。でも pack test は structural_only と返します。ケースは同梱されて、ハッシュもされて、それでも誰にも動かされないままです。

その pack は何について書かれているのか

knowledge:
  scope: ["company"]
  topics: ["access-control", "backup", "encryption"]
  owner: "Corp IT"
  evidence: ["情報セキュリティ規程", "運用設計書"]
  reviewed_at: "2026-08-01T00:00:00+00:00"

ブロック自体は書かなくても大丈夫です。ただし半分だけというのは通りません。置いたなら五つとも必須で、理由は reviewed_at にあります。見直した日が書いていない知識ほど、誰にも気づかれないまま古くなっていくからです。

evidence だけは、並べ替えなくて大丈夫です

人が書いた資料の題名を、その言語のまま並べるからです。コードポイント順なんて誰にも予測できません（運用設計書 は 情報セキュリティ規程 の後に来ます）。

そして順番そのものが意味を持っています。引用リストは、いちばん寄りかかっている資料から始まるからです。

同じものを二度書くのは断られます。答えの裏づけを、実際より厚く見せてしまうからです。

質問の側から、答えられそうな pack を探します

rig-wb pack knowledge                     # このスコープの全宣言
rig-wb pack knowledge --topic backup
rig-wb pack knowledge --topic backup --scope product

「バックアップは取っていますか」には、会社としての答えと、ある製品としての答えと、その下のインフラとしての答えが別々にあります。しかも質問した側は、どれのつもりだったかを決めていないことが多いんです。

選び出しはしますが、決めはしません

$ rig-wb pack knowledge --topic backup
company-security@0.1.0   company             Corp IT   reviewed 2026-08-01
  evidence: 情報セキュリティ規程, 運用設計書
product-security@0.1.0   product:northwind-one  Northwind    reviewed 2026-07-15
  evidence: サービス仕様書
scope is ambiguous: company, product:northwind-one
  — narrow with --scope before treating any of these as the answer

どっちのつもりだったかは質問した人のなかにある事実で、どの pack にも書いてありません。だから rig は当てにいかず、「まだ決まっていませんよ」ということと、選べる候補をそのまま返します。

影に隠れたページも、隠さず並べます

wiki: pack://user/company-security/facets/knowledge/backup-policy.md
        [shadowed by product-security]

隠すと「あのファイルどこ行ったの」と言わせてしまいますし、黙って引用すると、誰も読まないテキストの裏に答えを置くことになってしまいます。

pack を渡す

$ rig-wb pack bundle .rig/packs/my-domain
bundled: my-domain@0.1.0 (3 file(s)) -> dist/my-domain-0.1.0.zip
  sha256: 7ef9b1a3...

$ rig-wb pack install dist/my-domain-0.1.0.zip --scope project

中身のバイト列は毎回おなじになります。毎回変わる zip は毎回「変わりました」と言うことになって、それでは何も言っていないのと同じですよね。

rig は資格情報をひとつも持ちません

rig-wb pack source add product --scheme git+ssh \
    --url git@github.com:acme/rig-pack-{pack}.git
rig-wb pack install product:northwind@1.4.0 --scope project
rig-wb pack verify-sources --scope project

git を呼ぶだけなので、認証はもう設定してあるもの（SSH agent・credential helper・CI secret）が答えてくれます。トークンを埋め込んだ URL は断られます。

lock に残るのはソースの名前と commit だけで、URL は書きません。だから rig が書くファイルには、資格情報が乗りようがないんです。

info と explain は、答える問いが違います

  • info身元と来歴です。出どころ・digest・engine・依存。lock が知っていることを答えます。
  • explainそのアセットが tier の勝負に勝てているかどうか。resolver しか知らないことを答えます。

入っていて valid なのに、まるごと影に隠れている状態です。「override したのに何も起きない」の正体は、たいていこれ。

引っかかりやすいところ（1／2）

  • valid はできあがりではありませんdoctor の empty_pack 警告を見てみてください
  • pack.yaml は手で書きません「たまたま合っている」か「間違っている」かのどちらかにしかなりません
  • 署名した pack は sync できませんいったん署名を外して、sync してから、署名し直してください
  • install だけではコマンドになりませんcommand アセットは、自分で登録できるホスト向けの資料です

引っかかりやすいところ（2／2）

  • project pack は最初に同意が要りますRIG_ALLOW_PROJECT_PACKS=1 で同意します。同意は中身のハッシュに結びつきます
  • user / org では品質検証を飛ばせません--allow-unverified が使えるのは project スコープだけです
  • mock は品質の証拠になりません結果に non_quality_mock とはっきり書かれます
  • digest は「誰が」までは答えません誰が作ったかを答えるのは署名と trust root です。private であることは、その代わりになりません

まずは、ここから

  • 1　/rig:go と diff / accept / discard だけ使ってみてください。ゲートに一度落ちて「なんで落ちたんだろう」と読むところまで来れば、rig がどういう道具かは自然と分かります。
  • 2　/rig:knowledge でページを一枚だけ書いて、persona の inject: から参照させてみます。
  • 3　効くと分かってから pack init --type knowledge で、ちゃんとした配布物にします。

順番を逆にすると、まだ効くか分からないものに評価ケースを書くことになってしまいます。
