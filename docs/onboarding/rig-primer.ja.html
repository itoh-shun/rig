RIG

$ /rig:go "ログインバグを直して"
detected: bugfix recipe: bugfix mode: isolated worktree
gate: passed_with_warnings
pack://project/company-security/ facets/knowledge/backup-policy.md

AI に仕事を任せるとき、困るのは AI が間違えることではありません。間違えたことに 誰も気づかないまま、本体に混ざってしまうことです。rig はそこだけを構造で塞ぎます。

第一部　rig を知る

N° 01: rig とは何か

rig は Claude Code のための品質オペレーティングシステムです。ふつうの言葉でタスクを頼むと、種類を見分けて、必要な部品を組み合わせてハーネスを作り、いま作業しているツリーとは隔離された git worktree の中で作業します。決めておいた受け入れ基準でたしかめて、あなたが accept と言うまで本体には一切触れません。

ここは、最初に誤解を外しておきたいところです。rig が品質そのものを生んでくれるわけではありません。あなたが決めたルールを、AI に飛ばさせないための道具です。ルールを決めるのは人の仕事のままで、rig がやるのは守らせることと測ることだけです。

そのかわり、払うものがあります。隔離と検証と記録のために、rig は速さとトークンをわざと差し出しています。とにかく速くコードを書かせたいだけなら、モデルに直接お願いするほうが早いです。rig が効いてくるのは、失敗したときの痛手が速さより大きい場面です。

直接頼む場合と何が違うか

直接頼むrig 経由
失敗した変更作業ツリーに残るworktree ごと破棄、本体は無傷
「できました」信じるしかないacceptance-gate の合否が根拠
レビューの質不明検出率を実測できる
何が起きたかチャットログrun log と監査証跡

N° 02: 入口は二つある

用途が違うだけで、動いている中身は同じエンジンです。多くの場合は一つめで足ります。

Claude Code の中では、プラグイン

/rig:go をはじめとするスラッシュコマンドは、ここから来ます。

/plugin marketplace add itoh-shun/sito-plugins
/plugin install rig@sito-plugins

それ以外の場所では、rig-wb CLI

同じエンジンを、Claude Code のセッションの外から動かすためのものです。CI やスクリプト、あるいはほかのアシスタント（Codex / Cursor / Copilot）から呼びます。

pipx install git+https://github.com/itoh-shun/rig.git
rig-wb version

すでに Claude Code の中にいるなら、/rig:setup が同じことをやってくれます。両方そろえる必要はありません。プラグインだけで安全なひと通りの流れは動きますし、CLI だけで CI から回せます。

N° 03: 最初の三十秒

まず、設定はゼロ。manifest も gates.json も persona の設定も要りません（ぜんぶ後から足せます）。箱から出したままの状態で動きます。

/rig:go "ログインバグを直して"
/rig:go "このPRを厳しめにレビューして"
/rig:go "今の変更が安全か確認して"

実行すると、どうしてその段取りにしたのかを一行で見せてから走り出します。

▸ rig
task:     ログインバグを直して
detected: bugfix
recipe:   bugfix — 「バグ」「直して」を検出
mode:     isolated worktree
gate:     standard + bugfix

終わったら、確認して、決めます。ふだん使うのはこの三つだけです。

/rig:go diff       # 何が変わったか、なぜ安全か
/rig:go accept     # 作業ツリーへ反映（gate 未達なら拒否される）
/rig:go discard    # 破棄（作業ツリーは最初から触られていない）

N° 04: なぜ安全と言えるのか

「安全です」は、それだけでは言っただけになってしまいます。rig が安全だと言えるのは、次の四つが文章ではなく仕組みとして組み込まれているからです。

① 隔離された worktree

タスクごとに、専用の git worktree と使い捨てのブランチを作ります。rig があなたの作業ツリーに直接書き込むことはありません。失敗しても途中でやめても、手元は何も汚れないままです。

<repoの親>/rig-worktrees/<repo名>/rig-20260704-153012-login-fix/
<repo>/.rig/runs/rig-20260704-153012-login-fix/
    task.json        入力 / task_type / recipe / base branch / status
    acceptance.json  基準ごとの合否と根拠
    diff.md          Summary / Risk / Tests / Unrelated diff

タスクごとに閉じているので、何本か同時に走らせても大丈夫です。別の worktree と別のブランチなので、プロセス同士がファイルを取り合いません。

② acceptance-gate

モデルが「完了しました」と言っただけでは、終わったことになりません。関係ない差分が混じっていないか、テストと型は通るか、リスクは書かれたか、秘密情報が漏れていないか。こうした機械のチェックを通って、はじめて反映の候補になります。failed か pending が一件でも残っていたら、accept ははじかれます。

③ read-only な検証役

書く AI と、たしかめる AI を分けます。たしかめる側はプロセスの段階で読み取り専用に固定されます。お願いではなく、そうとしか動けない状態です。reviewer は claude --allowedTools Read,Grep,Glob や codex --sandbox read-only で起動します。見て、grep して、指摘を書くことはできます。編集も commit も、formatter での書き換えもできません。

そしてたしかめる側が読むのは、worktree の実際の git diff です。書いた側のレポートは「まだ確かめていない主張」というラベルつきで渡るだけです。

④ 明示的な accept / discard と、消えない記録

accept は squash merge で staged（コミット前）まで反映します。コミットするのはいつも人です。discard は worktree とブランチを消しますが、run log は残ります。何を試して、なぜ捨てたのかは後から追えます。

N° 05: ゲートの中身

すべてのタスクは standard（全種別に共通）に、種別ごとのプリセットを重ねた基準リストを持ちます。

preset対象基準の例
standard全種別task_intent_satisfied / no_unrelated_diff / diff_summary_written / risk_summary_written / tests_pass_or_explained / no_secret_leak / no_gate_tampering / no_injection_markers / no_destructive_operation
bugfixbugfix, performancebug_cause_identified / fix_is_minimal / regression_test_added_or_explained / existing_behavior_preserved
featurefeature, testrequirement_summary_written / implementation_matches_requirement / tests_added_or_explained / public_api_changes_documented
refactorrefactorbehavior_boundaries_identified / no_unintended_behavior_change / tests_confirm_behavior_preserved
reviewreviewfindings_are_concrete / severity_labeled / file_references_included / false_positive_risk_considered
securitysecurity_reviewauthn_authz_impact_checked / user_input_flow_checked / secret_exposure_checked / dependency_risk_checked

大事なのは、これらが自己申告ではないところです。いくつかの基準は、毎回おなじ結果になる機械のセンサーが裏づけます。秘密情報スキャン、インジェクション・マーカー検出、危ないコマンドの検出、ゲートの書き換えの検出、OpenAPI のスキーマ差分。見つかれば理由つきで落ちます。

プロジェクト側で基準を足すこともできます（.rig/gates.json）。ただし足す方向だけです。もとからある基準を消したりゆるめたりするキーは、その場ではじかれます。リポジトリの中のファイルが、そのリポジトリを守っているゲートをゆるめることはできません。

測っていないゲートは、効いているかどうかも分かりません。

N° 06: 中身は四種類のブリック

rig は起動のときに、四種類の部品を組み合わせてハーネスを作ります。LEGO のブロックだと思ってください。

  • persona誰が判定するかを決めます。security-reviewer、design-reviewer など。
  • instruction何をするかを決めます。手順そのものです。
  • patternどう分配し、どうゲートするかを決めます。isolated-worktree、acceptance-gate など。
  • recipestep の束です。bugfix、feature、review-only、release-flow など。

/rig:go はこの組み立てを自動でやってくれます。自分で指定したくなったら、/rig:dev が同じエンジンへの入口になります。

/rig:dev --plan --only review "現在の変更"   # ドライラン：構成だけ見る
/rig:dev --recipe hotfix --issue 1234        # 緊急修正を最短経路で
/rig:dev --list                              # 全 tier の recipe を一覧

ここが後半につながります。自分の領域へ広げるというのは、この部品を足すことです。エンジンのほうは変わりません。

N° 07: レビュアーを測る

reviewer persona は、テストできます。/rig:drill が、わざと仕込んだバグ（認可漏れ、インジェクション、N+1、破壊的変更、片道 migration、テスト欠落など）を使い捨ての diff に入れてレビューを走らせ、reviewer には見せていない答え合わせ用のキーと照らして採点します。

# Drill Result — strict_senior_engineer
Detection rate:    82%
False positive:    12%
Severity accuracy: 76%

## Missed Issues
1. SQL injection risk in search query (src/search.py:88)
2. Missing authorization check (src/api/users.py:120)

/rig:go stats は過去の run を集計して、まったく reject していないレビュアーを名前つきで教えてくれます。「6 run で 0 reject。ゴム印の可能性」。レビューがただの儀式になっていることは、こうやって初めて見えてきます。

PACK

ここから後半です。専用領域の知識を、口伝でもコピペでもなく、 バージョンとハッシュと出典を持った配布物として渡す方法を扱います。

第二部　pack で知識層を拡張する

N° 09: 知識層とは何か、そしてなぜ二種類あるのか

rig の知識層は、subagent のプロンプトに差し込まれる「その領域の知識」です。

「うちの会社ではバックアップをこう呼んでいる」「この製品ではこの言葉をこう使う」。こういうコードをいくら読んでも出てこない事実を、レビュアーや実装役に持たせておくための層です。

中身は二つあって、性格がはっきり違います。

セッション知識層pack
置き場~/.claude/rig/knowledge/ と <repo>/.claude/rig/knowledge/.rig/packs/・~/.rig/packs/ ほか
作り方/rig:knowledge で生成rig-wb pack で組み立て
配布できない（自分の環境とこのリポジトリ限り）zip / git リポジトリで配れる
版と改竄管理しないversion・sha256・lock で固定
品質本人の目承認済み評価ケースが必須
向く場面思いついたことを今すぐ効かせたいチームや複数リポジトリに同じ知識を効かせたい

手元で育てるなら、前者でじゅうぶんです。人に渡すときに出番が来るのが後者です。誰が書いたのか、いつ見直したのか、根拠は何か、途中で書き換わっていないか。pack は、この四つをちゃんと構造として持っています。

N° 10: 知識はどう注入されるのか

知識層の中心にあるのが wiki です。一つの概念につき正しいページを一枚だけ書いて、[[slug]] でつなぎます。persona は事実を本文に書き写さず、ページを見にいきます。

# persona: house-authenticity
inject: ["[[genre-house]]", "[[music-era-90s]]"]

なぜ書き写さないのか。書き写すと、その知識が誰にも見えない暗黙知になってしまうからです。参照にしておけば、ページを一枚直すだけで、見にきている persona 全員の判断がいっぺんに新しくなります。

inject: の [[slug]] は tier で解決されます。同じ slug が複数の層にあれば、上の層が勝ちます。

  • 1. project overlay<repo>/.claude/rig/knowledge/wiki/
  • 2. global~/.claude/rig/knowledge/wiki/
  • 3. orgチームで共有する層
  • 4. pack 同梱<pack>/facets/knowledge/<slug>.md
  • 5. shippedrig が最初から持つページ

pack の中の persona が inject: を持つ場合は、まず自分の pack をのぞきます。pack は、自分の persona に要るページを一緒に持ち歩くからです。同じ slug をプロジェクト側に置けば、これまでどおり上書きできます。

N° 11: pack の型。何を持てて、何を実行できるか

type は必須で、初期値がありません。初期値を置くと、大事な判断を「何も決めなかった人」に押しつけてしまうからです。type が決めているのは権限です。

type持てるものホストのコマンドを走らせるか
knowledgewiki・resource・評価ケースと結果いいえ
policy上記 ＋ policyいいえ
reviewer上記 ＋ persona・output-contractいいえ
skillすべてのプロンプト種別（instruction・recipe・pattern・command・agent）いいえ
workflowskill と同じいいえ
toolすべてはい

この表のいちばん右の列こそ、pack の型モデルがある理由です。recipe の中に checks:（手元のマシンで動くシェルコマンド）を書けるのは tool だけ。チームの知識を足すことが、そのままコマンドを動かす権限を渡すことになってはいけません。ほかの型が運ぶのは、プロバイダが読むテキストだけです。

type とまぎらわしいのが kind（core / official / domain / project）ですが、こちらは tier の順番を決めるだけで、権限ではありません。

知識層を配るのが目的なら、まず knowledge。persona も一緒に配りたくなったら reviewer、recipe やコマンドまで入れるなら skill です。必要以上に強い型を選ばないでおくことが、そのまま受け取る側への安心につながります。

N° 12: pack を作る。最短の一周

まず骨組みを作ります。pack init は上書きを断って、標準のディレクトリをぜんぶ掘ってから、次にやることを教えてくれます。

$ rig-wb pack init my-domain --type knowledge --kind domain --root .rig/packs
initialized: .rig/packs/my-domain

next:
  1. write an asset          my-domain/facets/knowledge/<name>.md
  2. rig-wb pack sync .rig/packs/my-domain
  3. rig-wb pack validate .rig/packs/my-domain

ページを書いたら、pack.yaml は手で書きません。中身をぜんぶパスと sha256 で宣言していて、検証のときに一字一句くらべられます。つまり自動で作られるものなので、手で書く場所ではないんです。

$ vi .rig/packs/my-domain/facets/knowledge/backup-policy.md
$ rig-wb pack sync .rig/packs/my-domain
  + facets/knowledge/backup-policy.md
pack sync: 1 asset(s) declared and hashed

sync はフォルダをそのまま写します。消したファイルは宣言のほうからも消えます。書き換わるのは assets と hashes だけで、version・description・entrypoints はあなたのものです。

そして validate。ただ、ここに落とし穴があります。中身が空の pack でもスキーマは満たすので、valid と出てしまうんです。嘘ではないのですが、できあがりと読み違えやすいところです。その状態は doctor が教えてくれます。

$ rig-wb pack doctor .rig/packs/my-domain
pack doctor: warning
- empty_pack: .rig/packs/my-domain

読むだけの resource ファイルしか入っていない知識 pack なら、一周はここで閉じます。PDF や CSV のような資料はプロンプト素材ではないので、評価ゲートの対象になりません。

N° 13: wiki を入れた瞬間、評価ゲートが立つ

wiki はプロンプト素材です。プロバイダに見せるテキストだからですね。なので wiki を持つ pack には、承認ずみの評価ケースが最低ひとつ要ります。うっかりそうなったのではなく、そう決めています。会社の知識ページも、ほかのプロンプト面とおなじルールで扱われます。

承認は、フラグを立てるだけでは済みません。eval promote は、しきい値に届かない証拠も、意味のほうを見ていないケースも受けつけません。結果には署名がつくので、手を入れた結果はしきい値を見るより先にはじかれます。

$ rig-wb pack validate .rig/packs/my-domain
[ERROR] prompt-bearing pack requires at least one evaluation case

# draft は pack の外（プロジェクト側）に書く：
#   .rig/evals/drafts/<case-id>/case.json
#   prompt_surfaces に ["wiki:backup-policy"] のように面を名指しする
$ rig-wb eval run <case-id> --repo . --phase baseline --provider ... --model ...
$ rig-wb eval run <case-id> --repo . --phase current  --provider ... --model ...
$ rig-wb eval compare --baseline <baseline.json> --current <current.json> --repo .

$ rig-wb eval promote <case-id> --baseline ... --current ... \
      --repo . --into .rig/packs/my-domain
$ rig-wb pack sync .rig/packs/my-domain
$ rig-wb pack validate .rig/packs/my-domain
valid: my-domain@0.1.0

draft を pack の中に置けないのは、pack が宣言していないものを一つも持てないからです。--into が変えるのは行き先だけで、ゲートの厳しさは変わりません。

もう一つ、忘れがちな一手があります。ケースが実際に走るためには、マニフェストが宣言している entrypoint を prompt_entrypoint に書いておく必要があります。知識 pack なら、それはページ自身です。

entrypoints:
  - id: backup-policy
    kind: wiki
    target: backup-policy

これを書き忘れても pack validate は通ってしまいます。でも pack test は structural_only と返します。ケースは同梱されて、ハッシュもされて、それでも誰にも動かされないままです。

N° 14: その pack は何について書かれているのか

type が「何を持てるか」を決めるなら、knowledge: ブロックは「何についてか」を書くところです。質問の側から、答えられそうな pack を探せるようにするためです。

knowledge:
  scope: ["company"]
  topics: ["access-control", "backup", "encryption"]
  owner: "Corp IT"
  evidence: ["情報セキュリティ規程", "運用設計書"]
  reviewed_at: "2026-08-01T00:00:00+00:00"

ブロック自体は書かなくても大丈夫ですが、半分だけというのは通りません。置いたなら五つとも必須で、理由は reviewed_at にあります。見直した日が書いていない知識ほど、誰にも気づかれないまま古くなっていくからです。

evidence だけは、並べ替えを求められません。人が書いた資料の題名を、その言語のまま並べるからです。コードポイント順なんて誰にも予測できませんし（運用設計書 は 情報セキュリティ規程 の後に来ます）、順番そのものが「主にどれに寄りかかっているか」を表します。

探す

rig-wb pack knowledge                        # このスコープの全宣言
rig-wb pack knowledge --topic backup
rig-wb pack knowledge --topic backup --scope product

ここでの rig の態度が、ちょっと変わっています。セキュリティ質問票の「バックアップは取っていますか」には、会社としての答えと、ある製品としての答えと、その下のインフラとしての答えが別々にあります。しかも質問した側は、どれのつもりだったかを決めていないことが多いんです。

$ rig-wb pack knowledge --topic backup
company-security@0.1.0   company            Corp IT        reviewed 2026-08-01
  topics: access-control, backup, encryption
  evidence: 情報セキュリティ規程, 運用設計書
product-security@0.1.0   product:northwind-one Northwind One Team reviewed 2026-07-15
  topics: backup, sla
  evidence: サービス仕様書
scope is ambiguous: company, product:northwind-one — narrow with --scope
  before treating any of these as the answer

rig は選び出しはしますが、決めはしません。どっちのつもりだったかは質問した人のなかにある事実で、どの pack にも書いてありません。だから当てにいかず、「まだ決まっていませんよ」ということと、選べる候補をそのまま返します。

候補は必ず evidence・owner・reviewed_at を連れてきます。答える側が出どころを組み立て直さずに引用できるようにするためです。knowledge: を書いていない pack は候補になりません。黙っていることは、あらゆるスコープへの名乗りにはならないからです。

さらに各候補は、同梱しているページを pack:// の形で連れてきます。影に隠れているページも、ラベルをつけて並べます。隠すと「あのファイルどこ行ったの」と言わせてしまいますし、黙って引用すると、誰も読まないテキストの裏に答えを置くことになるからです。

wiki: pack://user/company-security/facets/knowledge/backup-policy.md
        [shadowed by product-security]

N° 15: 渡す

zip にして手渡すのが、いちばん短い道です。

$ rig-wb pack bundle .rig/packs/my-domain
bundled: my-domain@0.1.0 (3 file(s)) -> dist/my-domain-0.1.0.zip
  sha256: 7ef9b1a3...

$ rig-wb pack install dist/my-domain-0.1.0.zip --scope project

バンドルの中身は毎回おなじバイト列になります（エントリは並べ替えられ、日付は固定されます）。毎回変わる zip は毎回「変わりました」と言うことになって、それでは何も言っていないのと同じですよね。

プライベートリポジトリから配る

配布先が git リポジトリなら、名前つきソースを使います。仕様が指すのはアドレスではなくソースの名前です。

rig-wb pack source add product --scheme git+ssh \
    --url git@github.com:acme/rig-pack-{pack}.git
rig-wb pack install product:northwind@1.4.0 --scope project
rig-wb pack verify-sources --scope project

rig は資格情報をひとつも持ちません。git を呼ぶだけなので、認証はもう設定してあるもの（SSH agent、credential helper、CI secret）が答えてくれます。トークンを埋め込んだ URL は断られます。lock に残るのはソースの名前と commit だけで URL は書かないので、rig が書くファイルには資格情報が乗りようがありません。

入っているものを見る

rig-wb pack list        # id@version・type・kind・origin・検証状態
rig-wb pack info    <id>   # 出所・digest・engine・依存
rig-wb pack explain <id>   # そのアセットは実際にプロンプトへ届いているか
rig-wb pack outdated       # 各ソースに publish 状況を問い合わせる（通信あり）

info と explain は、答える問いが違います。info は身元と来歴。explain はそのアセットが tier の勝負に勝てているか。入っていて valid なのに、まるごと影に隠れている。「override したのに何も起きない」の正体は、たいていこれです。

N° 16: 引っかかりやすいところ

  • valid は「完成」ではありません空の pack も valid になります。doctor の empty_pack 警告を見てください。doctor は警告では exit 0 を返します。failed だけがエラーです。
  • pack.yaml は手で書きません正準形とバイト単位で比較されるので、手書きは「たまたま一致する」か「間違っている」かのどちらかにしかなりません。pack sync に書かせてください。
  • 署名した pack は sync できませんマニフェストを書き換えると署名が無効になります。署名を外し、sync してから、鍵で署名し直してください。
  • install しただけではコマンドになりませんcommand アセットは、明示登録を扱えるホスト向けの資料です。install が自動でスラッシュコマンドを生やすことはありません。
  • project pack は初回に同意が要ります内容を確認し、RIG_ALLOW_PROJECT_PACKS=1 で asset trust を記録してから使います。同意は内容ハッシュに紐づくので、アセットが変われば再同意になります。
  • user / org スコープは品質検証を回避できません--allow-unverified が使えるのは project スコープだけです。その場合も lock に verification_status: unverified が残ります。
  • mock は品質の証拠になりません--provider mock の結果は non_quality_mock と明示的に報告されます。配線の確認にはなりますが、品質の裏づけにはなりません。
  • digest は「誰が」を答えませんハッシュが保証するのは、同じバイト列であることだけです。出所を答えるのは署名と trust root であって、private リポジトリであることは、どちらの代わりにもなりません。

N° 17: まずは、ここから

最初の一日は /rig:go と diff / accept / discard だけで大丈夫です。ゲートに一度落ちて「なんで落ちたんだろう」と読むところまで来れば、rig がどういう道具かは自然と分かります。

自分の領域を教え込みたくなったら、まず /rig:knowledge でページを一枚だけ書いて、persona の inject: から参照させてみてください。効くと分かってから、rig-wb pack init --type knowledge でちゃんとした配布物にします。順番を逆にすると、まだ効くか分からないものに評価ケースを書くことになってしまいます。

リポジトリの中のもとの資料は、この三つです。README.ja.md（全体像）、docs/packs.md（pack の仕様）、skills/engine/SKILL.md（ブリック一覧の本家）。

rig — Reasoning Integration Gateway。本書は rig リポジトリの README.ja.md、docs/packs.md、skills/engine/SKILL.md を典拠として書かれた入門資料です。
