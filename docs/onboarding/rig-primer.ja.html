RIG

$ /rig:go "ログインバグを直して"
detected: bugfix recipe: bugfix mode: isolated worktree
gate: passed_with_warnings
pack://project/company-security/ facets/knowledge/backup-policy.md

AI に仕事を任せるとき、困るのは AI が間違えることではありません。間違えたことに 誰も気づかないまま、本体に混ざってしまうことです。rig はそこだけを構造で塞ぎます。

第一部　rig を知る

N° 01: rig とは何か

rig は Claude Code のための品質オペレーティングシステムです。自然文でタスクを頼むと、種類を判定し、必要な部品を組み合わせてハーネスを作り、いま作業しているツリーとは隔離された git worktree の中で作業します。明示的な受け入れ基準で検証し、あなたが accept と言うまで本体には一切触れません。

ここは最初に誤解を外しておきたいところです。rig は品質を自動的に生む道具ではありません。あなたが決めた品質基準を、AI に無視させないための道具です。基準を作るのは人間の仕事のままで、rig の仕事は強制と測定です。

そのかわり対価があります。隔離と検証と記録のために、rig は速度とトークンをわざと払っています。とにかく速くコードを書かせたいだけなら、モデルに直接頼んだほうが速いです。rig が効いてくるのは、失敗したときのコストが速度より高い場面です。

直接頼む場合と何が違うか

直接頼むrig 経由
失敗した変更作業ツリーに残るworktree ごと破棄、本体は無傷
「できました」信じるしかないacceptance-gate の合否が根拠
レビューの質不明検出率を実測できる
何が起きたかチャットログrun log と監査証跡

N° 02: 入口は二つある

用途が違うだけで、動いている中身は同じエンジンです。多くの場合は一つ目で足ります。

Claude Code の中では、プラグイン

/rig:go をはじめとするスラッシュコマンドは、ここから来ます。

/plugin marketplace add itoh-shun/sito-plugins
/plugin install rig@sito-plugins

それ以外の場所では、rig-wb CLI

同じ決定論エンジンを、Claude Code のセッション外から動かすためのものです。CI やスクリプト、あるいは別のアシスタント（Codex / Cursor / Copilot）から呼びます。

pipx install git+https://github.com/itoh-shun/rig.git
rig-wb version

すでに Claude Code の中にいるなら、/rig:setup が同じことをやってくれます。両方は要りません。プラグインだけで安全フローは一通り動きますし、CLI だけで CI から回せます。

N° 03: 最初の三十秒

まず、設定はゼロ。manifest も gates.json も persona 設定も要りません（すべて後から足せます）。箱から出したままの状態で動きます。

/rig:go "ログインバグを直して"
/rig:go "このPRを厳しめにレビューして"
/rig:go "今の変更が安全か確認して"

実行すると、なぜその段取りになったかを一行で宣言してから走り出します。

▸ rig
task:     ログインバグを直して
detected: bugfix
recipe:   bugfix — 「バグ」「直して」を検出
mode:     isolated worktree
gate:     standard + bugfix

終わったら、確認して、決めます。日常で使うのはこの三つだけです。

/rig:go diff       # 何が変わったか、なぜ安全か
/rig:go accept     # 作業ツリーへ反映（gate 未達なら拒否される）
/rig:go discard    # 破棄（作業ツリーは最初から触られていない）

N° 04: なぜ安全と言えるのか

「安全です」は、それだけでは主張にすぎません。rig が安全だと言えるのは、次の四つが文章ではなく配線として入っているからです。

一、隔離された worktree

タスクごとに専用の git worktree と使い捨てブランチを作ります。rig があなたの作業ツリーに直接書き込むことはありません。失敗しても中断しても、手元は何も汚れません。

<repoの親>/rig-worktrees/<repo名>/rig-20260704-153012-login-fix/
<repo>/.rig/runs/rig-20260704-153012-login-fix/
    task.json        入力 / task_type / recipe / base branch / status
    acceptance.json  基準ごとの合否と根拠
    diff.md          Summary / Risk / Tests / Unrelated diff

隔離がタスクごとに閉じているので、複数タスクの同時実行が構造的に安全です。別の worktree と別のブランチなので、並列プロセス同士がファイルを取り合いません。

二、acceptance-gate

モデルが「完了しました」と言っただけでは、完了になりません。無関係な差分が混じっていないか、テストと型は通るか、リスクは書かれたか、秘密情報が漏れていないか。こうした機械的なチェックを通って、はじめて反映候補になります。failed か pending が一件でも残っていれば、accept は機械的に拒否されます。

三、read-only な検証役

実装する AI と検証する AI を分け、検証側はプロセスレベルで読み取り専用に固定します。お願いではなく強制です。reviewer は claude --allowedTools Read,Grep,Glob や codex --sandbox read-only で起動されます。ファイルを見て、grep して、指摘を書くことはできます。編集も commit も、formatter による書き換えもできません。

さらに検証役は、生成側が書いた自己申告レポートではなく、worktree の実際の git diff を一次証拠として判定します。レポートは「未検証の主張」というラベルつきで渡されるだけです。

四、明示的な accept / discard と、消えない記録

accept は squash merge で staged（未コミット）として反映します。コミットは常に人間が打ちます。discard は worktree とブランチを消しますが、run log は残ります。何を試してなぜ捨てたかは、後から必ず辿れます。

N° 05: ゲートの中身

すべてのタスクは standard（全種別に共通）に、種別ごとのプリセットを重ねた基準リストを持ちます。

preset対象基準の例
standard全種別task_intent_satisfied / no_unrelated_diff / diff_summary_written / risk_summary_written / tests_pass_or_explained / no_secret_leak / no_gate_tampering / no_injection_markers / no_destructive_operation
bugfixbugfix, performancebug_cause_identified / fix_is_minimal / regression_test_added_or_explained / existing_behavior_preserved
featurefeature, testrequirement_summary_written / implementation_matches_requirement / tests_added_or_explained / public_api_changes_documented
refactorrefactorbehavior_boundaries_identified / no_unintended_behavior_change / tests_confirm_behavior_preserved
reviewreviewfindings_are_concrete / severity_labeled / file_references_included / false_positive_risk_considered
securitysecurity_reviewauthn_authz_impact_checked / user_input_flow_checked / secret_exposure_checked / dependency_risk_checked

大事なのは、これらが自己申告ではないことです。いくつかの基準は決定論的な機械センサーが裏づけます。秘密情報スキャン、プロンプトインジェクション・マーカー検出、破壊的コマンド検出、ゲート改竄の検出、OpenAPI のスキーマ差分。検出されれば理由つきで落ちます。

プロジェクト側で基準を足すこともできます（.rig/gates.json）。ただし足す方向だけです。組み込み基準の削除キーや緩和キーは、その場で拒否されます。リポジトリの中のファイルが、そのリポジトリを守るゲートを弱めることはできません。

効果を測っていないゲートは、効いているかどうかも分かりません。

N° 06: ブリック。部品としての設計

rig は起動時に四種類の部品を組み合わせてハーネスを作ります。LEGO のブロックだと思ってください。

  • persona誰が判定するかを決めます。security-reviewer、design-reviewer など。
  • instruction何をするかを決めます。手順そのものです。
  • patternどう分配し、どうゲートするかを決めます。isolated-worktree、acceptance-gate など。
  • recipestep の束です。bugfix、feature、review-only、release-flow など。

/rig:go はこの組み立てを自動でやります。組み立てを自分で指定したくなったら、/rig:dev が同じエンジンへの明示的な入口になります。

/rig:dev --plan --only review "現在の変更"   # ドライラン：構成だけ見る
/rig:dev --recipe hotfix --issue 1234        # 緊急修正を最短経路で
/rig:dev --list                              # 全 tier の recipe を一覧

ここが後半につながります。専用領域への拡張とは、エンジンを変えることではなく、この部品を足すことです。エンジンはドメイン非依存のまま動きません。

N° 07: レビュアーを測る

reviewer persona は単なるプロンプトではありません。rig ではテストできます。/rig:drill は既知のバグ（認可漏れ、インジェクション、N+1、破壊的変更、片道 migration、テスト欠落など）を使い捨ての diff に仕込んでレビューを走らせ、reviewer には見せない答案キーと突き合わせて採点します。

# Drill Result — strict_senior_engineer
Detection rate:    82%
False positive:    12%
Severity accuracy: 76%

## Missed Issues
1. SQL injection risk in search query (src/search.py:88)
2. Missing authorization check (src/api/users.py:120)

/rig:go stats は過去の run を集計し、まったく reject しないレビュアーを名指しで警告します。「6 run で 0 reject。ゴム印の可能性」。レビューが儀式になっていることは、こうやって初めて見えます。

PACK

ここから後半です。専用領域の知識を、口伝でもコピペでもなく、 バージョンとハッシュと出典を持った配布物として渡す方法を扱います。

第二部　pack で知識層を拡張する

N° 09: 知識層とは何か、そしてなぜ二種類あるのか

rig の知識層は、subagent のプロンプトに注入されるドメイン知識です。

「この会社ではバックアップをこう定義している」「この製品のユビキタス言語はこれだ」。 こうした、コードを読んでも出てこない事実を、レビュアーや実装役に 持たせるための層です。

実体は二つあって、性格がはっきり違います。

セッション知識層pack
置き場~/.claude/rig/knowledge/ と <repo>/.claude/rig/knowledge/.rig/packs/・~/.rig/packs/ ほか
作り方/rig:knowledge で生成rig-wb pack で組み立て
配布できない（自分の環境とこのリポジトリ限り）zip / git リポジトリで配れる
版と改竄管理しないversion・sha256・lock で固定
品質本人の目承認済み評価ケースが必須
向く場面思いついたことを今すぐ効かせたいチームや複数リポジトリに同じ知識を効かせたい

手元で育てるなら前者で十分です。他人に渡すときに必要になるのが後者です。誰が書いたのか、いつ見直したのか、根拠は何か、途中で書き換わっていないか。pack はこの四つを構造として持っています。

N° 10: 知識はどう注入されるのか

知識層の中心は wiki です。一つの概念につき一枚の正準ページを書き、[[slug]] で相互リンクします。persona は事実を本文に埋め込まず、ページを参照します。

# persona: house-authenticity
inject: ["[[genre-house]]", "[[music-era-90s]]"]

なぜ埋め込まないのか。埋め込むと知識が暗黙知になるからです。参照にしておけば、ページを一枚直すだけで、それを参照する全 persona の判断が同時に更新されます。

inject: の各 [[slug]] は tier で解決されます。同じ slug が複数の層にあれば、上の層が勝ちます。

  • 1. project overlay<repo>/.claude/rig/knowledge/wiki/
  • 2. global~/.claude/rig/knowledge/wiki/
  • 3. orgチームで共有する層
  • 4. pack 同梱<pack>/facets/knowledge/<slug>.md
  • 5. shippedrig が最初から持つページ

pack 内の persona が inject: を持つ場合は、まず自分の pack の中を見ます。pack は自分の persona のために必要なページを同梱して持ち歩く、という設計です。同じ slug をプロジェクト側に置けば、これまでどおり上書きできます。

N° 11: pack の型。何を持てて、何を実行できるか

type は必須で、既定値を持ちません。既定値を置くと、その決定を「決めなかった人」に渡してしまうからです。type が決めるのは権限です。

type持てるものホストのコマンドを走らせるか
knowledgewiki・resource・評価ケースと結果いいえ
policy上記 ＋ policyいいえ
reviewer上記 ＋ persona・output-contractいいえ
skillすべてのプロンプト種別（instruction・recipe・pattern・command・agent）いいえ
workflowskill と同じいいえ
toolすべてはい

この表の一番右の列が、pack の型モデルがある理由そのものです。recipe の中に checks:（ホスト上で実行されるシェルコマンド）を書けるのは tool だけです。チームのドメイン知識を足すことが、そのままコマンド実行権限を渡すことになってはいけません。他の型が運ぶのは、プロバイダが読むテキストだけです。

type と紛らわしいのが kind（core / official / domain / project）ですが、こちらは tier 順のどこで解決されるかを決めるだけで、権限ではありません。

知識層を配るのが目的なら、まず knowledge を選びます。persona も一緒に配りたくなったら reviewer、recipe やコマンドまで含むなら skill です。必要以上に強い型を選ばないことが、そのまま受け取る側への安全保証になります。

N° 12: pack を作る。最短の一周

まず骨組みを作ります。pack init は上書きを拒否し、標準ディレクトリをすべて掘ってから、次にやることを教えてくれます。

$ rig-wb pack init my-domain --type knowledge --kind domain --root .rig/packs
initialized: .rig/packs/my-domain

next:
  1. write an asset          my-domain/facets/knowledge/<name>.md
  2. rig-wb pack sync .rig/packs/my-domain
  3. rig-wb pack validate .rig/packs/my-domain

ページを書いたら、pack.yaml は手で編集しません。マニフェストは全アセットをパスと sha256 で宣言し、検証のときに正準形とバイト単位で比較されます。つまり生成物であって、手書きするものではありません。

$ vi .rig/packs/my-domain/facets/knowledge/backup-policy.md
$ rig-wb pack sync .rig/packs/my-domain
  + facets/knowledge/backup-policy.md
pack sync: 1 asset(s) declared and hashed

sync はディレクトリを鏡写しにします。消したファイルは宣言からも消えます。書き換わるのは assets と hashes だけで、version・description・entrypoints はあなたのものです。

そして validate です。ただし、ここに落とし穴があります。空の pack もスキーマは満たすので valid と出ます。嘘ではないのですが、完成と読み違えやすいところです。その状態は doctor が名指ししてくれます。

$ rig-wb pack doctor .rig/packs/my-domain
pack doctor: warning
- empty_pack: .rig/packs/my-domain

純粋な resource ファイルだけの知識 pack なら、一周はここで閉じます。PDF や CSV のような読むだけの資料はプロンプト素材ではないので、評価ゲートの対象になりません。

N° 13: wiki を入れた瞬間、評価ゲートが立つ

wiki はプロンプト素材です。プロバイダに見せるテキストだからです。そのため wiki を持つ pack には、承認済みの評価ケースが最低一件必要になります。これは事故ではなく、意図された挙動です。会社の知識ページも、他のプロンプト面と同じ規律で扱われます。

承認は、フラグを立てることではありません。eval promote は、閾値を満たさない証拠を拒否し、意味的なルーブリックが判定されていないケースも拒否します。結果には署名がつくので、編集された結果は閾値を見る前に署名で落ちます。

$ rig-wb pack validate .rig/packs/my-domain
[ERROR] prompt-bearing pack requires at least one evaluation case

# draft は pack の外（プロジェクト側）に書く：
#   .rig/evals/drafts/<case-id>/case.json
#   prompt_surfaces に ["wiki:backup-policy"] のように面を名指しする
$ rig-wb eval run <case-id> --repo . --phase baseline --provider ... --model ...
$ rig-wb eval run <case-id> --repo . --phase current  --provider ... --model ...
$ rig-wb eval compare --baseline <baseline.json> --current <current.json> --repo .

$ rig-wb eval promote <case-id> --baseline ... --current ... \
      --repo . --into .rig/packs/my-domain
$ rig-wb pack sync .rig/packs/my-domain
$ rig-wb pack validate .rig/packs/my-domain
valid: my-domain@0.1.0

draft を pack の中に置けないのは、pack が宣言していないものを一切持てないからです。--into が変えるのは承認済みケースの行き先だけで、ゲートの厳しさは何も変わりません。

もう一つ、忘れやすい一手があります。ケースが実際に走るためには、マニフェストが宣言する entrypoint を prompt_entrypoint が名指ししている必要があります。知識 pack では、entrypoint はページそのものです。

entrypoints:
  - id: backup-policy
    kind: wiki
    target: backup-policy

これを書き忘れても pack validate は通ります。ただし pack test は structural_only と報告します。ケースは pack に同梱され、ハッシュされ、それでも誰にも実行されません。

N° 14: その pack は何について書かれているのか

type が「何を持てるか」を決めるなら、knowledge: ブロックは「何についてか」を宣言します。質問の側から、答えられる pack を探せるようにするためです。

knowledge:
  scope: ["company"]
  topics: ["access-control", "backup", "encryption"]
  owner: "Corp IT"
  evidence: ["情報セキュリティ規程", "運用設計書"]
  reviewed_at: "2026-08-01T00:00:00+00:00"

ブロック自体は任意ですが、半分だけ書かれたブロックは許されません。置いたなら五つとも必須で、その理由は reviewed_at にあります。見直し日のない知識宣言こそ、誰にも気づかれずに古びていくものだからです。

evidence だけはソートを求められません。人が書いた文書の題名を、書いた言語のまま並べるからです。コードポイント順は誰にも予測できませんし（運用設計書 は 情報セキュリティ規程 の後に来ます）、引用リストの順序そのものが「主にどれに依拠しているか」という意味を運びます。

探す

rig-wb pack knowledge                        # このスコープの全宣言
rig-wb pack knowledge --topic backup
rig-wb pack knowledge --topic backup --scope product

ここで rig が取る態度が特徴的です。セキュリティ質問票の「バックアップは取っていますか」には、会社としての正解と、ある製品としての正解と、その下のインフラとしての正解が別々にあります。そして質問した側は、どれのつもりだったかを決めていないことが多いのです。

$ rig-wb pack knowledge --topic backup
company-security@0.1.0   company            Corp IT        reviewed 2026-08-01
  topics: access-control, backup, encryption
  evidence: 情報セキュリティ規程, 運用設計書
product-security@0.1.0   product:northwind-one Northwind One Team reviewed 2026-07-15
  topics: backup, sla
  evidence: サービス仕様書
scope is ambiguous: company, product:northwind-one — narrow with --scope
  before treating any of these as the answer

これは選び出しますが、決めはしません。どちらのつもりだったかは質問した人についての事実であって、どの pack にも書かれていません。だから rig は推測せず、「問いが開いている」という事実と、選択肢の正確な集合を返します。

候補は必ず evidence・owner・reviewed_at を連れてきます。答える側が出典を再構成せずに引用できるようにするためです。knowledge: を宣言していない pack は候補になりません。黙っていることは、あらゆるスコープへの名乗りではないからです。

さらに各候補は、同梱するページを pack:// 形式で連れてきます。影に隠れているページは、隠されるのでも黙って引用されるのでもなく、ラベルつきで列挙されます。

wiki: pack://user/company-security/facets/knowledge/backup-policy.md
        [shadowed by product-security]

N° 15: 渡す

zip にして手渡すのが、一番短い経路です。

$ rig-wb pack bundle .rig/packs/my-domain
bundled: my-domain@0.1.0 (3 file(s)) -> dist/my-domain-0.1.0.zip
  sha256: 7ef9b1a3...

$ rig-wb pack install dist/my-domain-0.1.0.zip --scope project

バンドルのバイト列は再現可能です（エントリはソートされ、日付は固定されます）。毎回変わる zip は毎回「変わりました」と報告することになり、それは何も報告していないのと同じだからです。

プライベートリポジトリから配る

配布先が git リポジトリなら、名前つきソースを使います。仕様が指すのはアドレスではなくソースの名前です。

rig-wb pack source add product --scheme git+ssh \
    --url git@github.com:acme/rig-pack-{pack}.git
rig-wb pack install product:northwind@1.4.0 --scope project
rig-wb pack verify-sources --scope project

rig は資格情報を一切持ちません。git を呼ぶだけで、認証はすでに設定済みのもの（SSH agent、credential helper、CI secret）が答えます。トークンを埋め込んだ URL は拒否されます。lock が記録するのはソースの名前と commit で URL ではないので、rig が書くファイルは資格情報を運びようがありません。

入っているものを見る

rig-wb pack list        # id@version・type・kind・origin・検証状態
rig-wb pack info    <id>   # 出所・digest・engine・依存
rig-wb pack explain <id>   # そのアセットは実際にプロンプトへ届いているか
rig-wb pack outdated       # 各ソースに publish 状況を問い合わせる（通信あり）

info と explain は別の問いに答えるので、互いの代用になりません。info は身元と来歴です。explain はそのアセットが tier 争いに勝っているかです。pack がインストール済みで valid なのに、完全に影に隠れている。「override したのに何も起きない」の正体は、たいていこれです。

N° 16: 引っかかりやすいところ

  • valid は「完成」ではありません空の pack も valid になります。doctor の empty_pack 警告を見てください。doctor は警告では exit 0 を返します。failed だけがエラーです。
  • pack.yaml は手で書きません正準形とバイト単位で比較されるので、手書きは「たまたま一致する」か「間違っている」かのどちらかにしかなりません。pack sync に書かせてください。
  • 署名した pack は sync できませんマニフェストを書き換えると署名が無効になります。署名を外し、sync してから、鍵で署名し直してください。
  • install しただけではコマンドになりませんcommand アセットは、明示登録を扱えるホスト向けの資料です。install が自動でスラッシュコマンドを生やすことはありません。
  • project pack は初回に同意が要ります内容を確認し、RIG_ALLOW_PROJECT_PACKS=1 で asset trust を記録してから使います。同意は内容ハッシュに紐づくので、アセットが変われば再同意になります。
  • user / org スコープは品質検証を回避できません--allow-unverified が使えるのは project スコープだけです。その場合も lock に verification_status: unverified が残ります。
  • mock は品質の証拠になりません--provider mock の結果は non_quality_mock と明示的に報告されます。配線の確認にはなりますが、品質の裏づけにはなりません。
  • digest は「誰が」を答えませんハッシュが保証するのは、同じバイト列であることだけです。出所を答えるのは署名と trust root であって、private リポジトリであることは、どちらの代わりにもなりません。

N° 17: ここから先

最初の一日は /rig:go と diff / accept / discard だけで大丈夫です。ゲートに一度落ちて、なぜ落ちたかを読むところまで来れば、rig が何をする道具かは体で分かります。

自分のドメインを教え込みたくなったら、まず /rig:knowledge でページを一枚書き、persona の inject: から参照させてみてください。それが効くと確信できてから、rig-wb pack init --type knowledge で配布物に格上げします。順番を逆にすると、まだ効くか分からないものに評価ケースを書くことになります。
