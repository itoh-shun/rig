rig — 教本

RIG

$ /rig:go "ログインバグを直して"
detected: bugfix recipe: bugfix mode: isolated worktree
gate: passed_with_warnings
pack://project/company-security/ facets/knowledge/backup-policy.md

AI に仕事を任せるとき、危ないのは AI が間違えることではなく、間違えたことに 誰も気づかないまま本体に混ざることだ。rig はそこだけを構造で潰す。

第一部 — rig を知る

N° 01: rig とは何か

rig は Claude Code のための品質オペレーティングシステムだ。自然文でタスクを頼むと、 種類を判定し、必要な部品を組み合わせてハーネスを合成し、いま作業している ツリーとは隔離された git worktree の中で作業し、明示的な受け入れ基準で 検証し、あなたが accept と言うまで本体には一切触れない。

ここを最初に誤解しないでほしい。rig は品質を自動的に生む道具ではない。 あなたが定義した品質基準を、AI に無視させないための道具だ。 基準を作るのは人間の仕事のまま。rig の仕事は強制と測定。

そして対価がある。隔離・検証・記録のために、rig は速度とトークンを意図的に払う。 とにかく速くコードを書かせたいだけなら、モデルに直接頼んだほうが速い。 rig が効いてくるのは、失敗したときのコストが速度より高い場面だ。

直接頼む場合と何が違うか

直接頼むrig 経由
失敗した変更作業ツリーに残るworktree ごと破棄、本体は無傷
「できました」信じるしかないacceptance-gate の合否が根拠
レビューの質不明検出率を実測できる
何が起きたかチャットログrun log と監査証跡

N° 02: 入口は二つある

用途が違うだけで、動いている中身は同じエンジンだ。多くの場合は一つ目で足りる。

Claude Code の中では、プラグイン

/rig:go をはじめとするスラッシュコマンドはここから来る。

/plugin marketplace add itoh-shun/sito-plugins
/plugin install rig@sito-plugins

それ以外の場所では、rig-wb CLI

同じ決定論エンジンを Claude Code のセッション外から動かすためのもの。CI、スクリプト、 あるいは別のアシスタント（Codex / Cursor / Copilot）から呼ぶ。 

pipx install git+https://github.com/itoh-shun/rig.git
rig-wb version

すでに Claude Code の中にいるなら /rig:setup が同じことをやってくれる。 両方は要らない。プラグインだけで安全フローは一通り動くし、CLI だけで CI から回せる。

N° 03: 最初の三十秒

設定はゼロでいい。manifest も gates.json も persona 設定も要らない（すべて後から足す opt-in だ）。箱から出してすぐ動く。 

/rig:go "ログインバグを直して"
/rig:go "このPRを厳しめにレビューして"
/rig:go "今の変更が安全か確認して"

実行すると、なぜその段取りになったかを一行で宣言してから走り出す。

▸ rig
task:     ログインバグを直して
detected: bugfix
recipe:   bugfix — 「バグ」「直して」を検出
mode:     isolated worktree
gate:     standard + bugfix

終わったら、確認して、決める。この三つが日常操作のすべてだ。

/rig:go diff       # 何が変わったか、なぜ安全か
/rig:go accept     # 作業ツリーへ反映（gate 未達なら拒否される）
/rig:go discard    # 破棄（作業ツリーは最初から触られていない）

N° 04: なぜ安全と言えるのか

「安全です」は主張にすぎない。rig が安全なのは、次の四つが文章ではなく配線として 入っているからだ。

一、隔離された worktree

タスクごとに専用の git worktree と使い捨てブランチを作る。rig はあなたの作業ツリーに 直接書き込まない。失敗しても中断しても、手元は何も汚れない。 

<repoの親>/rig-worktrees/<repo名>/rig-20260704-153012-login-fix/
<repo>/.rig/runs/rig-20260704-153012-login-fix/
    task.json        入力 / task_type / recipe / base branch / status
    acceptance.json  基準ごとの合否と根拠
    diff.md          Summary / Risk / Tests / Unrelated diff

隔離がタスク単位で閉じているので、複数タスクの同時実行が構造的に安全だ。 別 worktree・別ブランチなので、並列プロセス同士がファイルを取り合わない。

二、acceptance-gate

モデルが「完了しました」と言っただけでは完了にならない。無関係な差分が混じっていないか、 テストと型は通るか、リスクは書かれたか、秘密情報が漏れていないか——機械的なチェックを 通って初めて反映候補になる。failed か pending が一件でも 残っていれば accept は機械的に拒否される。

三、read-only な検証役

実装する AI と検証する AI を分離し、検証側はプロセスレベルで読み取り専用に固定される。 お願いではなく強制として、だ。reviewer は claude --allowedTools Read,Grep,Glob や codex --sandbox read-only で起動される。ファイルを見て、grep して、 指摘は書ける。編集・commit・formatter による書き換えはできない。

さらに検証役は、生成側が書いた自己申告レポートではなく worktree の実際の git diff を一次証拠として判定する。 レポートは「未検証の主張」というラベルつきで渡されるだけだ。

四、明示的な accept / discard と、消えない記録

accept は squash merge で staged（未コミット）として 反映する。コミットは常に人間が打つ。discard は worktree とブランチを 消すが、run log は残る——何を試みてなぜ捨てたかは後から必ず辿れる。

N° 05: ゲートの中身

すべてのタスクは standard（全種別共通）に、種別ごとのプリセットを 重ねた基準リストを持つ。

preset対象基準の例
standard全種別task_intent_satisfied / no_unrelated_diff / diff_summary_written / risk_summary_written / tests_pass_or_explained / no_secret_leak / no_gate_tampering / no_injection_markers / no_destructive_operation
bugfixbugfix, performancebug_cause_identified / fix_is_minimal / regression_test_added_or_explained / existing_behavior_preserved
featurefeature, testrequirement_summary_written / implementation_matches_requirement / tests_added_or_explained / public_api_changes_documented
refactorrefactorbehavior_boundaries_identified / no_unintended_behavior_change / tests_confirm_behavior_preserved
reviewreviewfindings_are_concrete / severity_labeled / file_references_included / false_positive_risk_considered
securitysecurity_reviewauthn_authz_impact_checked / user_input_flow_checked / secret_exposure_checked / dependency_risk_checked

重要なのは、これらが自己申告ではないことだ。いくつかの基準は決定論的な機械センサーが 裏づける。秘密情報スキャン、プロンプトインジェクション・マーカー検出、破壊的コマンド 検出、ゲート改竄の検出、OpenAPI のスキーマ差分。検出されれば理由つきで落ちる。

プロジェクト側で基準を足すこともできる（.rig/gates.json）。ただし 加算のみだ。組み込み基準の削除や緩和キーは即座に拒否される。 リポジトリの中のファイルが、そのリポジトリを守るゲートを弱めることはできない。

測れないゲートは、願望にすぎない。

N° 06: ブリック — 部品としての設計

rig は起動時に四種類の部品を合成してハーネスを作る。LEGO のブロックだと思えばいい。

  • persona誰が判定するか。security-reviewer、design-reviewer など。
  • instruction何をするか。手順そのもの。
  • patternどう分配し、どうゲートするか。isolated-worktree、acceptance-gate。
  • recipestep の束。bugfix、feature、review-only、release-flow など。

/rig:go はこの組み立てを自動でやる。組み立てを自分で指定したくなったら /rig:dev が同じエンジンへの明示的な入口になる。 

/rig:dev --plan --only review "現在の変更"   # ドライラン：構成だけ見る
/rig:dev --recipe hotfix --issue 1234        # 緊急修正を最短経路で
/rig:dev --list                              # 全 tier の recipe を一覧

ここが後半につながる。専用領域への拡張とは、エンジンを変えることではなく、 この部品を足すことだ。エンジンはドメイン非依存のまま動かない。

N° 07: レビュアーを測る

reviewer persona は単なるプロンプトではない。rig ではテストできる。 /rig:drill は既知のバグ（認可漏れ、インジェクション、N+1、破壊的変更、 片道 migration、テスト欠落…）を使い捨ての diff に注入し、レビューを走らせ、 reviewer には見せない答案キーと突き合わせて採点する。 

# Drill Result — strict_senior_engineer
Detection rate:    82%
False positive:    12%
Severity accuracy: 76%

## Missed Issues
1. SQL injection risk in search query (src/search.py:88)
2. Missing authorization check (src/api/users.py:120)

/rig:go stats は過去の run を集計し、まったく reject しない レビュアーを名指しで警告する。「6 run で 0 reject。ゴム印の可能性」—— レビューが儀式になっていることは、こうやって初めて見える。

N° 08: コマンドの地図

覚える順番はこの通りでいい。上から下へ、必要になってから降りていく。

  • Core/rig:go・/rig:talk（会話的な入口）・/rig:dev・status / diff / accept / discard / log
  • 観測/rig:go board（管制塔）・cockpit・stats
  • Quality/rig:drill・/rig:pr・/rig:qa・/rig:harness
  • Knowledge/rig:knowledge・/rig:persona・/rig:catalog・/rig:import / /rig:export・/rig:forge
  • Planning/rig:brainstorm・/rig:tasks・/rig:goal・/rig:design・/rig:loop
  • その他/rig:queue（積んで一括実行）・/rig:init（リポジトリ側の初期設定）

PACK

ここから後半。専用領域の知識を、口伝でもコピペでもなく、 バージョンとハッシュと出典を持った配布物として渡す方法の話だ。

第二部 — pack で知識層を拡張する

N° 09: 知識層とは何か、そしてなぜ二種類あるのか

rig の知識層は、subagent のプロンプトに注入されるドメイン記述知識だ。 「この会社ではバックアップをこう定義している」「この製品のユビキタス言語はこれだ」 ——コードを読んでも出てこない事実を、レビュアーや実装役に持たせるための層である。

実体は二つあり、性格がはっきり違う。

セッション知識層pack
置き場~/.claude/rig/knowledge/ と <repo>/.claude/rig/knowledge/.rig/packs/・~/.rig/packs/ ほか
作り方/rig:knowledge で生成rig-wb pack で組み立て
配布できない（自分の環境とこのリポジトリ限り）zip / git リポジトリで配れる
版と改竄管理しないversion・sha256・lock で固定
品質本人の目承認済み評価ケースが必須
向く場面思いついたことを今すぐ効かせたいチームや複数リポジトリに同じ知識を効かせたい

手元で育てるなら前者で十分だ。他人に渡した瞬間に必要になるのが後者—— 誰が書いたのか、いつ見直したのか、根拠は何か、途中で書き換わっていないか。 pack はその四つを構造として持つ。

N° 10: 知識はどう注入されるのか

知識層の中心は wiki だ。一つの概念につき一枚の正準ページを書き、 [[slug]] で相互リンクする。persona は事実を本文に埋め込まず、 ページを参照する。 

# persona: house-authenticity
inject: ["[[genre-house]]", "[[music-era-90s]]"]

なぜ埋め込まないのか。埋め込むと知識が暗黙知になるからだ。参照にしておけば、 ページを一枚直すだけで、それを参照する全 persona の判断が同時に更新される。

inject: の各 [[slug]] は tier 解決される。 同じ slug が複数の層にあれば、上の層が勝つ。

  • 1. project overlay<repo>/.claude/rig/knowledge/wiki/
  • 2. global~/.claude/rig/knowledge/wiki/
  • 3. orgチームで共有する層
  • 4. pack 同梱<pack>/facets/knowledge/<slug>.md
  • 5. shippedrig が最初から持つページ

pack 内の persona が inject: を持つ場合、まず自分の pack の中を見る。 pack は自分の persona のために必要なページを同梱して持ち歩く、という設計だ。 そして同じ slug をプロジェクト側に置けば、従来どおり上書きできる。

N° 11: pack の型 — 何を持て、何を実行できるか

type は必須で、既定値を持たない。既定値を置くと、その決定を 「決めなかった人」に渡してしまうからだ。type が決めるのは権限である。

type持てるものホストのコマンドを走らせるか
knowledgewiki・resource・評価ケースと結果いいえ
policy上記 ＋ policyいいえ
reviewer上記 ＋ persona・output-contractいいえ
skillすべてのプロンプト種別（instruction・recipe・pattern・command・agent）いいえ
workflowskill と同じいいえ
toolすべてはい

この表の一番右の列が、pack の型モデルが存在する理由そのものだ。recipe の中に checks:（ホスト上で実行されるシェルコマンド）を書けるのは tool だけである。チームのドメイン知識を追加することが、 同時にコマンド実行権限を渡すことになってはいけない。他の型が運ぶのは、 プロバイダが読むテキストだけだ。

type と紛らわしいのが kind（core / official / domain / project）だが、こちらは tier 順のどこで解決されるかを決めるだけで、権限ではない。

知識層を配るのが目的なら、まず knowledge を選ぶ。persona も一緒に 配りたくなったら reviewer。recipe やコマンドまで含むなら skill。必要以上に強い型を選ばないことが、そのまま受け取る側への 安全保証になる。

N° 12: 作る — 最短の一周

まず骨組みを作る。pack init は上書きを拒否し、標準ディレクトリを すべて掘ってから、次にやることを教えてくれる。 

$ rig-wb pack init my-domain --type knowledge --kind domain --root .rig/packs
initialized: .rig/packs/my-domain

next:
  1. write an asset          my-domain/facets/knowledge/<name>.md
  2. rig-wb pack sync .rig/packs/my-domain
  3. rig-wb pack validate .rig/packs/my-domain

ページを書いたら、pack.yaml は手で編集しない。 マニフェストは全アセットをパスと sha256 で宣言し、検証時に正準形とバイト比較される ——だから生成物であって、手書きの対象ではない。 

$ vi .rig/packs/my-domain/facets/knowledge/backup-policy.md
$ rig-wb pack sync .rig/packs/my-domain
  + facets/knowledge/backup-policy.md
pack sync: 1 asset(s) declared and hashed

sync はディレクトリを鏡写しにする。消したファイルは宣言からも消える。 書き換えるのは assets と hashes だけで、version・ description・entrypoints はあなたのものだ。

そして validate。ただしここに落とし穴がある。空の pack もスキーマは 満たすので valid と出る。それは真実だが、完成と読み違えやすい。 doctor がその状態を名指しする。 

$ rig-wb pack doctor .rig/packs/my-domain
pack doctor: warning
- empty_pack: .rig/packs/my-domain

ここまでで一周が閉じるのは、純粋な resource ファイルだけの知識 pack の場合だ。PDF や CSV のような読むだけの資料は、プロンプト素材ではないので 評価ゲートの対象にならない。

N° 13: wiki を入れた瞬間、評価ゲートが立つ

wiki はプロンプト素材だ——プロバイダに見せるテキストである。 だから wiki を持つ pack には、承認済みの評価ケースが最低一件必要になる。 これは事故ではなく意図された挙動だ。会社の知識ページも、他のプロンプト面と 同じ規律で統治される。

承認はフラグで立てるものではない。eval promote は、閾値を満たさない 証拠を拒否し、意味的なルーブリックが判定されていないケースも拒否する。 結果には署名がつくので、編集された結果は閾値を見る前に署名で落ちる。 

$ rig-wb pack validate .rig/packs/my-domain
[ERROR] prompt-bearing pack requires at least one evaluation case

# draft は pack の外（プロジェクト側）に書く：
#   .rig/evals/drafts/<case-id>/case.json
#   prompt_surfaces に ["wiki:backup-policy"] のように面を名指しする
$ rig-wb eval run <case-id> --repo . --phase baseline --provider ... --model ...
$ rig-wb eval run <case-id> --repo . --phase current  --provider ... --model ...
$ rig-wb eval compare --baseline <baseline.json> --current <current.json> --repo .

$ rig-wb eval promote <case-id> --baseline ... --current ... \
      --repo . --into .rig/packs/my-domain
$ rig-wb pack sync .rig/packs/my-domain
$ rig-wb pack validate .rig/packs/my-domain
valid: my-domain@0.1.0

draft を pack の中に置けないのは、pack が宣言していないものを一切持てないからだ。 --into が変えるのは承認済みケースの行き先だけで、 ゲートの厳しさは何も変わらない。

もう一つ、忘れやすい一手がある。ケースが実際に走るためには、 マニフェストが宣言する entrypoint を prompt_entrypoint が 名指ししていなければならない。知識 pack では、entrypoint はページそのものだ。 

entrypoints:
  - id: backup-policy
    kind: wiki
    target: backup-policy

これを書き忘れても pack validate は通る。だが pack test は structural_only と報告する—— ケースは pack に同梱され、ハッシュされ、そして誰にも実行されない。

N° 14: その pack は何について書かれているのか

type が「何を持てるか」なら、knowledge: ブロックは 「何についてか」を宣言する。質問の側から、答えうる pack を探せるようにするためだ。 

knowledge:
  scope: ["company"]
  topics: ["access-control", "backup", "encryption"]
  owner: "Corp IT"
  evidence: ["情報セキュリティ規程", "運用設計書"]
  reviewed_at: "2026-08-01T00:00:00+00:00"

ブロック自体は任意だが、半分だけ書かれたブロックは許されない。 置いた以上は五つとも必須で、その理由は reviewed_at にある。 見直し日のない知識宣言こそ、誰にも気づかれずに腐っていくものだからだ。

evidence だけはソートを要求されない。これは人が書いた文書の題名で、 しかも書いた言語のままだ。コードポイント順は誰にも予測できないし （運用設計書 は 情報セキュリティ規程 の後に来る）、 引用リストの順序自体が「主にどれに依拠しているか」という意味を運ぶ。

探す

rig-wb pack knowledge                        # このスコープの全宣言
rig-wb pack knowledge --topic backup
rig-wb pack knowledge --topic backup --scope product

ここで rig が取る態度が特徴的だ。セキュリティ質問票の「バックアップは取っていますか」 には、会社としての正解と、ある製品としての正解と、その下のインフラとしての正解が 別々にある。そして質問した側は、どれのつもりだったかを決めていないことが多い。 

$ rig-wb pack knowledge --topic backup
company-security@0.1.0   company            Corp IT        reviewed 2026-08-01
  topics: access-control, backup, encryption
  evidence: 情報セキュリティ規程, 運用設計書
product-security@0.1.0   product:northwind-one Northwind One Team reviewed 2026-07-15
  topics: backup, sla
  evidence: サービス仕様書
scope is ambiguous: company, product:northwind-one — narrow with --scope
  before treating any of these as the answer

これは選び出すが、決めはしない。どちらのつもりだったかは 質問者についての事実であって、どの pack にも書かれていない。だから rig は推測せず、 「問いが開いている」という事実と、選択肢の正確な集合を返す。

候補は必ず evidence・owner・reviewed_at を 連れてくる。答える側が出典を再構成せずに引用できるようにするためだ。 knowledge: を宣言していない pack は候補にならない—— 沈黙は、あらゆるスコープへの名乗りではない。

さらに各候補は、同梱するページを pack:// 形式で連れてくる。 影に隠れているページは、隠されるのでも黙って引用されるのでもなく、 ラベルつきで列挙される。 

wiki: pack://user/company-security/facets/knowledge/backup-policy.md
        [shadowed by product-security]

N° 15: 渡す

zip にして手渡すのが一番短い経路だ。

$ rig-wb pack bundle .rig/packs/my-domain
bundled: my-domain@0.1.0 (3 file(s)) -> dist/my-domain-0.1.0.zip
  sha256: 7ef9b1a3...

$ rig-wb pack install dist/my-domain-0.1.0.zip --scope project

バンドルのバイト列は再現可能だ（エントリはソートされ、日付は固定される）。 毎回変わる zip は、毎回「変わりました」と報告することになり、 つまり何も報告しないのと同じになるからだ。

プライベートリポジトリから配る

配布先が git リポジトリなら、名前つきソースを使う。仕様が指すのはアドレスではなく ソースの名前だ。 

rig-wb pack source add product --scheme git+ssh \
    --url git@github.com:acme/rig-pack-{pack}.git
rig-wb pack install product:northwind@1.4.0 --scope project
rig-wb pack verify-sources --scope project

rig は資格情報を一切持たない。git を呼ぶだけで、認証は すでに設定済みのもの（SSH agent、credential helper、CI secret）が答える。 トークンを埋め込んだ URL は拒否される。lock が記録するのはソースの名前と commit であって URL ではないので、rig が書くファイルは資格情報を運びようがない。

入っているものを見る

rig-wb pack list        # id@version・type・kind・origin・検証状態
rig-wb pack info    <id>   # 出所・digest・engine・依存
rig-wb pack explain <id>   # そのアセットは実際にプロンプトへ届いているか
rig-wb pack outdated       # 各ソースに publish 状況を問い合わせる（通信あり）

info と explain は別の問いに答えるので、互いの代用に ならない。info は身元と来歴。explain は そのアセットが tier 争いに勝っているか。pack が インストール済みで、valid で、しかし完全に影に隠れている—— 「override したのに何も起きない」の正体はたいていこれだ。

N° 16: 引っかかりやすいところ

  • valid は「完成」ではない空の pack も valid になる。doctor の empty_pack 警告を見ること。doctor は警告では exit 0 を返す——failed だけがエラーだ。
  • pack.yaml を手で書かない正準形とバイト比較されるので、手書きは「たまたま一致する」か「間違っている」かのどちらかにしかならない。pack sync に書かせる。
  • 署名した pack は sync できないマニフェストを書き換えると署名が無効になる。署名を外し、sync し、鍵で署名し直す。
  • install しただけではコマンドにならないcommand アセットは、明示登録を扱えるホスト向けの資料だ。install が自動でスラッシュコマンドを生やすことはない。
  • project pack は初回に同意が要る内容を確認し、RIG_ALLOW_PROJECT_PACKS=1 で asset trust を記録してから使う。同意は内容ハッシュに紐づくので、アセットが変われば再同意になる。
  • user / org スコープは品質検証を回避できない--allow-unverified が使えるのは project スコープだけで、その場合も lock に verification_status: unverified が残る。
  • mock は品質の証拠ではない--provider mock の結果は non_quality_mock と明示的に報告される。配線の確認にはなるが、品質の裏づけにはならない。
  • digest は「誰が」を答えないハッシュが保証するのは同じバイト列であることだけだ。出所を答えるのは署名と trust root であって、private リポジトリであることはどちらの代わりにもならない。

N° 17: ここから先

最初の一日は /rig:go と diff / accept / discard だけでいい。ゲートに一度落ちて、なぜ落ちたかを読むところまで 来れば、rig が何を売っているかは体で分かる。

自分のドメインを教え込みたくなったら、まず /rig:knowledge で ページを一枚書き、persona の inject: から参照させてみる。 それが効くと確信できてから、rig-wb pack init --type knowledge で 配布物に格上げする。順番を逆にすると、まだ効くか分からないものに 評価ケースを書く羽目になる。

リポジトリ内の一次資料はこの三つだ。 README.ja.md（全体像）、 docs/packs.md（pack の仕様）、 skills/engine/SKILL.md（ブリック目録の正本）。
