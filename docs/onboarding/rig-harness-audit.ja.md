# 「AI開発のハーネス、みんなどう作ってるの？」に正直に答えると

CLAUDE.md を書いて、Skills を足して、hook を入れて、MCP をつないで。だんだん増えてくると、ふと不安になりますよね。

「これ、合ってるのかな」「よそはどうやってるんだろう」

同じことを聞かれるので答えを書こうとしたんですが、正直に言うと**知りません**。そして、知らないまま書くのがいちばんまずいと思っています。

## なぜ「よそ」を書けないか

[rig](https://github.com/itoh-shun/rig) というオーケストレータを作っていて、他ツールとの比較表を置いています。ただし、自分のところ以外はほぼ全部 `unknown` のままです。方針としてそう決めています。

> Nobody on this project has run the other tools under the axes below, and a landscape filled in from marketing pages would be a set of guesses wearing a table's authority.

公式サイトを読んで埋めた比較表は、**表の見た目をした推測**です。「みんなこうしてるらしい」も同じで、伝聞を並べた瞬間に、読んだ人はそれを事実として持ち帰ります。

なので、他所の話はしません。代わりに、**自分のハーネスに穴が空いていないか自分で見る方法**を置いていきます。そっちのほうが役に立つはずです。

## まず、ハーネスは2層あります

用語がぶれやすいので先に。

- **エージェントハーネス** — Claude Code や Codex に内蔵されているループ、ツール、メモリ、コンテキスト管理。こちらは作れません。
- **ユーザーハーネス** — CLAUDE.md、Skills、Hooks、MCP、テスト、lint、CI。**私たちが組むのはこっち**です。

包含関係としては、プロンプトの外にコンテキストがあって、その外にハーネスがあります。プロンプトだけ磨いても届かない範囲があるのは、この形のせいです。

## 2×2 に並べると、穴が見える

ハーネスの要素は2軸で分類できます。**計算的（コードが判定）か、推論的（LLMが判断）か**。そして **ガイド（先回りして方向づける）か、センサー（あとから検知する）か**。

| | ガイド（先回り） | センサー（事後・検知） |
|---|---|---|
| **計算的**（決定論的） | 型・LSP・CLI・scaffold・テンプレ | lint・型チェック・テスト・build・CI |
| **推論的**（LLM判断） | CLAUDE.md・Skills・設計ドキュメント | AIコードレビュー・LLM-as-judge |

自分の資産をここに書き出してみてください。**4象限が揃って初めて強い**です。

推論だけだと、レビューはするけどテストがない。計算だけだと、テストは通るけど設計の妥当性を誰も見ていない。どちらも穴です。

## 穴になりやすいのは4か所、重い順

### 1. 計算的センサーがループに入っていない（最頻）

rig のカタログが最頻・最重として置いているのがこれです。テストも lint も **ある**。でもエージェントの実行ループに**バックプレッシャーとして入っていない**。

```
CLAUDE.md に「テストを実行して」と書く  ≪  hook で毎回強制する
```

散文の依頼は守られないことがあります。hook の強制は決定論的です。信頼性が段違いなんですよね。

「ある」と「効いている」は別物です。点検するときは、prose 止まりのルールを**未強制**として数えてください。

### 2. 検証ループがない

> モデルに自分の仕事を検証する手段を与えると品質が2〜3倍（Boris Cherny）

バックプレッシャーがないと、エージェントは自己評価に甘くなります。しかも計算的センサーは **sweet-talk できません**。テストは説得できない。だから最強のバックプレッシャーになります。

順番としては、**計算的センサーを一次、推論的センサーを二次**に置きます。AIレビューは大事ですが、それだけを頼りにすると採点が甘くなります。

### 3. 足しただけで、測っていない

ルールを足す。効果は測らない。これが3番目です。

**善意のルール追加が逆効果になることがあります。** Context Rot、つまり文脈が長いほど性能が落ちる現象があるので、ルールの肥大は判断を濁します。

逆方向の事故もあります。判定ルーブリックを6項目で検証したあと、プロンプトを採用3項目だけに「整理」したところ、**残った項目の判定が反転しました**。人間が書いた文書へのメタ言及の偽陽性が 6.7% から 50% に跳ねています（長井英之/オープンデータラボ 2026-07-09）。

LLM は項目リスト全体を文脈にして判定基準を組み立てているので、項目を削るのは無害な整理ではなく**判定挙動の変更**です。減らすなら再検証が要ります。

足すときは、**減らす候補**も一緒に持っておくのが安全です。

### 4. ハーネスが厚すぎる

> Thin Harness, Fat Skills（Garry Tan）

ループ管理は薄く、200行くらいに。知能は Skills に、実行は決定論的なツールに委譲する。親ループや親コンテキストが肥大してきたら、たぶん設計が間違っています。

## 自分に当てる6つの問い

そのまま使えるチェックリストにしておきます。

| 観点 | 見るところ | 落ちていたら |
|---|---|---|
| 計算的センサー | lint・型・テスト・build の存在と、hook / gate での強制 | prose の依頼で済ませている |
| 推論的センサーの独立 | レビューと判定の担い手が、生成者と別 | 自己採点で甘くなる |
| ガイドの両輪 | CLAUDE.md・Skills に加えて scaffold・テンプレ・CLI | 先回りが推論側だけ |
| 強制の決定論性 | 重要ルールが hook / CI に落ちている | prose 止まり＝未強制 |
| 薄さ | 親ループと親コンテキストが薄く、知能は Skills 側 | 親が肥大している |
| 計測 | ルールの効果測定と、削減候補の保持 | 足しっぱなし |

rig では `/rig:harness` がこれを自動でやります。ただ、問いのほうが本体なので、ツールを入れなくても手で当てられます。

## 結論は「足す」ではありません

穴が見つかったとき、最初にやりたくなるのはルールを足すことです。でも効くのはたいてい逆側でした。

**繋ぐ。強制する。薄くする。**

すでに持っている lint とテストをループに繋ぐ。CLAUDE.md に書いただけのルールを hook に移す。太った親ループを削る。この3つのほうが、新しいルールを1つ足すより効きます。

「みんなどう作ってるの？」への答えは、やっぱり持っていません。持っているのは、自分のを4象限に並べる紙とペンだけです。埋めてみて右上が空いていたら、そこが最初の1手です。
