# 「AIを放置で回したい」の答えは、止まり方を先に決めることでした

AIエージェントに仕事を任せるとき、いちばん欲しいのって「見てなくていい状態」ですよね。走らせて、寝て、起きたら終わってる。

でも実際にやると、だいたいこうなります。朝起きたら「完了しました！」と書いてあって、中身を見たら全然できていない。あるいは、同じところをぐるぐる回ったままトークンだけ溶けている。

このあたりを真面目に設計したくて、[rig](https://github.com/itoh-shun/rig) というオーケストレータを作っています。そこで出た結論が、タイトルのやつです。放置できるかどうかは、走り方ではなく**止まり方**で決まりました。

## 放置していいものと、ダメなもの

まず最初に線を引きます。

放置したいのは、**人が待つこと**です。確認画面の前でAIが止まって、こちらが「はい」を押すまで進まない。あれを消したい。

手放しちゃいけないのは、**人が決めること**です。マージするか、本番に出すか、このファイルを消していいか。

rig では自走モードに `--autonomous` を付けますが、同じ一文が3つのレシピに書いてあります。

> `--autonomous` でも capture ゲートは解除されない

自走で省けるのは「毎周の確認」だけで、書き込み・push・マージのゲートは残ります。待つのをやめて、決めるのは残す。ここを分けないと、放置の話はだいたい「AIに任せて大丈夫なの？」という水掛け論になります。

ついでに言うと、rig が同梱している42本のレシピは**全部 `autonomy: interactive`** です。既定で放置はしません。放置は必ず自分で明示する opt-in にしてあります。

## 放置は5か所で壊れる

「ループを1周回す」を分解すると、5つの動きになります。

| 動き | 欠けると |
|---|---|
| discovery（次の一手を見つける） | 空回りする |
| handoff（自分でやらず投げる） | 親エージェントが肥大する |
| verification（独立に検証する） | **間違ったまま完了する** |
| persistence（圧縮を跨いで覚える） | コンテキスト圧縮のあと最初からやり直す |
| scheduling（次をいつ起こすか） | コストが無駄に増える |

放置が失敗した話を聞くと、たいていこのどれかが抜けています。とくに multi-agent でハマるのは persistence で、長時間走らせると圧縮が入り、目標を忘れて別のことを始めます。

## いちばん壊れるのは検証で、犯人は自己採点

5つのうち、経験上いちばん事故るのが verification です。理由もはっきりしています。

**エージェントは、自分の出力を採点すると甘く付けます。**

生成した直後は意図が頭に残っているので、行間を勝手に補完して読んでしまう。人間でも自分の書いた文章の誤字が見えないのと同じです。

これが放置と最悪の相性なんですよね。人が見ていれば「いや違うだろ」で止まるものが、誰も見ていないので、そのまま「達成しました」で終わります。

なので rig は「作って、自分で合格」を禁止しています。しかも文章のお願いではなく、コードで返します。

```python
# 採点者が生成者だったら、gate はこれを返す
if any(str(v.get("by", "")).lower() in ("", "self", "generator", "producer") for v in verdicts):
    return "self-graded"
```

採点する人と作る人を分ける。放置運用でいちばん効いた対策が、たぶんこれです。

## 止まれるから、放置できる

無限に回るものは放置できません。止まる条件が決まっているから、安心して放っておけます。

rig の止まり方は3つあります。

**詰まりガード** — 未達のまま進捗ゼロの周回が2回続いたら止めて人に返します。ランナーのメッセージがそのまま思想です。

```
ESCALATE: ... (no infinite loops; hand off to the user.)
```

**停止条件の必須化** — 監視ループは `--until` か `--times` か明示の合意がないと、そもそも起動しません。「無限に見張っといて」ができないようにしてあります。

**過剰実装の禁止** — 基準を全部満たしたら止まります。良かれと思って作り続けません。

終わり方は `DONE` / `BLOCKED` / `ESCALATE` / `AWAIT` / `AWAIT_APPROVAL` の5つで、「なんとなく終わった」がありません。

## 壊れても本体が汚れない

これも放置には必須でした。rig は変更を独立した git worktree の中で作ります。

> AI の変更は、accept されるまで本体の作業ツリーに触れない。

そして accept は説得できません。

> failed か pending が1つでもあれば accept は**コードが拒否する**（散文の自制ではなくランナーが強制）

`--force` を付けても上書きできない前提が3つ残ります（worktree の存在、base branch の記録、差分サマリの生成）。最後の反映も squash merge の staged 状態までで、コミットはしません。**最後の一手は人に残る**ようにしてあります。

放置していて何かが壊れても、壊れるのは worktree の中だけです。これが分かってから、だいぶ気楽に走らせられるようになりました。

## 使い方

繰り返し・監視なら loop、達成まで詰めたいなら goal を使います。

```bash
# 終わりのない仕事（見張り・ポーリング）。停止条件は必須
/rig:loop --until "CI が green" "この PR を見張って"

# 終わりのある仕事（達成まで収束）
/rig:goal "ログイン不具合を回帰テスト込みで直して"
```

ヘッドレスで完全に放置するならこちらです。

```bash
rig-wb run bugfix --provider claude --verifier-provider codex --max-steps 20
```

`--verifier-provider` を生成側と別にしているのがポイントで、さっきの自己採点対策がここに出てきます。同じモデルしか使えないときは、合格扱いにせず「未検証」として報告します。

## まとめ

- 放置していいのは**待つこと**、ダメなのは**決めること**
- 1周回は discovery / handoff / verification / persistence / scheduling に分解できて、1つ欠けると事故る
- いちばん壊れるのは verification。自己採点は甘くなるので、採点者と生成者を分ける
- 詰まりガード・停止条件・過剰実装の禁止で、必ず止まるようにする
- 変更は worktree に隔離して、最後の一手は人に残す

自走そのものより、勝手に止まる保証のほうが大事だった、という話でした。
