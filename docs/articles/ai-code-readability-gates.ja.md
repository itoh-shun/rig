# 「動くからOK」の反対は「きれいだからOK」ではない — AI が書いたコードの可読性をゲートに載せる

AI に書かせたコードがテストを通る。動く。マージする。
半年後、誰もそのファイルを開きたがらない。

この問題への素朴な処方は「クリーンアーキテクチャにしろ」「レイヤを分けろ」を受入基準に足すことだ。
**それは効かない。効かないどころか、きれいな形をした負債が返ってくる。**

理由は、別の題材で実測してある。この記事はその実測を、コードの可読性に持ち込む話である。

## テストは可読性に対して盲目である

「動くからOK」の正体は、**行動ゲートしか通していない**という状態だ。
テストは入力と出力の関係を検査する。同じ入力に同じ出力を返す限り、
3層の間接を挟んでいようが200行の関数だろうが、テストは緑になる。

人間が書いていた時代、これでもある程度は成立していた。書き手が**自分で後で読むコストを払う**からだ。
可読性は明文化されたゲートではなく、書き手のインセンティブに乗った暗黙の制約だった。

AI に書かせると、その制約だけが消える。生成側は後で読まない。
**書き手が交代した瞬間に、暗黙だった制約は制約でなくなる。**
だから明示的なゲートに移す必要がある——ここまでは、たぶん誰でも同意する。

問題は移し方だ。

## 検査可能にするほど、機械的に充足される

別のベンチマークで、日本語の文章を「AIっぽくなく」書かせる実験を12設計ぶん回した
（[記録](jp-natural-writing-round2.ja.md)）。そこで何度も再現した法則がある。

> **検査可能な要求には、均等充足という抜け道が必ずある。**

実例を2つ挙げる。どちらも実測である。

**「検証可能な固有名詞を最低3つ入れること」**を受入基準にしたアームは、
タイトルに PostgreSQL 16 を掲げながら本文が MySQL の逸話で、索引の上限値も間違っている記事を返した。
**持っていない情報を要求すると、モデルは捏造で応じる。**

**文長分散の閾値**（形態素解析器による決定的な検出）をゲートにしたアームは、
短文を等間隔に挿入することでそれを攻略した。検出器の findings は 5.5 → 1.0 に改善し、
ブラインド判定は**悪化**した。判定役の講評はこうだった——「短文の挿入による意図的なリズム調整が機械的」。

**均等に演じられた品質は、それ自体が指紋になる。**

コードに移すと何が起きるか、想像はつくと思う。「レイヤを分けろ」を検査可能な基準にすれば、
**1箇所でしか使わない3層の抽象**が返る。rig の `/rig:drill` は既知のバグを注入して
レビュアーの検出率を測る仕組みだが、その種カタログにはこの class が最初から載っている。

| 種の class | 例 | 検出すべき観点 |
|---|---|---|
| 過剰抽象 | 1箇所でしか使わない 3層の抽象 | design / lazy-senior |
| 誤誘導命名 | 実態と逆の意味の関数名 | cognitive-economist |

つまり「クリーンアーキテクチャを基準にする」は、
**クリーンアーキテクチャの形をした過剰抽象**を誘発する。
基準を精密にするほど、機械的充足への誘導が強くなる。

これは AI が意地悪をしているのではない。**満たす方向が存在する要求は、その方向で満たされる**、
というだけのことだ。人間相手でも起きる（KPI のゲーム化と同じ構造）が、
生成が速く安い相手だと桁違いに起きやすい。

## 効いたのは「要求する」ではなく「絞る」だった

12設計のうち唯一効いたのは、出力に条件を要求しない型だった。
実在の成果物を**閉じた在庫**として渡し、在庫にない固有名詞・数値が出たら機械的に差し戻す。

ノルマとの違いは決定的で、**「多く出せば満たせる」方向が存在しない**。
だから捏造が起きない。持っていないものは書けない、というだけになる。

一般化するとこうなる。

| | 要求側ゲート | 供給側ゲート |
|---|---|---|
| 機構 | 出力が基準を満たすまでリトライ | 入力の語彙・素材・権限を閉じる |
| 失敗様式 | 満たす方向があるので**その方向で満たす** | 材料が無ければ書けない＝失敗が静か |
| 可読性での例 | 「レイヤを分けろ」「命名を改善せよ」 | 触れるファイルを限る・差分サイズの上限・**新しい抽象を作らせず既存のものを使わせる** |

**注意**: これは日本語生成で測った結果であって、コードでは測っていない。
上の表の右下は**予測**である。ただし予測の形は明確なので検証できる——
供給を絞ったアームと基準を足したアームで、同じ課題を解かせて過剰抽象の発生率を比べればいい。
rig の `benchmarks/hard-tasks/` はそういう比較のための場所だ。

## 基準ではなく視点を置く

供給を絞っても、残る部分はある。そこには**チェックリストではなく視点**を置く。

rig のレビュアーは、観点ごとに独立したペルソナとして分かれている。可読性に効く2枚を引く。

```
cognitive-economist — 読み手の認知コスト最小化に執着する
  評価軸: 命名の明瞭さ / 論理の素直さ / 局所性・一貫性 / 認知の無駄
  バイアス: 読み手に考えさせた時点で負け

lazy-senior — 怠惰な優秀シニア
  評価軸: 消せるコード / 不要なコメント / 過剰防御 / 将来のメンテ負債
  バイアス: 同じ動作なら行数が少ない方が正義。最高の褒め言葉は「これ消せるね」
```

チェックリストとの違いは、**満たす方向が一意でない**ことだ。
「命名を改善せよ」は充足できるが、「読み手に考えさせた時点で負け」は充足の形が定まらない。
だから均等充足の抜け道が作りにくい。

そして両者は**互いに反対を向いている**。cognitive-economist は明示を是とし、
lazy-senior は削除を是とする。明示のために足したコードは lazy-senior に叩かれ、
削って暗黙にしたコードは cognitive-economist に叩かれる。
**片方だけを満たす答えが存在しない**ように配置してある。

これも一般則で、日本語生成でも同じことが起きていた。生成器に「主観表現を使うな」と
形容詞レベルの指示を出したアームは、判別 75% から **100%（全敗）**へ悪化した。
一方、書き手の同一性を**データとして**（形容詞ではなく在庫として）渡した設計だけが機能した。
**形容詞は演じられる。制約は演じられない。**

## ここからが本題 — レビュアーも、測らないと嘘をつく

「可読性レビュアーを置く」は誰でもやる。ここから先が、実測しないと分からない領域だった。

### 1. 同じ入力に対する判定のブレを測っていない

日本語ベンチで一番大きい発見は、設計ではなく**判定役の側**にあった。
同じ記事を5回判定させると、ゲート付きアームの出力は sd 21〜30 で分布が二峰になった。

**バイト単位で同一のテキストが、9点と62点と68点を取った。**

これで過去の「発見」がいくつか死んだ。「68→12 の劇的改善」として3コミットにわたって
報告した数字は、判定のブレだった。

レビュアーでも同じことが起きる。同じ diff を2回投げて verdict が違うなら、
そのレビュアーの単票には意味がない。**にもかかわらず、これを測る機構はどこにもなかった。**
rig の `/rig:drill` は既知のバグの検出率を測るが、
**同一入力に対する分散**は測っていない。だから今回それを足した（`--repeat`）。

分散が大きい persona は、単票ではなく**クォーラム**で扱う必要がある。
何票必要かは、較正から決まる。決め打ちの数字ではない。

### 2. レビュアーが述べる理由は、判定の原因とは限らない

こちらのほうが厄介だった。

日本語ベンチで、負け講評の 24回中16回が「リンク・画像の欠如」を名指ししていた。
特徴量としても人間 5.56 対 AI 0.01 で全次元中最大の差（d=1.73）。
誰が見ても本命だった。

同一記事の sha 言及18箇所を実在の URL へ機械置換し、**他は一字も変えずに**再判定した。

```
騙せた試行  4/32  →  4/32     1ペアも動かない
```

同じ形式で、最大の特徴量差だった丁寧体率（人間 65.2% 対 生成 0.0%）を
機械変換で 67.8% までほぼ正確に閉じた。**これもゼロ**だった。

> **判定役が述べる理由は、その判定を動かしている変数とは限らない。**

これはレビューに直接効く。レビュアーが「この命名が分かりにくいので REJECT」と書いたとき、
**その命名が REJECT の原因である保証はどこにもない。**
指摘は正しく、しかし判定を動かしていない——という状態がありうる。

そこで `/rig:drill --ablate` を足した。手順は単一次元のアブレーションで、上の実験と同じ形だ。

1. REJECT を出したレビュアーの finding を1件取る
2. **その finding が名指しした欠陥だけ**を diff から機械的に取り除く。他は1バイトも変えない
3. 同じ persona で再判定する（アブレーションであることは伝えない）
4. verdict が翻れば、その指摘は**原因**。翻らなければ**装飾**である

```
| finding                        | 除去後の verdict | 判定 |
|--------------------------------|-----------------|------|
| 認可漏れ（src/orders.py:42）     | APPROVE         | 原因 |
| 命名が実態と逆（src/util.py:9）   | REJECT          | 装飾 |
```

**帰無対照を先に置くこと。** 何も除去していない同一 diff を同じ persona へもう一度投げ、
verdict が再現するかを見る。再現しない persona ではアブレーションが読めない——
判定のブレを因果と読み違えるからだ。日本語ベンチでは、この対照を置いた結果、
**バイト同一テキストの再判定でも 31ペア中1ペアが動く**ことが分かった。
それが床であり、床を超えない変化は効果ではない。

### 3. 測定器そのものが壊れる

もう一段外側にも欠陥があった。

「人間の文章は文長分散が大きい（143.9 対 36.0）」という数字を根拠に、
文長を不揃いにする介入を設計していた。その数字は**分析器のバグ**だった。
`。` だけで文を分割していたので、人間が書いた markdown の画像埋め込み行・箇条書き・表が
すべて隣接文に連結され、186字の疑似「文」になっていた。

生成側はそういう行をほとんど出さない（行の 1.8% 対 33.4%）。
**片側にしか効かないアーティファクトが、存在しないギャップを製造していた。**
両側同じ基準で数え直すと、人間 24.3 対 生成 29.3 で、**生成側のほうが大きかった**。

コード品質メトリクスも同じリスクを持つ。循環的複雑度・行数・凝集度——
どれも「何を1単位として数えるか」で値が変わり、その定義は生成コードと人間コードで
非対称に効きうる。**メトリクスを人間/AI で比べる前に、抽出器を両側の生の入力に当てて目視する。**

## まとめると

「動くからOK」は行動ゲートしか通していない状態で、AI 開発では書き手のインセンティブが
可読性を担保しなくなるぶん、明示的なゲートが要る。ここまでは自明だ。

自明でないのはここから先で、実測が言っているのは4つある。

1. **可読性を検査可能な基準にすると、機械的に充足される。** 「レイヤを分けろ」は
   1箇所でしか使わない3層の抽象を生む。これは AI の悪意ではなく、要求の形の帰結である。
2. **効くのは要求より供給の制約。** 出力に条件を課すより、触れる面・使える抽象・
   差分の大きさを閉じるほうが、同じ検査可能性で機械的充足を招かない。
3. **基準ではなく視点を、しかも互いに反対を向いた視点を置く。**
   明示を是とする観点と削除を是とする観点を並べると、片方だけを満たす答えが存在しなくなる。
4. **そのレビュアー自身を測る。** 同一入力での分散を測らないと単票が読めない。
   指摘の因果性を測らないと、正しいが判定を動かしていない指摘に時間を溶かす。

そして、この4つのうち最後の1つがいちばん省略されやすい。
レビュアーを置いた時点で品質保証をした気になるからだ。
**日本語ベンチでは、54コミットのうち大半が生成側ではなく測定側の欠陥を潰すために費やされた。**
たぶんコードレビューでも比率はそう変わらない。

## 正直に書いておく限界

この記事の実測は**すべて日本語文章生成で取られたもの**で、コードでは測っていない。
「均等充足」「供給側ゲート」「講評は原因ではない」はどれも、
題材を跨いで成立するという保証がまだない。

一方、`/rig:drill` の種カタログに `過剰抽象`（1箇所でしか使わない3層の抽象）と
`誤誘導命名`（実態と逆の意味の関数名）が最初から載っているのは、
**コード側でも同じ失敗様式が観測されていた**ということではある。それが独立の傍証にはなる。

やるべきことは決まっている。同じ課題を「基準を足したハーネス」と「供給を絞ったハーネス」で
解かせ、過剰抽象と誤誘導命名の発生率を比べる。帰無対照（同一 diff の再レビュー）を先に取る。
`--ablate` で、レビュアーの指摘が verdict を動かしているかを確かめる。

それを回すまでは、この記事の主張は**別の題材で測った法則の、まだ検証されていない転用**である。
