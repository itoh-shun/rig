# AIの品質ゲートは、測らないと平気で嘘をつく — rig で「AIっぽくない日本語」を測り続けた記録

[rig](https://github.com/itoh-shun/rig) は、AIに書かせた変更を隔離された worktree で走らせて、受入ゲートを通ったものだけを手元に入れるワークベンチです。README には「ゲートの効き目は主張ではなく計測で示す」と書いてあります。この記事は、その主張を日本語生成という一番測りにくい領域で本気で試したら何が起きたか、という記録です。

結論を先に書くと、54コミットと30本の結果ファイルの大半は、生成側ではなく**測定側**の欠陥を潰すために費やされました。そして16個のハーネス設計のうち、効いたのは1つだけでした。

## 何を測ろうとしたか

課題はシンプルです。ベンチマークの各アーム（ハーネス構成）に日本語の技術記事を書かせ、別プロセスの Claude Opus 5 に「これはAIが書いたか」を0〜100で判定させる。低いほど人間らしい。判定役はどのアームの出力かを知らされず、read-only ツールに固定されます。これは rig 本体が verifier ロールに課しているのと同じ enforcement です。

最初にやるべきだったのは、判定役の較正でした。ChatGPT 公開（2022-11-30）より前の Qiita 記事を16本集めて同じ判定にかけると、平均 11.06、誤判定は 1/16。つまり判定役は本物の人間の文章をちゃんと人間と判定します。目標水準は「11」です。50前後まで下がって喜んでいた時期がありましたが、あれは「まだ明らかにAI」の帯域の中で動いていただけでした。

較正で分かったことがもう一つあります。人間の記事が人間と判定される理由は、文章のうまさではありませんでした。「2022年3月27日時点では反応しませんでした」という日付つきの観察、「num_trainig_steps」というタイプミス、文の途中で終わっている記事、落ちたAWS試験の話。検証可能で、固有で、しばしば雑。この観察があとで全部の伏線になります。

## 12設計、ほぼ全滅

試した設計と結果です。

| 設計 | 結果 |
|---|---|
| 数量ノルマ基準（固有名詞を最低3つ等） | 退行。捏造を誘発 |
| 自己推敲ループ | 変化なし。SEO記事のテンプレへ収束 |
| 形態素解析 lint をゲート化 | lint は 5.5→1.0 に改善、判定は悪化 |
| 記事全体を各パスに見せない生成 | 悪化。導入文6連発になる |
| 段落末の内省を後処理で削除 | 変化なし |
| 節ごとに生成モデルを交代 | 悪化 |
| 骨格・構成指示を全部外す | 均質さの指摘率 8/8 のまま |
| 人間記事の構造だけ移植 | bare と1点差。無効果 |

個別に面白い失敗がいくつかあります。

ノルマ基準は「検証可能な固有名詞を最低3つ」と要求しました。返ってきたのは、タイトルに PostgreSQL 16 を掲げながら本文が MySQL の逸話で、しかも索引の上限値を間違えている記事です。**持っていない情報を要求すると、モデルは捏造で応じます。**

lint ゲートは coji さんの [natural-japanese](https://github.com/coji/natural-japanese)（sudachipy ベースの決定的検出器。人間103文書・AI81文書で較正されています）を借りました。モデルは `low_burstiness`（文長分散の検出器）を、短文を等間隔に挿入することで攻略しました。lint の findings は 5.5 から 1.0 に減り、ブラインド判定は悪化。判定役の講評は「短文の挿入による意図的なリズム調整が機械的」。**検査可能な要求には、均等充足という抜け道が必ずあります。** そして均等に演じられた人間らしさは、それ自体が指紋です。

構成指示を全部外す実験は、私自身の仮説を潰しました。「節に分けなくてよい、分量を揃えなくてよい」と明示しても、モデルは自分で「発端→実行→照合→結論」を組み立て、段落頭を「まず/次に/続けて」で揃えます。均質さはハーネスが押し付けていたのではなく、放っておくとモデルが自前で建てるものでした。

## 測定器が主犯だった

途中で一番大きい発見は、設計ではなく判定役の側にありました。

同じ記事を5回判定させると、素の生成（bare）は sd 2.5〜5.0 で安定します。ところがゲート付きアームの出力は sd 21〜30 で、分布が二峰になる。大半は72〜76、ときどき8〜22。**バイト単位で同一のテキストが、9点と62点と68点を取りました。**

これで過去の「発見」がいくつか死にました。68→12 の劇的改善として3コミットにわたって報告した数字は、判定のブレでした。「実行間分散25点」として生成のせいにしていたものも、大部分は判定側でした。以後、判定は3回反復に変更し、平均ではなく「3回中何回30点未満に入ったか」を見るようにしました。

最終的には絶対採点をやめて、2択判別に切り替えました。実在の人間記事と生成記事を同トピック・同字数で並べ、「どちらが人間か」を両順序で判定させる。50%なら見分けがつかない、100%なら常に見破られる。この方式は再現します — 2ラウンド回して、判別率だけでなく騙せた4試行のペアまで完全に一致しました。

現在地はこうです。**最良アームは、実在の人間記事との直接対決で4回に1回勝ちます**（生成の世代によっては8回に1回まで落ちます）。 bare は0勝です。目標の「見分けがつかない」は2回に1回。

## 効いた1つと、効かなかった有力候補

生き残った設計は writer と呼んでいるアームです。実在の成果物の台帳 — このリポジトリの実際のコミット、実際に落ちているテストのアサーション全文、ベンチ自身の記録値 — を閉じた語彙として渡し、台帳にない固有名詞・数値が出たら機械的に差し戻します。ノルマと違って「多く出せば満たせる」方向が存在しないので、捏造が起きません。

判定役が writer を人間と選んだときの講評は毎回同じことを言います。実在のコミットハッシュ、`assert 126 == 124` という生の失敗、そして「まだ切り分けられていない」で終わる構成。素材が本物で、問題が開いたままであること。

一方で、有力に見えた候補が完全統制の実験でゼロと出ました。リンク密度は人間 5.56/1000字 対 AI 0.01 で全特徴量中最大の差（d=1.73）、負けた試行の講評でも 24回中16回名指しされていました。そこで同一記事の sha 言及18箇所を `[sha](実在のコミットURL)` に機械置換して、他は一字も変えずに再判別したところ、騙せた試行は 4/32 → 4/32。1ペアも動きませんでした。講評に書かれる「リンク・画像の欠如」は人間側の豊かさの記述であって、判定を動かす原因ではなかった。相関と因果はここまで乖離します。

書き手の声についても同じ型の結果があります。コーパスを測ると、hedge・段落末の内省・一人称・口語はどれも**AIの方が人間より多い**。人間 Qiita 記事の丁寧体率は68.7%、AIアームは17.6%。語彙の多様性も人間の方が低い（TTR 0.68 対 0.84 — 人間は同じ語を繰り返します）。「人間らしさを足す」方向の介入は、最初から過剰側にさらに積んでいました。

## rig に返ってきたもの

このベンチは rig のゲート設計一般への教訓をいくつか実測で残しました。基準を精密にするほど機械的充足に誘導されること。生成器が持っていない情報を受入基準で要求すると捏造が返ること。ゲートの効き目を測る前に、**測定器自身の分散を測る**必要があること。

副産物もあります。fieldnote 系のアームは記事の素材として実際にこのリポジトリを調査するので、走らせるたびに本体の不備が出てきます。今回見つかったのは gitignore の穴が2件（`rig-action-state.json`、`.venv_*/`）と、私自身が入れた退行1件 — ベンチのタスクを `benchmarks/tasks/` に置いたせいでデフォルトコーパスの契約テストが壊れ、約20コミットの間、赤いまま push し続けていました。`pytest -x` が最初の失敗しか見せていなかったのが敗因です。ベンチ自体が、リポジトリへの反復的な実地監査として機能しています。

## 開いたままのもの

負けた24試行の講評を集計すると、残っている指摘は「文体の均質さ」が19回で圧倒的です。実在の素材を持たせても、散文のリズムそのものが均一に出る。これはモデルに書き直させれば自身の均質さが再導入され、ハーネス側で構造をいじれば破綻に見えるか無効果、という袋小路で、このセッションの手法では動かせませんでした。

素材の側にも上限があります。writer の強さは「本当に開いているバグ」から来ていますが、いまリポジトリに実在する未解決は4件しかなく、8トピックで使い回しています。これは捏造では増やせません。

再現手順と全結果は [`benchmarks/writing-tasks/jp-natural-writing/`](https://github.com/itoh-shun/rig/tree/claude/japanese-generation-facet-benchmark-5r3776/benchmarks/writing-tasks/jp-natural-writing) にあります。判定役の較正から始めてください。較正していない判定役の数字は、このセッションの前半がそうだったように、何かを測っているようで判定役の癖を測っています。

`tests/test_bench_providers.py` の `assert 126 == 124` は、まだ落ちています。
