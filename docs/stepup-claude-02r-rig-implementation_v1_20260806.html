VOL.3 実装編 STEPUP-CLAUDE-02r ・ 開発特化ステップアップガイド【rig 実装編】

4つのエンジニアリングを、rig で試す

前編（02a）・後編（02b）が扱う設計を、プロンプト／コンテキスト／ハーネス／ループの4つの層ごとに整理し、それぞれ「何のエンジニアリングか」「rig ではどう実装されているか」「実際に試す手順」の3点セットで示す。あわせて、rig 自身が rig で開発され、決定論的なベンチマークで自分を測りながら改善していることと、その結果として二冊の要求にどこまで届き、どこは届いていないかを数字で示す。

FIG.01 4つのエンジニアリングの入れ子と rig の担当（後編2-1の4層モデル）：①⊂②⊂③⊂④。rig は③を既製品として持ち込み、④は設定で開ける。

先に、30秒でわかる要約。
  • rig はAI を賢くする道具ではない。あなたが決めたルールを、AI に無視させないための道具である
  • 頼むと別室で作業して、合格したものだけを見せてくる。失敗しても手元のファイルは汚れない
  • 「できました」では通らない。合格していない変更は反映できない（人ではなく機械が断る）
  • 作った本人に合格を出させない。確かめる役は、そもそもファイルを書き換えられない状態で起動する
  • ただしパソコン側の隔離と、危険なコマンドの禁止は自分で用意する。rig は「入っていませんよ」と知らせるだけ

この資料の読み方

01〜04章は、4つの層をそれぞれ「何のエンジニアリングか → rig ではどうなるか → 試す流れ → できること／残ること」の順で扱う。05章では rig 自身がどう作られているか（自分で自分を開発し、ベンチマークで測っている）を、06章では二冊の要求に対する到達度を数字で示す。

層設計するものrig で試す入口
① プロンプト1回の指示の質——誰に、どの観点で見させるか/rig:persona・/rig:drill
② コンテキストその会話で何を見せるか／見せないか--plan の注入一覧・/rig:knowledge
③ ハーネスタスク1件の作業環境と合否判定　＝rig の本体/rig:go・/rig:harness
④ ループいつ・どれだけ回すか、どこで止めるか/rig:goal・/rig:loop

01 プロンプト・エンジニアリング　L1 基礎

つまり：AI への頼み方を毎回その場で考えるのをやめて、使い回せる形にして、良し悪しを点数で測る層。

何のエンジニアリングか

1回の指示の質を上げる層である。4層のいちばん内側で、効きはその1回きり——だから「良い書き方」を覚えるだけでは資産にならない。この層で本当に価値があるのは、うまくいった指示を次も同じ形で出せるようにすることである。

rig ではどうなるか

rig は指示を3つに分けてファイルにしている。観点（＝どこを見るか。セキュリティ担当・設計担当・テスト担当…といった見る目の違い。11種類が最初から入っていて、どれも読むだけで書き換えはできない）、決めごと（守らせたい方針。頼み文の決まった場所に、毎回そのまま入る）、返し方の型（合否の行を機械が拾えるように、書式を固定する）。この3つを毎回その場で書くのではなく、部品として組み合わせて頼み文を作る。

いちばんの違いは、プロンプトの良し悪しを測れることである。rig には、そのレビュー役が本当に欠陥を見つけられるかを採点する仕組み（/rig:drill）がある。やり方は学校のテストと同じで、わざと欠陥を仕込んだ使い捨ての成果物を見せて、答え合わせをする。採点項目は7つ（見つけた数・見逃した数・間違って指摘した数など）。プロンプトが感想でなく数字で評価できる状態になる。

採点の仕組みは、3つの意味で「自分用」にできる

この採点は、最初から入っている問題だけで動くものではない。①誰を測るか ②どんな問題を出すか ③何の成果物で測るか——3つとも差し替えられる。

差し替えるものできることやり方
測る相手（レビュー役）自分で作った観点を名指しで採点できる。組み込みのレビュー機能も同じ物差しに並べられる--personas <名前,…>（省略時は既定の3人＋プロジェクト設定の常設レビュー役）
出題（欠陥のカタログ）プロジェクト固有の欠陥を出題に足せる。標準カタログだけ／自作だけ／両方、を選べる--corpus standard｜project｜all。自作は .claude/rig/drill-corpus.md に標準と同じ列構成の表で置く
成果物の種類コード以外も測れる——文章・画面仕様・投稿文・商談メモなど最初から入っている24種のうち4種が非コード（下記）。採点のやり方はコードとまったく同じ
出題として持ち込むのは「欠陥の定義」であって、バグ入りのファイルそのものではない。 自作カタログに書くのは欠陥の種類・どの観点が見つけるべきか・本来つけるべき重大度で、実際のコードや文章はその定義に沿って毎回その場で合成される（本物のコードには触れず、終わったら破棄）。自分が用意した実ファイルで測りたい場合は別の仕組みが用意されている——05章のベンチマークは、脆弱な元コード／もっともらしいが不完全な修正／本当の修正／隠しチェックの4点セットを自分で書いて持ち込む形式である。もうひとつ、--replay は自分の過去の実際の差分に対して再採点するので、合成ではない、本物の題材で前後を比べたいときはこちらを使う。

非コードの出題は標準カタログに最初から入っている。コアの24種のうち4種が文章・設計物である——AI 臭の混入（文章）／UX ヒューリスティック違反・アクセシビリティ違反（画面仕様）／エンゲージメント構造の欠陥（投稿文）。採点方法は同一で、検出率も重大度の精度も説明の質も同じように出る。用途特化の出題（商談メモ・投稿文など）は、後述の拡張パック側が自分の評価ケースとして持つ形に整理された。自社の禁止表現や契約書の NG 条項のような独自の欠陥を足したいときは、自作カタログに1行足すだけでよい。

プロンプトを変えたら、評価ケースを要求する（回帰ゲート）

採点に加えて、頼み文を直すこと自体に CI の関門が掛かるようになった。どのファイルが「AI への頼み文」なのか——観点・決めごと・返し方の型・手順書など——はリストで決まっている。そこを1文字でも直したら、「直した結果、前にできていたことが壊れていないか」を確かめた記録を出せと CI に言われる。要するに、頼み文をコードと同じ扱いにするということである。

評価ケースが持つものなぜ要るか
直す前は落ちていた／直したら通った、の記録「直した」と言うには、直す前に本当に落ちていたことを見せる必要がある
「何も起きてはいけない入力」も試す直したい入力だけでなく、反応してはいけない入力も毎回走らせる。過剰に反応するようになっていないかを見る
機械の判定と、AI の採点を分ける数えれば分かる部分は機械で、読まないと分からない部分は AI で。混ぜない
3回以上の反復1回の当たり外れを結果にしない（3回未満は拒否される）
記録に封をする記録を取った後にこっそり頼み文を書き換えても、その記録は使い回せない

CI にはこのための専用ジョブがある。まずお金のかからない確認（直したファイルに対応する記録があるか）、次に信頼できる環境での実行。外部から来た変更では勝手に有料実行せず、メンテナが回す手順に落ちる。そして直したいところが良くなっても、反応してはいけない入力で悪化していれば通らない。

2つの仕組みの使い分け。 drill は「このレビュー役は、どれだけ欠陥を見つけられるか」を測る（実力テスト）。評価ケースは「この変更で、前できていたことが壊れていないか」を見る（壊れ防止）。育てるための物差しと、壊さないための関門。両方あって初めて、頼み文がコードと同じ扱いになる。

採点が甘くならないよう、2つの仕掛けが入っている。1つは「欠陥ゼロの成果物」を混ぜること。そこに何か指摘したら全部まちがいとして数える——「とりあえず何か言っておく」レビュー役が高得点にならないようにするためである。もう1つは、仕込んだつもりが実は無害だった問題を、別の担当が指摘して分母から外すこと。おかしな問題のせいで点数が不当に下がらないようにしている。

試す流れ：自分の観点をプロンプト資産にして、測る /rig:dev --plan --only review "現在の変更" → 誰にどの観点で見させるつもりか（合成結果）を、実行せずに確認する /rig:persona "リリース前に必ず移行手順を疑うレビュー役" → 説明文から観点ファイルを生成。以後 --persona で呼べる /rig:drill --personas my-reviewer → 自作の観点を名指しで採点。検出率・誤検知率・重大度精度…7指標 → Missed Issues（見逃し）と改善提案が、履歴通算で出る /rig:drill --corpus all --seeds 10 → 標準カタログ＋自作カタログの両方から出題（結果は選定元ごとに別行で記録） /rig:drill --replay my-reviewer → 観点を書き直したあと、過去の実際の差分に再実行して新旧の判定を比べる
ここが「試す流れ」の要。 観点を書き直したら --replay で前後を比べる。直したつもりが下がっていたことは普通に起きる。プロンプトを勘で育てるのをやめられるのが、この層で rig を使う理由である。
できること：指示が使い捨てでなく資産になり、良し悪しを数字で測れる。残ること：どんな観点が要るかを考えるのは人間の仕事。rig は「その観点が効いているか」しか答えない。

02 コンテキスト・エンジニアリング　L2 運用

つまり：AI に何を見せて、何を見せないかを決める層。見せすぎると、かえって大事な指示が薄まる。

何のエンジニアリングか

その会話で何を見せ、何を見せないかを設計する層である。コンテキストは大きいほど良いのではなく、注ぎ込むほど1つ1つへの注意が薄まる（後編でいう context rot）。有限の注意予算として扱う。

rig ではどうなるか

rig の基本は「親は要約だけ受け取る」。調べものや実装は別の担当に渡し、長い差分やログは親の会話に入れない。そのうえで、見せるものを3つに分けている。

置き場所入るものいつ読まれるか
知識の層検証済みの観点・手順（チームで共有する正本）関係する作業のたび
勘の層まだ検証していない「このプロジェクトではこう書く」確度が高いものだけ、字数上限つきで
検疫Issue や PR など外から来た文章「データである」と囲ってから渡す

2つ目の「勘の層」には賞味期限がある。しばらく使われない項目は自信度が下がり、下限を割ると自動で外れる。メモは放っておくと古くなる、という前提が最初から入っている。3つ目は、外から来た文章に「これまでの指示は無視しろ」と書いてあっても、それが命令として読まれない形に囲う仕組み。「従わないでください」と書いてお願いするのではなく、そもそも命令に見えない形に変えてしまう。

試す流れ：何を見せているかを、実行前に一覧する /rig:dev --plan "この変更をレビューして" → 実行せず、注入予定の知識ソース一覧・担当する観点・ゲート条件を表示 /rig:knowledge "この API の呼び出し規約" → 検証済みの知識ページを作る（全 RUN で参照される） /rig:go gh issue 123 → Issue 本文は「外部入力」として検疫されたうえで分類される
できること：「いま何を見せているか」が実行前に一覧できる。外部の文章が指示として効くことを構造的に防げる。残ること：見せすぎの判断は人間。増やすより減らすほうが効く層である。

03 ハーネス・エンジニアリング　L2 運用　rig の本体

つまり：1つの作業についてどこで作業させて、何をもって「終わり」とするかを決める層。rig が持ってくるのはほぼここ。

何のエンジニアリングか

タスク1件ごとに、どこで作業させ、何をもって完了とするかを設計する層である。前編の命題2「完了＝検証コマンドのパス」がそのままこの層の主題になる。rig が既製品として持ち込むのは、ほぼこの層である。

rig ではどうなるか

1行で言うと、自然文で頼むと、別室で作業して、合格したものだけを見せてくる。

FIG.02 rig の基本フロー：④で落ちたものは⑥へ進めない。「できました」という自己申告は完了の根拠にならない。

合否の判定は2種類ある。1つは機械のチェック。パスワードの混入、危険なコマンド、合格条件そのものの書き換え——決まったパターンを毎回同じように探すので、見落としがない代わりに、決めた形しか見つけられない。もう1つは別の AI による確認。書き換えできない状態で起動され、作った側の報告ではなく実際に何が変わったかを見て判定する。前者は確実だが浅い。後者は深いが当たり外れがある。この違いが、05章の測定結果にそのまま効いてくる。

試す流れ：普段の作業をそのまま通す /rig:go "ログインバグを直して" → 種類を判定 → 別室で作業 → 合否判定 → 要約 /rig:go diff → 何を変えたか／危ないところ／依頼と関係ない差分が無いか /rig:go accept → 合格していなければ断られる。コミットは常に人間が行う /rig:harness → 自分のプロジェクトのハーネス自体を監査（read-only）

/rig:harness は、「テストはあるのに、落ちても誰も止まらない」という穴を探す点検である。直し方の順番は足すより先に、繋ぐ・止まるようにする・減らす。新しいルールを足すのはいちばん最後でよい——たいていの穴は、すでにある道具が実行の流れに繋がっていないことで起きている。

できること：失敗しても手元が汚れない。自己申告では通らない。確かめる側が書き換えられない。残ること：パソコン側の隔離は別途必要（rig の「別室」はファイル作業を分けるだけで、危険なコードの実行を止める壁ではない）。

04 ループ・エンジニアリング　L3 発展

つまり：毎回人が指示しなくても回るようにする層。考えることは1つ、「どこで止めるか」だけ。

何のエンジニアリングか

人が毎回起点にならなくても回る形を作る層である。ここでの設計対象は「どう作業させるか」ではなく「いつ回し、どこで止めるか」——つまり停止条件の設計がこの層のほぼ全てである。

rig ではどうなるか

rig はループのために新しい仕組みを作っていない。1周まわる間にやることを5つに分けて、すでにある部品に割り振っただけである。覚えるのはこの5つでいい。

FIG.03 ループ1周回の5つの動き：①見つける →②任せる →③確かめる →④覚える →⑤次を予約する。1つでも欠けると事故る——特に③が甘いと、間違ったまま「できた」で止まる。

ゴールは「機械で確かめられる形」に落とす

ループが「終わった」と判断する基準は、要件定義から来る。要件には8つの要素があるが、ループにとって決定的なのは「Done（どうなったら終わりか）」の1つである。/rig:goal は最初の1回で目標を合格条件のリストに変え、以後は毎周それと照らし合わせる。

ゴールが基準に落ちないなら、それはまだ人間が決めていない。 「使いやすくして」は基準にならない。「3クリック以内で操作できる」「今あるテストが全部通る」なら基準になる。誰が見ても同じ判定になるかが分かれ目である。ループを開ける前のいちばん確実なチェックは、/rig:goal --plan で基準リストだけ出させて眺めることである。曖昧な基準のまま回すと、ループは「なんとなく達成」で止まる。
試す流れ：まず基準だけ見る → 収束させる → 見張らせる /rig:goal --plan "ログイン不具合を回帰込みで直して review 通過まで" → 受け入れ基準と想定ループ構成を出して停止（実行しない） /rig:goal "ログイン不具合を回帰込みで直して review 通過まで" → 基準を全部満たすまで回す。進捗ゼロが2回続いたら止めて相談 /rig:loop --every 10m --until "CI が green" /rig:pr 1234 → 終わりのない仕事（見張り）。止め方（条件か回数）の指定は必須 /rig:loop --every 1h /rig:goal "…" → 外側が「1時間ごとに起こす人」、内側が「達成まで詰める人」

自動化は3段階で上げる

FIG.04 自動化の3段階：--autonomous が省くのは毎周の確認であって、合格判定ではない。

できること：5つの動きが最初から割り当てられている。停止条件の指定が引数として必須になっている。残ること：人がいない時間に「始める」仕組みは rig の外（rig の予約はセッション内なので、CI や定期実行と組み合わせる）。そして③を外さないこと——ここは設定で外せてしまう。
実例

rig 自身が、rig で作られている

ここまでの4層を実際に回すとどうなるか。いちばん具体的な実例が rig 自身の開発である——rig は rig を使って開発され、決定論的なベンチマークで自分の効きを測りながら改善している。良い数字だけでなく、効かなかったという測定結果も含めて記録されている。

05 自分で自分を測りながら改善する　L2 運用

5-1 開発そのものが、同じゲートを通っている

rig 自身も、rig が求めるのと同じルールの下で開発されている。数字で言うとこうなる 確認済み（リポジトリの git 履歴・CI 定義を直接確認）。

開発期間1ヶ月2026-07-06 → 08-06
マージ済み PR61本全 134 コミット
バージョン記録148件CHANGELOG＋アーカイブ
テストファイル83本CI で全 PR に強制

CI は全ての変更に対して2種類の検査を掛ける。1つ目がコード側——書き方の統一／部品リストと実ファイルのずれ／同じ入力から同じ結果になるか／テスト一式。2つ目が頼み文の側（01章）——直した頼み文について、壊れていないことの記録を要求する。あわせて「資料で挙げた根拠が本当に存在するか」も毎回確認される（06章）。1つでも落ちれば変更は取り込まれない。つまり「終わったかどうかは、検査が通ったかで決める」という前編の考え方を、道具を作っている側が自分自身にも当てはめている。

5-2 効きを測る2つのベンチマーク——片方は課金ゼロで回る

「rig を使う意味があるか」は、実はまったく別の2つの問いに分かれる。rig はこれを混ぜずに測っている。

主張A：決まった欠陥は必ず止まる主張B：出力の質
何を言いたいか素のループではそもそも走らないチェックが必ず走る同じモデルでも rig 経由の方が出力が良い
測り方固定コーパスに機械センサーを直接ぶつける同一条件で「素で1回」対「rig 経由」を対戦させる
コストAI を1回も呼ばない・お金がかからない・何度やっても同じ結果実モデルと実課金が要る（明示フラグが必須）
結果既知の悪パターン 10/10 を捕捉、紛らわしい安全パターンでの誤検知 0/7合格条件は厳格（下記）。現時点ではまだ合格を主張していない

主張Aで大事なのは数字そのものではない。rig を使わない場合、この数字がそもそも存在しないということである。誰かがチェックを仕込まない限り検査は走らないので、同じ問題集に対する捕捉率は必ず 0% になる。ただしこれは決まったパターンを取りこぼさないという保証だけで、判断を要する欠陥（設計の誤り・業務ロジックの取り違え）については何も言えない 確認済み。

主張Bの合格ラインは、自分に厳しく引いてある。10課題以上、1課題あたり3組以上、rig 側の「気づかれない欠陥」が rig なしより半分以下、rig が安全のために途中で止まる割合は20%以下、AI を呼ぶ回数は2.5倍まで。しかもrig なし側に1件も欠陥が出なかったら「合格」ではなく「判定できず」にする——差が出なかったことを勝ちに数えないという決めである。

5-3 実際に測ったら、rig が効かなかった——その負の結果と、その後

ここがこの章でいちばん読む価値のあるところである。rig は「効かなかった」という測定結果を隠していない。むしろそこを起点に直している 確認済み（benchmarks/hard-tasks/README.md・CHANGELOG 1.24.0／1.24.1）。

実際に測った結果（2026-07-23／3種類のモデル・各9回）。 使った問題は「すでにある権限チェックの関数を信じてしまう」タイプの罠である。rig なしだと3モデルとも9回すべてで、気づかれない欠陥を出した（いちばん強いモデルも含めて）。そしてrig を通しても結果は同じだった。理由ははっきりしている——確かめる側が見抜けない欠陥は、何回やり直させても直らない。作る側と確かめる側が同じところを見落としていると、ゲートは欠陥をそのまま通してしまう。

rig が最初から言っていること——「rig は品質を自動で生まない。あなたが決めた基準を無視させないだけ」——が、そのまま数字で裏づけられた形である。逆に言えば、強くすべきなのはやり直しの回数ではなく、見つける力のほう。原因を追いかけたら、見落としは3段階あった。

FIG.05 測定 →原因の分解 →改善の実例：3層のうち2層は修正、残る1層は「観点では埋まらない構造的な限界」と認めたうえで、別の手段（全体走査）をゲートに繋いだ。

この一連の流れが、そのまま4層のエンジニアリングを一周した実例になっている——プロンプト層（観点を追加）、ハーネス層（振り分けとゲート条件を修正）、そして測定（ベンチマークとレビュー採点）で確かめる。CHANGELOG には「検出器と物差しは出荷したが、数字が動いたとはまだ主張しない」と明記されている。効いたことにしない、という規律である。

5-4 コード以外でも測った——日本語の文章で、約1700回

同じやり方を文章にも向けている。「rig を通すと、日本語の文章は人間が書いたものに近づくか」を、判定役に人間の記事と見分けさせて測り続けた記録がある。結論を先に言うと、これも「効かなかった」という記録である 確認済み（リポジトリ内の公開記事2本・CHANGELOG 1.28.3）。

段階起きたこと
第1ラウンド16のハーネス設計のうち、効いたのは1つだけ（実在の成果物を閉じた台帳として渡す設計）
その数字が消える測定側の欠陥が判明——対戦相手をトピックあたり1本しか使っていなかった。相手を31体に広げると判別率は 75% ではなく 94% だった
比較の基準を先に測るバイト単位で同一のテキストをもう一度判定させて、判定のばらつきだけで何ペア動くかを先に測った。答えは31ペア中1ペア——これを超えない差は、何も言えない
第2ラウンドさらに6設計・約1700判定。ばらつきの範囲を超えた設計は1つも無かった
分解能の較正そもそもこの測定器が検出できる差は 19〜29 ポイント規模と判明。「検出されなかった」を「効果が無い」と書き換え、過去の結論のどれが生き残るかを文書に明記

実は、途中で出てきたおまけの発見のほうが役に立つ。

  • 特徴量の差の大きさは、介入の価値を予測しない。人間と AI で最も開いていた特徴（文体・リンク）を機械的に埋めても、判定は1ペアも動かなかった
  • ギャップそのものが分析器のバグだった。「人間の文は長い」という前提は、画像や箇条書きを1文として数えていたせい。数え直すと人間のほうが短い文を書いていた——それまでの介入は、既に過剰な側にさらに積んでいた
  • 1行しか出力しない1時間半のジョブは、ハングと死亡と正常進行が区別できない。実行が2回消えて、途中経過の保存を足した
  • 道具の不在を黙殺していた。テスト実行環境が無い状態を「落ちているテストは無い」と読む欠陥があり、これを直さずに実験を続けていたら誤った結論が出るところだった
そして出した結論は「やめる」だった。 「生成側を押し続ける根拠は、もう無いと思っている」——約1700判定して、ばらつきの範囲を超えた設計が1つも無かったので、その方向への投資を止めるという判断が公開記事に書かれている。効かなかったと認めて撤退できたのは、「差が無いときにどれだけ動くか」を先に測っておいたからである。この基準が無ければ、ばらつきを成果と読み違えて、効かない改善を積み続けることになる。
rig の開発は「作る → 測る → 効かなかった所を特定する → 直す／やめる → また測る」で回っている。特筆すべきは、効かなかったという測定結果が製品ドキュメントに残っていること——コードでも（5-3）、文章でも（5-4）。ゲートの実効性を主張ではなくデータとして扱う設計方針が、自分自身にも適用されている。真似できるところを1つだけ挙げるなら、「差が無いときにどう出るか」を先に測っておくことである。

06 二冊の要求に、どこまで届いているか　L1 基礎

前編・後編が挙げる主要な要求を23項目に整理し、到達度を4段階で判定した。判定の基準は「実装があるか」と「効いていることを示せるか」を分けることである——実装しただけの項目を、証拠のある項目と同じ列に並べない。

この表は、資料の中で言い張っているのではない。リポジトリの側が確かめている。 23項目と、その根拠になるファイル名・テスト名は evals/coverage-map.json に置いてある。rig-wb coverage が「根拠として挙げたものが本当に存在するか」を毎回 CI で確認する。--run を付ければ、お金のかからない根拠を実際に走らせて合否まで出す。判定は書き込むのではなく、根拠から自動で決まるので、説明を強く書き直しても評価は上がらない。表が古くなったときに直すのは、表ではなく根拠のほうである。
対応済み・根拠あり18/23実行できる根拠が揃っている
一部だけ3/23残りは計画または有料実行
仕組みはあるが未測定1/23存在は効果ではない
未着手1/23仕様だけ書いてある

23項目のうち18項目は、根拠を挙げて実行できる状態になっている。残る5項目には、何を作れば埋まるかの仕様が1件ずつ書いてあり、その仕様自体も CI が検査する（空文句の「今後対応」を置けない）。うち2項目は rig の外側の要求——コンテナ隔離と実行時のコマンド禁止で、rig は検出して雛形を配るところまでを担い、実施は運用者に残る。

6-2 成果として言えること／言えないこと

数字の扱いは慎重にする必要がある。測れているものと、まだ測れていないものは別である。

言えること言えないこと
決まった欠陥を止めることは数字で示せる。既知の悪パターン 10/10 捕捉・誤検知 0/7。素のループにはこの数値自体が存在しない「rig を通すと出力が良くなる」はまだ証明されていない。セキュリティ課題群では素との差が出ず判定不能、難課題では同率だった
確かめる側が書き換えられないことは検証できる。プロバイダごとに強制の厚みが違うことまで公開されているゲートが見抜けない欠陥には効かない。作る側と確かめる側が同じ盲点を持つと、rig は素のモデルと同じように欠陥を通す
コード以外でも測る仕組みを作り、実際に回した。日本語の文章について約1700回の判定を実施し、判定のばらつきを先に測って基準にした文章の品質を上げられたことは示せていない。試した設計はどれもばらつきの範囲を出ず、「生成側を押し続ける根拠は無い」という撤退判断まで公開されている（05-4）
レビュー役の質は測れる。検出率・誤検知率・重大度精度を採点し、露呈した盲点は出題として追加される差分の外にある欠陥は、差分レビューでは原理的に見えない。全体走査ツールをゲートに繋いで補うという構造的な回答が要る
開発そのものが同じゲートの下で1ヶ月回っている。61 PR・83本のテスト・プロンプト変更の回帰ゲート・到達度の根拠の実在確認を CI が全 PR に強制その数値は自動公開されていない。メンテナーが手元で実行して貼る運用で、継続更新される公開スコアではない
この表の読み方。 左列は決まった手続きが必ず実行されることの保証、右列は出力が賢くなることの証明である。rig が今のところ確実に提供しているのは左列だけ——決まったパターンは必ず止める、確かめる側は書き換えられない、測る物差しがある。右列（同じモデルでも rig 経由なら質が上がる）は、厳しい合格条件を自分に課したうえで、まだ合格を主張していない。道具の評価としてはむしろこの正直さを見るべきところである。

6-3 残っている5つと、担当が運用者に残る2つ

未達の項目は「今後対応」で流さず、何を作れば埋まるかを仕様として書いてある。仕様の中身も機械が検査するので、空文句は置けない。

残っていること何を作れば埋まるか
red 証跡の機械確認（02a 3-A）実装 step の前に対象テストが実際に落ちた記録を実行状態へ残し、バグ修正の基準から参照する
主張の確からしさラベル（02a 3-A）出力契約に語彙を追加し、ラベルの無い主張を warning 段の基準で検出する（判断を要するので反映は止めない）
Intent 8要素の充足チェック（02b 2-3）--plan の出力に「どの要素が空欄のまま RUN に入ろうとしているか」を足し、Done が観点検証だけの場合に警告する
出力の質の証明（02b 5-1）有料の対戦ベンチを実際に回す。合格条件は先に記録済み——後から基準を緩めて「合格」にできないようにするため
テストスイートの検知力（02b 5-2）外部のミューテーションツールの結果を取り込む adapter を足し、スコアの劣化を warning 段の基準として扱う（100%は目標にしない）

そして、rig 側の対応が済んでも担当が移らないものが2つある。

  • コンテナ隔離——rig は「今このセッションはコンテナの中か」を検出して報告し、雛形まで配る。入れるのは運用者。隔離 worktree はファイル作業の分離であって、コード実行の境界ではない
  • 実行時のコマンド禁止——rig は permissions.deny が設定されているかを検出する。止めるのはホストの権限層。rig のセンサーが読むのは diff に書かれたコマンドで、実行の傍受ではない

この2つを「rig の外だから対象外」と書くのをやめて、検出して報告するところまで rig に持たせた——設定し忘れが「いつか整える」のまま残らないようにするためである。ただし報告は強制ではない。入れる判断は人間に残る。

07 はじめかた——層の順に開ける　L1 基礎

4層は内側から積む。③から入り、④は最後。これを逆にすると、速く間違い続ける仕組みになる。

STEP 0土台（rig の外）コンテナで隔離し、削除・本番反映・秘密の出力を権限設定で塞ぐ。rig より先にやる。
STEP 1③ ハーネス層で普段使いインストールして /rig:init、あとは /rig:go "…"。設定ゼロで安全フローが動く。2週間続ける。
STEP 2①② を測って整える/rig:drill でレビュー役の検出率を測り、--plan で何を見せているかを一覧する。/rig:harness で穴を洗う。
STEP 3④ ループ層を開ける/rig:goal --plan でゴールが基準に落ちることを確認してから回す。無人化はさらにその後。
STEP 1 の最短経路 /plugin marketplace add itoh-shun/sito-plugins /plugin install rig@sito-plugins /rig:init → プロジェクト設定などを提案 → 確認 → 生成 /rig:go "ログインバグを直して" /rig:go diff /rig:go accept → 合格していなければ断られる。コミットは常に人間が行う

導入チェックリスト

  • rig を入れる前に、コンテナ隔離と危険操作の権限設定を済ませた（06-3）
  • CLAUDE.md の「完了と言う前に検証しろ」系の記述を、rig のゲート側に任せた（01・06-1）
  • 2週間 /rig:go で普段の作業を回し、一度も落ちないゲートが無いか確認した（03）
  • レビュー役の検出率を一度は測り、書き直したら --replay で前後を比べた（01）
  • ループを開ける前に、ゴールが機械で確かめられる形に落ちることを確認した（04）
  • 「確かめる側を分ける」設定を、速さのために外していない（04・05）
  • rig の測定がまだ証明していないこと（出力の質の向上）を、社内説明で誇張していない（06-2）
  • rig-wb hostcheck を一度は走らせ、コンテナ隔離と permissions.deny の欠けを潰した（06-3）
