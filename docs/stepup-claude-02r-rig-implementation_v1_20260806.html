4つのエンジニアリングを、rig で試す

前編（02a）・後編（02b）が扱う設計を、プロンプト／コンテキスト／ハーネス／ループの4つの層ごとに整理し、それぞれ「何のエンジニアリングか」「rig ではどう実装されているか」「実際に試す手順」の3点セットで示す。あわせて、rig 自身が rig で開発され、決定論的なベンチマークで自分を測りながら改善していることと、その結果として二冊の要求にどこまで届き、どこは届いていないかを数字で示す。

01 プロンプト・エンジニアリング　L1 基礎

何のエンジニアリングか

1回の指示の質を上げる層である。4層のいちばん内側で、効きはその1回きり——だから「良い書き方」を覚えるだけでは資産にならない。この層で本当に価値があるのは、うまくいった指示を次も同じ形で出せるようにすることである。

rig ではどうなるか

rig は指示を3つに分けてファイルにしている。観点（誰として見るか。セキュリティ／設計／テストなど11種類の read-only レビュー役）、規範（守らせたい方針。プロンプトの決まった位置に必ず入る）、出力形式（返し方の型。判定行を機械が拾えるようにする）。毎回その場で書くのではなく、合成して組み立てる。

いちばんの違いは、プロンプトの良し悪しを測れることである。rig は「レビュー役が本当にバグを見つけられるか」を採点する仕組みを持っている——使い捨ての差分にわざとバグを仕込み、検出率・誤検知率・重大度の精度など6指標で採点する。プロンプトが感想でなく数字で評価できる状態になる。

試す流れ：自分の観点をプロンプト資産にして、測る /rig:dev --plan --only review "現在の変更" → 誰にどの観点で見させるつもりか（合成結果）を、実行せずに確認する /rig:persona "リリース前に必ず移行手順を疑うレビュー役" → 説明文から観点ファイルを生成。以後 --persona で呼べる /rig:drill → わざとバグを仕込んだ差分で採点。検出率・誤検知率・重大度精度…6指標 /rig:drill --replay → 観点を書き直したあと、同じ差分で再採点して前後を比べる
ここが「試す流れ」の要。 観点を書き直したら --replay で前後を比べる。直したつもりが下がっていたことは普通に起きる。プロンプトを勘で育てるのをやめられるのが、この層で rig を使う理由である。
できること：指示が使い捨てでなく資産になり、良し悪しを数字で測れる。残ること：どんな観点が要るかを考えるのは人間の仕事。rig は「その観点が効いているか」しか答えない。

02 コンテキスト・エンジニアリング　L2 運用

何のエンジニアリングか

その会話で何を見せ、何を見せないかを設計する層である。コンテキストは大きいほど良いのではなく、注ぎ込むほど1つ1つへの注意が薄まる（後編でいう context rot）。有限の注意予算として扱う。

rig ではどうなるか

rig の既定は「親は要約だけ受け取る」である。調査や実装は別の担当（subagent）に渡し、長い差分やログは親の会話に入れない。そのうえで、見せるものを3つに分けている。

置き場所入るものいつ読まれるか
知識の層検証済みの観点・手順（チームで共有する正本）関係する作業のたび
勘の層まだ検証していない「このプロジェクトではこう書く」確度が高いものだけ、字数上限つきで
検疫Issue や PR など外から来た文章「データである」と囲ってから渡す

2つ目の「勘の層」には賞味期限がある——しばらく使われない項目は確度が下がり、下限を割ると自動で外れる。暗黙知は放っておくと腐る、という前提が設計に入っている。3つ目の検疫は、外部の文章に「これまでの指示を無視しろ」と書かれていても、それが指示として読まれない形に囲う仕組みである（散文で「従わないで」と書くのではなく、構造で無効化する）。

試す流れ：何を見せているかを、実行前に一覧する /rig:dev --plan "この変更をレビューして" → 実行せず、注入予定の知識ソース一覧・担当する観点・ゲート条件を表示 /rig:knowledge "この API の呼び出し規約" → 検証済みの知識ページを作る（全 RUN で参照される） /rig:go gh issue 123 → Issue 本文は「外部入力」として検疫されたうえで分類される
できること：「いま何を見せているか」が実行前に一覧できる。外部の文章が指示として効くことを構造的に防げる。残ること：見せすぎの判断は人間。増やすより減らすほうが効く層である。

03 ハーネス・エンジニアリング　L2 運用　rig の本体

何のエンジニアリングか

タスク1件ごとに、どこで作業させ、何をもって完了とするかを設計する層である。前編の命題2「完了＝検証コマンドのパス」がそのままこの層の主題になる。rig が既製品として持ち込むのは、ほぼこの層である。

rig ではどうなるか

1行で言うと、自然文で頼むと、別室で作業して、合格したものだけを見せてくる。

FIG.02 rig の基本フロー：④で落ちたものは⑥へ進めない。「できました」という自己申告は完了の根拠にならない。

合否判定には2種類ある。機械のチェック（秘密情報の混入・危険なコマンド・ゲート定義の改ざん・外部からの指示混入など、決まったパターンを決定論的に走査する）と、別の AI による検証（書き換えできない状態で起動され、作った側の報告ではなく実際の差分を見て判定する）。前者は確実だが浅く、後者は深いが当たり外れがある——この性質の差が、05章の測定結果に効いてくる。

試す流れ：普段の作業をそのまま通す /rig:go "ログインバグを直して" → 種類を判定 → 別室で作業 → 合否判定 → 要約 /rig:go diff → 何を変えたか／危ないところ／依頼と関係ない差分が無いか /rig:go accept → 合格していなければ断られる。コミットは常に人間が行う /rig:harness → 自分のプロジェクトのハーネス自体を監査（read-only）

/rig:harness は「テストや lint はあるのに、どこにも繋がっていない（落ちても止まらない）」という穴を探す監査である。手の打ち方の順序は足すより、繋ぐ・強制する・薄くする——新しいルールの追加は最後に置く。

できること：失敗しても手元が汚れない。自己申告では通らない。確かめる側が書き換えられない。残ること：パソコン側の隔離は別途必要（rig の「別室」はファイル作業を分けるだけで、危険なコードの実行を止める壁ではない）。

04 ループ・エンジニアリング　L3 発展

何のエンジニアリングか

人が毎回起点にならなくても回る形を作る層である。ここでの設計対象は「どう作業させるか」ではなく「いつ回し、どこで止めるか」——つまり停止条件の設計がこの層のほぼ全てである。

rig ではどうなるか

rig はループのために新しい仕組みを作っていない。ループの1周回を5つの動きに分解し、既にある部品に割り当てているだけである。覚えるのはこの5つだけでよい。

FIG.03 ループ1周回の5つの動き：①見つける →②任せる →③確かめる →④覚える →⑤次を予約する。1つでも欠けると事故る——特に③が甘いと、間違ったまま「できた」で止まる。

ゴールは「機械で確かめられる形」に落とす

ループの採点基準は、後編でいう Intent（要件定義）から来る。8要素のうち、ループにとって決定的なのは④Done（受け入れ基準＝停止条件）である。rig の /rig:goal は最初の1回で目標を基準リストに変換し、以後の毎周それと照らす。

ゴールが基準に落ちないなら、それはまだ人間が決めていない。 「使いやすくして」は基準にならないが、「操作が3クリック以内」「既存テストが緑」なら基準になる。ループを開ける前のいちばん確実なチェックは、/rig:goal --plan で基準リストだけ出させて眺めることである。曖昧な基準のまま回すと、ループは「なんとなく達成」で止まる。
試す流れ：まず基準だけ見る → 収束させる → 見張らせる /rig:goal --plan "ログイン不具合を回帰込みで直して review 通過まで" → 受け入れ基準と想定ループ構成を出して停止（実行しない） /rig:goal "ログイン不具合を回帰込みで直して review 通過まで" → 基準を全部満たすまで回す。進捗ゼロが2回続いたら止めて相談 /rig:loop --every 10m --until "CI が green" /rig:pr 1234 → 終わりのない仕事（見張り）。止め方（条件か回数）の指定は必須 /rig:loop --every 1h /rig:goal "…" → 外側が「1時間ごとに起こす人」、内側が「達成まで詰める人」

自動化は3段階で上げる

FIG.04 自動化の3段階：--autonomous が省くのは毎周の確認であって、合格判定ではない。

できること：5つの動きが最初から割り当てられている。停止条件の指定が引数として必須になっている。残ること：人がいない時間に「始める」仕組みは rig の外（rig の予約はセッション内なので、CI や定期実行と組み合わせる）。そして③を外さないこと——ここは設定で外せてしまう。

rig 自身が、rig で作られている

ここまでの4層を実際に回すとどうなるか。いちばん具体的な実例が rig 自身の開発である——rig は rig を使って開発され、決定論的なベンチマークで自分の効きを測りながら改善している。良い数字だけでなく、効かなかったという測定結果も含めて記録されている。

05 自分で自分を測りながら改善する　L2 運用

5-1 開発そのものが、同じゲートを通っている

rig のリポジトリは、rig が課すのと同じ規律の下で開発されている。数字で言うと次のとおり 確認済み（リポジトリの git 履歴・CI 定義を直接確認）。

開発期間1ヶ月2026-07-06 → 08-06
マージ済み PR60本全 135 コミット
リリース35回CHANGELOG の記録
テストファイル61本CI で全 PR に強制

CI（validate.yml）は全 PR に対して4つを強制する——lint／構造チェック（ブリック目録と実ファイルのずれ検出）／決定論チェック（同じ入力で同じ合成結果になるか）／テスト一式。1つでも落ちれば PR は通らない。前編の命題2「完了＝検証コマンドのパス」を、道具の作り手自身が自分に適用している形である。

5-2 効きを測る2つのベンチマーク——片方は課金ゼロで回る

「rig を使う意味があるか」は、性質の違う2つの主張に分かれる。rig はこれを分けて測っている。

主張A：機械の床主張B：出力の質
何を言いたいか素のループには存在しないチェックが必ず走る同じモデルでも rig 経由の方が出力が良い
測り方固定コーパスに機械センサーを直接ぶつける同一条件で「素で1回」対「rig 経由」を対戦させる
コストLLM 呼び出しゼロ・課金ゼロ・完全決定論実モデルと実課金が要る（明示フラグが必須）
結果既知の悪パターン 10/10 を捕捉、紛らわしい安全パターンでの誤検知 0/7合格条件は厳格（下記）。現時点ではまだ合格を主張していない

主張Aの要点は数値そのものではない。素の claude -p ループには、この数値自体が存在しないことである——誰かが配線しない限りチェックは走らないので、同じコーパスに対する保証捕捉率は構造的に 0% になる。これは床であって天井ではない：判断を要する欠陥（設計の誤り・業務ロジックの取り違え）については何も証明しない 確認済み。

主張Bの合格条件は自分に厳しく設定されている——10タスク以上、各タスク3組以上の有効ペア、rig 側の「静かな欠陥」率が素の側より50%以上低いこと、rig の安全停止率が20%以下、平均呼び出し回数が素の2.5倍以下、など。そして素の側に欠陥が1件も出なければ「合格」ではなく「判定不能」とする——差が出なかったことを勝ちに数えない設計である。

5-3 実際に測ったら、rig が効かなかった——その負の結果と、その後

ここが、この章でいちばん伝える価値のある部分である。rig は「効かなかった」測定結果を隠さず、それを起点に改善している 確認済み（benchmarks/hard-tasks/README.md・CHANGELOG 1.24.0／1.24.1）。

実測（2026-07-23／3モデル・各9サンプル）。 「認可ヘルパーを信じてしまう」タイプの罠に対し、素のモデルは3モデルとも全9回で静かな欠陥を出した（最上位モデルを含む）。そしてrig を通しても安全率は同じ 50% で並んだ——rig は助けにならなかった。理由は明快で、ゲートが見抜けない欠陥には、何回やり直させても意味がないから。作る側と確かめる側が同じ盲点を持っていると、ゲートは欠陥を通してしまう。

rig 自身の主張——「rig は品質を自動的に生むのではなく、あなたが定義した品質基準を無視させない道具である」——が、そのまま測定で裏づけられた形である。裏を返せば、強くすべきは繰り返し回数ではなくゲートの検知力だということになる。原因を追ったところ、盲点は3層あった。

FIG.05 測定 →原因の分解 →改善の実例：3層のうち2層は修正、残る1層は「観点では埋まらない構造的な限界」と認めたうえで、別の手段（全体走査）をゲートに繋いだ。

この一連の流れが、そのまま4層のエンジニアリングを一周した実例になっている——プロンプト層（観点を追加）、ハーネス層（振り分けとゲート条件を修正）、そして測定（ベンチマークとレビュー採点）で確かめる。CHANGELOG には「検出器と物差しは出荷したが、数字が動いたとはまだ主張しない」と明記されている。効いたことにしない、という規律である。

rig の開発は「作る → 測る → 効かなかった所を特定する → 直す → また測る」で回っている。特筆すべきは、効かなかったという測定結果が製品ドキュメントに残っていること。ゲートの実効性を主張ではなくデータとして扱う、という設計方針が、自分自身にも適用されている。

06 二冊の要求に、どこまで届いているか　L1 基礎

前編・後編が挙げる主要な要求を22項目に整理し、rig の到達度を4段階で判定した。判定の基準は「実装があるか」と「効いていることを数字で示せるか」を分けることである——実装しただけの項目を、成果が出ている項目と同じ列に並べない。

実装＋実測あり5/22数字で効きを示せる
実装のみ13/22動くが未測定
部分的2/22半分は rig の外
rig の外2/22別の層で用意する

実装は 18/22 まで届いている。ただし「効いている」と数字で言えるのは 5 項目である。この差こそが、この資料でいちばん正確に伝えたいところである。

6-2 成果として言えること／言えないこと

数字の扱いは慎重にする必要がある。測れているものと、まだ測れていないものは別である。

言えること言えないこと
機械の床は数字で示せる。既知の悪パターン 10/10 捕捉・誤検知 0/7。素のループにはこの数値自体が存在しない「rig を通すと出力が良くなる」はまだ証明されていない。セキュリティ課題群では素との差が出ず判定不能、難課題では同率だった
確かめる側が書き換えられないことは検証できる。プロバイダごとに強制の厚みが違うことまで公開されているゲートが見抜けない欠陥には効かない。作る側と確かめる側が同じ盲点を持つと、rig は素のモデルと同じように欠陥を通す
レビュー役の質は測れる。検出率・誤検知率・重大度精度を採点し、露呈した盲点は出題として追加される差分の外にある欠陥は、差分レビューでは原理的に見えない。全体走査ツールをゲートに繋いで補うという構造的な回答が要る
開発そのものが同じゲートの下で1ヶ月回っている。60 PR・35リリース・61本のテストを CI が全 PR に強制その数値は自動公開されていない。メンテナーが手元で実行して貼る運用で、継続更新される公開スコアではない
この表の読み方。 左列は「土台の保証」、右列は「賢さの証明」である。rig が今のところ確実に提供しているのは左列だけ——決まったパターンは必ず止める、確かめる側は書き換えられない、測る物差しがある。右列（同じモデルでも rig 経由なら質が上がる）は、厳しい合格条件を自分に課したうえで、まだ合格を主張していない。道具の評価としてはむしろこの正直さを見るべきところである。

6-3 rig の外で用意するもの（5つ）

  • パソコン側の隔離——コンテナ（DevContainer）以上。rig はその中で動かす
  • 危険なコマンドの実行禁止——Claude Code 側の権限設定。rig のチェックは二重目の網
  • 何を良しとするかの基準——人間が決める。決めた基準は rig に追加できる（緩めることはできない）
  • 人がいない時間に「始める」仕組み——CI や定期実行。rig は始まった後を担当する
  • テストスイートの検知力の測定——言語ごとのミューテーションテストを検証コマンドに繋ぐ

07 はじめかた——層の順に開ける　L1 基礎

4層は内側から積む。③から入り、④は最後。これを逆にすると、速く間違い続ける仕組みになる。

STEP 0土台（rig の外）コンテナで隔離し、削除・本番反映・秘密の出力を権限設定で塞ぐ。rig より先にやる。
STEP 1③ ハーネス層で普段使いインストールして /rig:init、あとは /rig:go "…"。設定ゼロで安全フローが動く。2週間続ける。
STEP 2①② を測って整える/rig:drill でレビュー役の検出率を測り、--plan で何を見せているかを一覧する。/rig:harness で穴を洗う。
STEP 3④ ループ層を開ける/rig:goal --plan でゴールが基準に落ちることを確認してから回す。無人化はさらにその後。
STEP 1 の最短経路 /plugin marketplace add itoh-shun/sito-plugins /plugin install rig@sito-plugins /rig:init → プロジェクト設定などを提案 → 確認 → 生成 /rig:go "ログインバグを直して" /rig:go diff /rig:go accept → 合格していなければ断られる。コミットは常に人間が行う

導入チェックリスト

  • rig を入れる前に、コンテナ隔離と危険操作の権限設定を済ませた（06-3）
  • CLAUDE.md の「完了と言う前に検証しろ」系の記述を、rig のゲート側に任せた（01・06-1）
  • 2週間 /rig:go で普段の作業を回し、一度も落ちないゲートが無いか確認した（03）
  • レビュー役の検出率を一度は測り、書き直したら --replay で前後を比べた（01）
  • ループを開ける前に、ゴールが機械で確かめられる形に落ちることを確認した（04）
  • 「確かめる側を分ける」設定を、速さのために外していない（04・05）
  • rig の測定がまだ証明していないこと（出力の質の向上）を、社内説明で誇張していない（06-2）
順番は土台 →③ハーネス →①②を測る →④ループ。rig は入れた初日から「機械の床」として効くが、「出力が良くなる」はまだ測定中の主張である。床を買う道具として導入し、質の向上は自分のプロジェクトで測って判断する——それが、この道具自身の作り方と一致した使い方である。
