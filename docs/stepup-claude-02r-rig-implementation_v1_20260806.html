01 rig を制御要素マップに置く　L1 基礎

1-1 rig とは何か（1枚で）

rig は Claude Code のプラグインとして動く、品質保証つきの AI ワークベンチである。自然文のタスクを渡すと、①タスク種別を分類し、②対応する recipe（step の束）を選び、③作業ツリーとは隔離された git worktree で実行し、④acceptance-gate で機械的に検証し、⑤明示的な accept があるまで手元のファイルに一切触れない。

重要なのは、rig が「品質を自動的に生む道具」ではないことである。rig 自身がそう書いている——rig は、あなたが定義した品質基準を AI に無視させないための強制と測定の層であり、基準を作るのは人間の仕事のまま。この位置づけは、前編02章の「文脈は①〜③、強制は⑥⑦」という分担と正確に一致する。rig が引き受けるのは⑥⑦の側である。

FIG.01 rig の基本フロー：①分類→②recipe→③隔離→④gate→⑤サマリ→accept/discard。前編命題2「完了＝検証コマンドのパス」が、accept の前提条件としてコードに埋まっている。

2-1 A：働き方要点5行が、どこに機械化されるか

前編3-Aの「働き方の要点5行」は、rig ではほぼ全行が機械側へ移せる。これが rig を入れる実利のうち最も分かりやすい部分である——CLAUDE.md に書いた「お願い」を、gate と別プロセスの verifier に置き換えられる。

要点5行（前編3-A）rig での機械化強制力の移動
主張には VERIFIED / REASONED / ASSUMED のラベルを付ける直接の対応物は無い。近いのは output-contracts/review-findings（severity・file:line・Blocking/Non-blocking を必須にする出力契約）と、verifier の CRITERION n: PASS|FAIL|UNKNOWN 行——UNKNOWN を明示的に許すことで「確認できていない」を潰さない文脈 → 構造（部分的）
完了＝検証コマンドのパス。実行結果なしに完了と報告しないacceptance-gate。failed/pending が1件でもあれば accept が exit 1 で拒否される文脈 → 強制
テストは red を確認してから実装に入る（red証跡）bugfix プリセットの regression_test_added_or_explained／feature プリセットの tests_added_or_explained。加えて no_gate_tampering が「既存テストの改変・assert 削除・skip マーカー追加」を warning として検出する文脈 → 強制
同じ修正に2回失敗したら、コンテキストをリセットするstuck-guard（同一エラー反復で発動・固定上限2）と max_retries K（gate 収束ループの上限・既定2）の独立した2カウンタ。どちらも上限で user へエスカレーションし、状態ヘッダに stuck: N/2・(try N/K) として常時可視化される文脈 → 構造
委譲時はこの要点を逐語コピーで運び、再委任はしないブリック合成（PARSE→RESOLVE→COMPOSE→RUN）。policy facet はプロンプト末尾、persona は System、という配置順が決まっており、要約されずファイルの内容がそのまま入る文脈 → 構造

2行目・3行目が強制まで上がるのが要点である。前編が「言われれば当然だが、書かれていないと守られない」と評した5行のうち、破られると最も痛い2行が、お願いから機械の拒否になる。残り3行は構造どまり——つまり、発動条件を満たせば安定して効くが、条件の外では効かない。

ラベル行だけは、rig を入れても自分で書く。 主張ラベル（VERIFIED / REASONED / ASSUMED）に相当する仕組みは rig に無い。verifier 側の UNKNOWN 判定と /rig:sage の確度表示が近いが、日常の報告文に確からしさを付けさせるのはCLAUDE.md の1行に残すのが正しい。rig で埋まらないマスの1つ目である。

2-2 B：working-method.md は、どこへ分解されるか

前編3-Bの working-method.md（4部構成）は、rig では3つの置き場所に分かれる。1ファイルに集めないのは、それぞれ読み込まれるタイミングが違うためである（前編3-Bの「常時払うコストと、必要時に払うコストの仕分け」をさらに細かくしたもの）。

working-method.md の部rig での置き場所読み込まれるとき
PART 1 書く前の行動recipes/*.md の step 列（intake→design→implement→verify→review→pr→merge）recipe 解決時。番号でなく step 名で欠番が見える
PART 2 検証レシピmanifest .claude/rig.md の build/lint/test ＋ recipe の checks: 行該当 step 実行時。コマンドとして実行されるので散文ではない
PART 3 意思決定の分岐facets/policies/*（risk-based-testing・branch-strategy・ci-cost・pr-hygiene ほか）subagent プロンプト末尾に注入
PART 4 学習ループ知識層 facets/knowledge/（検証済み）＋ .rig/instincts.jsonl（未検証・confidence つき）知識層は全 RUN、instinct は SessionStart で 0.7 以上のみ

PART 4 の二層構造は、前編3-Bには無い rig 独自の分割である。検証済みの知識と、まだ検証していない勘を混ぜない——さらに instinct には減衰が入る（30日未使用で confidence 低下、0.2 未満で失効）。「暗黙知は放置すれば腐る」という前提を設計に埋めた形で、前編3-Eの週次 pruning を知識側にも適用したものと読める 確認済み（workbench.py instincts）。

2-3 C：強制境界——rig が持ってくる5つの機械センサー

前編3-Cは「破られては困る禁止を CLAUDE.md に書かない」と述べた。rig の acceptance-gate のうち5基準は、モデルの自己申告ではなく決定論的なスキャナが裏づける 確認済み（scripts/workbench.py）。ここが rig の強制境界の中核である。

基準センサー等級脱出口
no_secret_leaktask diff へのシークレットスキャン（scan-secrets）fail--set no_secret_leak=passed（抜粋は常にマスク済み）
no_injection_markersdiff＋repo の散文へのインジェクション・マーカースキャン不可視/bidi Unicode は fail／指示上書き語は warning--set …=passed（記録される）
no_gate_tamperinganti-tamper スキャン（.rig/gates.json・recipe・CI workflow の編集）ゲート定義の編集は fail／既存テスト改変は warning--set …=passed（記録される）
no_destructive_operation破壊的コマンドスキャン（rm -rf /・mkfs・DROP DATABASE ほか）上記は fail／git clean -f・force push 等は warning--set …=passed（記録される）
public_api_changes_documentedOpenAPI schema-diff（openapi.json 等を自動検出）warning（単独では gate を落とさない）—

設計上の要点は3つある。第一に、脱出口はあるが必ず記録される（.rig/audit.jsonl／workbench.py audit）。第二に、ゲート定義そのものの改変を検出する基準（no_gate_tampering）が入っている——これは前編3-Cのコラムが警告した「/update-config が permissions.allow をついでに広げる」問題の、ゲート側での対処にあたる。第三に、プロジェクト側の .rig/gates.json は加算のみで、組み込み基準の削除・緩和キーは即座に拒否される——リポジトリ内のファイルがゲートを弱められない。

「境界を守る仕組みが、無審査で緩む経路を残さない」の実装。 前編3-Cはこれを原則として述べ、rig は3つの層で実装している：①gates.json は加算のみ、②no_gate_tampering がゲート定義の編集を fail 扱いにする、③accept の構造的前提（worktree_exists・base_branch_recorded・diff_summary_generated）は --force でも上書きできない。--force が越えられるのは soft な gate 未達だけで、そのときは監査証跡が残る。

2-4 前編1-3「隔離」との関係——ここは rig では埋まらない

rig の isolated worktree は、前編1-3の隔離5分類の代替ではない。 worktree 隔離は同一ホスト・同一ユーザー権限の中でのファイル作業の隔離であり、「失敗した変更が手元に残らない」ことは保証するが、プロンプトインジェクション経由の任意コード実行に対する境界は一切提供しない。前編1-3の推奨ベースライン（③コンテナ／DevContainer 以上、自律実行なら⑤MicroVM の検討）は、rig を入れてもそのまま必要である。正しい構成は二層——DevContainer の中で rig を走らせる。

逆に言えば、この2つは目的が違うので競合しない。隔離レベル（①〜⑤）が「ホストを守る」ものであるのに対し、worktree は「あなたの作業ツリーと、まだ承認していない変更を分ける」ものである。後編2-2の acceptance-gate 3本柱でいえば、worktree は①受け入れゲート（基準を通過しない限りメイン作業ツリーへ反映しない）の実装手段にあたる。

3-6 実際の手順：見張るループと、収束するループ

rig は「終わりのある仕事」と「終わりのない仕事」を別コマンドに分けている。後編2-2の4分類でいえば ②goal-based と ③time-based の分離である。

収束するループ（goal-based）——終端＝受け入れ基準 /rig:goal --plan "ログイン不具合を回帰込みで直して review 通過まで" → 受け入れ基準＋想定ループ構成を提示して停止（RUN しない＝L1 report-only 相当） /rig:goal "ログイン不具合を回帰込みで直して review 通過まで" → 基準化 → 現状把握 → 次手 → /rig:dev へ委譲 → 独立照合 → 未達なら次周回 → 全基準充足で停止（過剰実装しない）／進捗ゼロ2回で停止して人間へ
見張るループ（time-based）——終端＝停止条件または回数 /rig:loop --every 10m --until "CI が green" /rig:pr 1234 → 10分ごとに1 tick。各 tick を報告し、停止条件の充足で終了 /rig:loop --every 1h /rig:goal "Issue を review 通過まで" → 外側が loop（スケジューラ）、内側が goal（収束）。重ねて使える /rig:loop --times 3 /rig:dev --only review → 回数で止める。停止条件も上限も無いまま無限監視には入らない

この2つを分けておくことの実利は、停止条件の書き忘れが構造的に起きにくくなることである。/rig:loop は --until か --times のどちらかを要求し、両方省いた場合は安全上限の確認に落ちる。後編2-2が「どの分類でも設計の中心は停止条件」と述べた点が、引数仕様のレベルで強制されている。

ループエンジニアリングを rig でやる、とは「5つの動き（discovery / handoff / verification / persistence / scheduling）を、既にある部品へ割り当てる」ことである。新しいループ機構は作らない。自律度は --plan（L1）→ 既定の gated フロー（L2）→ --autonomous・queue・Action（L3）の順に上げ、どのレベルでも acceptance-gate は外さない。④proactive の起動側だけは rig の外（CI・cron・Routines）で用意する。

各基準は passed / failed / warning / skipped のいずれかで根拠つきに記録され、全体は passed / passed_with_warnings / failed / pending / skipped に集約される。warning は accept を止めないが、常に提示され黙って握りつぶされない——後編06章②の Bad vs Sad でいえば、Sad を可視のまま積み残す設計である。

5-2 /rig:drill＝レビュアー版のミューテーションテスト

後編5-2のミューテーションテストは「テストが通ること」と「テストが守っていること」を分ける手法だった。rig の /rig:drill は同じ発想をレビュアーに適用する——既知のバグ class（認可漏れ・インジェクション・N+1・破壊的変更・片道 migration・テスト欠落）を使い捨て diff に注入し、reviewer に見せない答案キーと突き合わせて採点する。

FIG.07 ミューテーションテストと /rig:drill の対応：測る対象がテストからレビュアーへ移っているだけで、狙い（偽陰性の可視化）は同じ。

drill が出す指標は6つ——true_positive / false_positive / false_negative / severity accuracy / blocking accuracy / explanation quality。後編3-4が求めた「検出率だけでなく誤検知率まで測る（Score＝検出率−誤検知率）」が指標セットに入っている点が要点である。さらに改善提案は固定4カテゴリ（add_checklist_item / adjust_severity_rule / add_false_positive_guard / strengthen_security_focus）からのみ選ばれる——曖昧な感想ではなく、run をまたいで集計できる形にするため。--replay でペルソナ編集後の回帰確認（スナップショットテスト）ができる。

コードのミューテーションテストそのものは rig には無い。 drill が測るのはレビュアーであって、テストスイートの検知力ではない。後編5-2をそのまま実行したいなら、言語ごとのミューテーションテストツールを recipe の checks: に繋ぐ（対象を絞って小さく回し、スコアの推移を見る）。rig で埋まらないマスの2つ目である。

5-3 ゴム印レビュアーの検出

後編5-1の「AI レビューを一次に置く」構成で最も静かに壊れるのが、何でも通すレビュアーである。rig の stats はこれを名指しで警告する。

workbench.py stats（抜粋） Verifier behavior: - strict_senior_engineer: 14 runs, 6 rejects - product_reviewer: 6 runs, 0 rejects Warning: product_reviewer has 0 rejects across 6 runs. Possible rubber-stamp behavior.

この検出が成立するには、review タスクの verdict を記録する運用（/rig:go review <task_id> --set <persona>=<APPROVE|REJECT|…>）が要る。記録しないと測れない——後編が繰り返す「測れないゲートは願望にすぎない」の、運用側の対価である。

5-4 所見の側も疑う：--verify-findings

reviewer を増やすほど false-positive も増える。rig は集約判断表を適用する前に反証段を挟む opt-in を持つ——REJECT の根拠とマージ前必須条件を1件ずつ finding-verifier（所見を出した reviewer とは別 subagent）へ渡し、反証を試みさせる。

反証結果扱い設計意図
REFUTED（証拠つきで反証された）ゲートに通さない。ただし棄却理由と反例アンカーを1行ログとして残すサイレントに消さない
UPHELD / UNRESOLVED通す疑わしきは所見の利——棄却は確証がある時だけ

後編2-2の「疑わしきは不合格側に倒す」と、この「疑わしきは所見の利」は同じ原理の表と裏である（どちらも不確実なときは安全側＝止まる側に倒す）。verifier 自身の票もテレメトリに記録され、棄却の質を後から監査できる。

5-5 CI ゲートの4段と、rig の置き場所

後編5-3の「Lint → Audit → Test → Build」の4段に対し、rig が持ち込むのは段の追加ではなく、段の前倒しである。

段rig での置き場所いつ落ちるか
① Lintgit hooks pre-commit（manifest lint＋staged シークレットスキャン）commit 前
② Auditgate の機械センサー5種＋scripts/sast_adapter.py（/rig:sec）accept 前（CI より手前）
③ Testrecipe の checks:＋git hooks pre-push（build＋test）push 前
④ Build通常の CI／action.yml（gate が DONE のときだけ push＋PR 作成）CI 上

後編5-3のもう1つの要点——ループ自体の CI/CD と、ループ生成物の CI/CD を混ぜない——は、rig では no_gate_tampering が部分的に守る（CI workflow・gates.json・recipe の編集が task diff に混ざっていたら fail 扱い）。「仕組みを直したら検査が緩んだ」を、diff の混在という形で検出する。

5-6 検査面を事前に絞る（ASVS）と、外部入力の扱い

後編5-4の「後で見つけるから、最初から満たすへ」に対応するのが /rig:sec パックである（audit ＝攻撃者視点の read-only 探索／pentest-fix ＝PoC の回帰テスト化→修正／monitor ＝定期再スキャン）。観点カタログは facets/knowledge/wiki/attack-catalog にあり、決定論センサーは sast_adapter.py と scan-secrets が担う。倫理境界（自プロダクト／許可済み環境・静的＋ローカル検証のみ）がパックの定義に書き込まれている。

外部入力の扱いは、後編5-4の話題より一段構造的である。GitHub の Issue/PR 本文・コメントは信頼できない外部入力として、下流の persona に届く前に検疫フェンスで囲われる——推測不能な per-call デリミタでデータであることを明示し、不可視/bidi Unicode を先に剥離する（改竄シグナル）。散文で「従わないで」と書くのではなく、埋め込まれた指示がフェンスを抜け出せない構造にする 確認済み（rig_workbench/orchestrate/quarantine.py）。前編02章の「文脈は破られる／強制は破られない」を、外部入力に適用した実装である。

品質担保で rig が加えるのは「ゲートを測る層」である——drill が reviewer の検出率と誤検知率を、stats がゴム印を、digest が期間推移を出す。後編が繰り返した「測れないゲートは願望にすぎない」に対する道具側の回答であり、逆に言えば記録しなければ測れない——verdict の記録と drill の定期実行は運用の仕事として残る。

06 導入：どの順で入れるか　L1 基礎 〜 L2 運用

前編04章の導入順序（①1モデル完結 →②スキル1〜3個 →③週次ルーチン定着 →④マルチ化）を、rig の入れ方に翻訳する。最初から Loop 層を開けない——後編2-1の「下位層を疎かにしたまま上位層を導入しても効かない」がそのまま適用される。

STEP 1土台を先に置くDevContainer 等でホストを隔離する（前編1-3）。CLAUDE.md に働き方要点を書き、permissions.deny で削除系・本番反映・秘密出力を塞ぐ。rig の前にやる——rig はこの層を代替しない。
STEP 2Harness 層から入れる/plugin install → /rig:init（manifest・知識層・Compact Instructions を確認のうえ生成）→ /rig:go "<タスク>" を普段の作業で使う。設定ゼロで安全フローは動く。
STEP 3gate が落ちるのを見る2週間ほど回して workbench.py digest --period week を見る。一度も落ちない gate は、効いていないか、緩い。/rig:harness で空象限と「繋がっていない資産」を洗う。
STEP 4測ってから広げる/rig:drill で reviewer の検出率を実測 → --verifier-provider でクロスプロバイダ → /rig:queue で並列 → 最後に /rig:goal・--autonomous で Loop 層を開ける。
STEP 2 の最短経路 /plugin marketplace add itoh-shun/sito-plugins /plugin install rig@sito-plugins /rig:init → manifest（.claude/rig.md）・知識層ディレクトリ・CLAUDE.md の Compact Instructions 節を提案 → 確認 → 生成 /rig:go "ログインバグを直して" → 分類 → recipe 選択（理由バナー1行）→ 隔離 worktree → gate → サマリ /rig:go diff/rig:go accept → gate 未達なら accept は拒否される。commit は常に人間が行う

STEP 3 の「一度も落ちない gate は効いていない」という見方は、後編5-2のミューテーションテストの発想を運用に持ち込んだものである。前編3-Eの週次ルーチン（/insights→/fewer-permission-prompts→/update-config→pruning→/checkup）と rig 側の週次（digest→stats→instincts --decay→/rig:harness）は別々に回す——前者は Claude Code 環境の健全性、後者はプロジェクトのハーネスの健全性で、見ているものが違う。

7-2 実装はあるが未検証（rig 自身の申告）

rig は README で未検証領域を名指ししている。この誠実さ自体が本書の推奨理由の一部だが、導入時は未検証の機能を安全性の前提に置かないこと 仮定。

7-3 道具では決まらないこと（後編2-4の反証を引き継ぐ）

後編2-4は「ループの価値には上限がある」という反証を、両論のまま置いた。rig を入れてもこの論点は動かない。むしろ、rig を入れると回す速度が上がる分だけ、この問いが早く来る。

閉じた問題か、開いた問題か。 自走時間ではなくフィードバックの情報量が成果物の独自性の上限を決める、という批判である。ルール既知・自己完結採点の「閉じた問題」は無限に自走できるが、競合・規制・利用者期待が動く「開いた問題」は外から情報を入れ続けない限り前へ進めない。rig の gate は閉じた問題の採点を機械化する道具であり、開いた問題の情報供給は代替しない。/rig:goal を回す前に、そのゴールが機械検証可能な基準へ落ちるかを見ること——落ちないなら、それはまだ人間が決めていないという信号である。

もう1つ、後編2-2の長期実測が挙げた残課題——属人化（本人が休むと仕組みが止まる）——も rig では埋まらない。むしろ recipe・persona・manifest という形で設定が増える分、引き継ぎの対象が増える。/rig:catalog（全 tier 横断の地図）と --plan（合成ハーネスの提示）は、その引き継ぎコストを下げるための機能だと理解しておくとよい。

rig は強制と測定の層であって、隔離の代替でも、基準の代わりでもない。「rig を入れたから後編の設計が済んだ」と読まないこと。埋まらない5つ（ホスト隔離・実行時ブロック・主張ラベル・proactive の起動側・コードのミューテーション）は、rig を入れた後も自分で用意する。
