VOL.3 実装編 STEPUP-CLAUDE-02r ・ 開発特化ステップアップガイド【rig 実装編】

ガイドラインを rig でやると、こうなる

前編（02a）と後編（02b）が「何を、どの強制力で載せるか」を決める本だとすれば、この資料は「では rig を使うと、それが実際どう回るか」を図で示す1枚ものである。細かい設定名は追わない。何が自動で守られ、何は自分でやるのか——判断に必要なところだけを書く。

FIG.01 1枚まとめ：rig が引き受けるのは強制と記録。基準づくりと土台の隔離は、rig を入れても自分の仕事として残る。

この資料でいちばん伝えたいこと。 rig は「AI に良い仕事をさせる道具」ではなく、「あなたが決めた基準を、AI に無視させない道具」である。前編の命題1でいえば、rig が持ってくるのは強制の輪だけ。文脈の輪（CLAUDE.md に書く働き方の要点）は、rig を入れても自分で書く。

01 rig は何をする道具か　L1 基礎

やることは1行で言える。自然文でタスクを頼むと、別室で作業して、合格したものだけを見せてくる。

FIG.02 rig の基本フロー：④で落ちたものは⑥へ進めない。前編の命題2「完了＝検証コマンドのパス」が、道具の動作としてそのまま入っている。

CLAUDE.md に書いていた「お願い」が、どこまで機械の拒否になるか

前編3-Aの働き方要点5行のうち、2行は自動で守られるようになる。残りは引き続き書いておく必要がある。ここが導入の実利のいちばん分かりやすい部分である。

前編3-A の要点rig を入れると
完了＝検証コマンドのパス機械の拒否になる。合格していないものは反映できない
テストは失敗を確認してから実装するチェック項目になる。テストを勝手に緩めた形跡も検出する
同じ修正に2回失敗したらリセットする回数カウンタが自動で数え、上限で人間に相談してくる
委譲するときは要点を逐語で運ぶ決まった位置に決まった文面が入る（要約されない）
主張には確からしさのラベルを付ける対応する仕組みは無い。CLAUDE.md に書いたまま残す
rig は「別室で作業して、合格したものだけを見せる」道具である。CLAUDE.md に書いた「完了と言う前に検証しろ」だけは、お願いから機械の拒否に変わる。それ以外は今までどおり書いておく。

02 ループエンジニアリングは、rig だとこう回る　L2 運用

後編02章の主題（人が起点でなくても回る形）を rig でやる場合、覚えることは1つだけである。rig はループのために新しい仕組みを作っていない。ループの1周回を5つの動きに分解して、既にある部品に割り当てているだけである。

FIG.03 ループ1周回の5つの動き：①見つける →②任せる →③確かめる →④覚える →⑤次を予約する。5つのうち1つでも欠けると事故る——特に③が甘いと、間違ったまま「できた」で止まる。

動き欠けるとどうなるか
① 見つける同じ場所をぐるぐる回る（空回り）
② 任せる親の会話が長い差分やログで膨れて遅くなる
③ 確かめる間違ったまま「達成」で止まる（自分の成果を甘く採点するため）
④ 覚える会話が圧縮された瞬間にゴールを忘れ、最初からやり直す
⑤ 次を予約する無駄に高くつく／止まらなくなる

2つのループを使い分ける

rig は「終わりのある仕事」と「終わりのない仕事」を別コマンドに分けている。この2つを混ぜないのが、止まらないループを作らないコツである。

終わりがあるゴールまで回す/rig:goal "ログイン不具合を回帰込みで直して review 通過まで"

基準を全部満たしたら止まる。進まなくなったら人間に相談して止まる。
終わりがない見張る・定期実行/rig:loop --every 10m --until "CI が green"

止め方（条件か回数）を必ず指定する。指定しないまま無限監視には入れない。

重ねることもできる。/rig:loop --every 1h /rig:goal "…" なら、外側が「1時間ごとに起こす人」、内側が「達成まで詰める人」になる。

自動化の度合いは、3段階で上げる

後編2-2の成熟度モデル（報告だけ → 修正案まで → 無人）は、rig ではフラグの違いとして現れる。どの段でも、合格判定は外れないのが要点である。

FIG.04 自動化の3段階：--autonomous が省くのは毎周の確認であって、合格判定ではない。「採点者のいない自動運転」になりにくくしてある。

ループを回すとは、5つの動きを毎周ちゃんと踏ませること。rig は5つを既存の部品に割り当ててあるので、自分で組む必要はない。ただし③（別の目で確かめる）だけは設定で外せてしまうので、そこは外さない。自動化は第1段→第2段→第3段の順に、gate が実際に落ちるのを見てから上げる。

03 分業と品質は、こう分かれる　L2 運用

作る側と確かめる側を、プロセスごと分ける

後編の命題1「自分の宿題を自分で採点させない」を、rig はお願いではなく起動時の設定で実現している。検証役はそもそもファイルを書き換えられない状態で起動される。

FIG.05 作る側と確かめる側の分離：「レビュー担当が、レビュー対象を勝手に直してしまう」が構造的に起きない。

並列で走らせても、ぶつからない

後編3-1が挙げた衝突のうち、いちばん被害が大きい「同じファイルを同時に編集してしまう」は rig では起きない。タスクごとに別室が作られるためで、並列にするために追加で気をつけることが無い。/rig:queue に積んでまとめて走らせても同じである。

「ゲートがある」と「ゲートが効いている」を分ける

後編05章のいちばん大事な指摘は、測っていないゲートは願望にすぎないということだった。rig はここに道具を用意している。

知りたいことやること
レビュー役は、本当にバグを見つけられるのかわざとバグを仕込んだ差分を見せて、検出率と誤検知率を採点する（/rig:drill）
何でも通すレビュー役がいないか実績を集計すると「N回中0件しか却下していない」と警告が出る
そもそもゲートは効いているのか週次の集計を見る。一度も落ちないゲートは、効いていないか緩い

最初のうちは「落ちるのが煩わしい」と感じるが、落ちないゲートには意味が無い。2週間ほど回して、一度も落ちていない項目があれば、基準の方を見直す。

分業で効くのは2つだけ覚えればよい。確かめる側は書き込めない状態で起動することと、タスクごとに別室なので並列でぶつからないこと。そのうえで、ゲートが本当に効いているかをときどき測る。

04 rig がやらないこと　L1 基礎

ここが導入判断でいちばん効く。rig を入れてもガイドラインの要求が全部埋まるわけではない。埋まらないのは次の5つで、いずれも別の場所で用意する。

埋まらないことどこで埋めるか
パソコン側の隔離（前編1-3）
rig の「別室」はファイル作業を分けるだけで、危険なコードの実行を止める壁ではない		DevContainer などのコンテナ。rig はその中で動かす
危険なコマンドの実行禁止（前編3-C）
rig が見るのは「差分に書かれたコマンド」で、実行そのものは止めない		Claude Code 側の権限設定（deny）。rig のチェックは二重目の網
何を良しとするかの基準
rig は基準を作らない。守らせるだけ		人間が決める。決めた基準は rig に追加できる
人がいない時間に勝手に始める仕組み
rig の予約はセッションの中だけ。閉じれば止まる		GitHub Actions・cron・Routines。rig は始まった後を担当する
テストの検知力の測定（後編5-2）
rig が測るのは「レビュー役」であって、テストの品質ではない		言語ごとのミューテーションテストのツールを、検証コマンドに繋ぐ
未検証の機能を、安全の前提にしない。 rig は自分の README で「実装はあるが実環境では未検証」の領域を正直に名指ししている（GitHub Actions からの PR 作成、Codex・Cursor の実機動作、一部のプロバイダなど）仮定。この誠実さは道具として信頼できる材料だが、導入時は安全性の土台をそこに置かないこと。土台は前編1-3の隔離と、Claude Code 側の権限設定に置く。

05 はじめかた　L1 基礎

順番を守ることが大事である。最初からループ（自動で回す）を開けない。下の層を飛ばすと、速く間違い続ける仕組みになる。

STEP 1土台を先に置くコンテナで隔離し、削除・本番反映・秘密の出力を権限設定で塞ぐ。rig より先にやる。
STEP 2普段の作業で使うインストールして /rig:init、あとは /rig:go "…" を普段どおり使うだけ。設定ゼロで動く。
STEP 32週間、落ちるのを見る週次の集計を見て、一度も落ちないゲートが無いかを確認する。落ちないなら基準を見直す。
STEP 4測ってから広げるレビュー役の検出率を測る → 検証役を別モデルにする → 並列にする → 最後にループを開ける。
STEP 2 の最短経路 /plugin marketplace add itoh-shun/sito-plugins /plugin install rig@sito-plugins /rig:init → プロジェクト設定などを提案 → 確認 → 生成 /rig:go "ログインバグを直して" → 種類を判定 → 別室で作業 → 合否判定 → 要約 /rig:go diff /rig:go accept → 合格していなければ断られる。コミットは常に人間が行う

導入チェックリスト

  • rig を入れる前に、コンテナでの隔離と、危険な操作の権限設定を済ませた
  • CLAUDE.md の「完了と言う前に検証しろ」系の記述を、rig のゲート側に任せた
  • 2週間 /rig:go で普段の作業を回した
  • 週次の集計を見て、一度も落ちないゲートが無いか確認した
  • レビュー役の検出率を一度は測った
  • ループ（/rig:goal・自動実行）を開ける前に、ゴールが機械で確かめられる形になっているか確認した
  • 「確かめる側を分ける」設定を、速さのために外していない
順番は土台 → 普段使い → 測る → 広げる。rig は入れた初日から安全側に効くが、ループを開けるのは最後。ゴールを機械で確かめられる形に落とせないうちは、それはまだ人間が決めていないということである。
