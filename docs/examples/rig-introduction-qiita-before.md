# Rigというツールを使ってみた話

RigはAIを使った開発を支援するワークベンチで、いろいろなことができるので便利だと思います。普通にAIとチャットしてコードを書かせることもできますが、Rigを使うと開発フローとして組み立てられるようになるので、そこが違うところだと思います。

Rigの動きは4段階になっていて、PARSE、RESOLVE、COMPOSE、RUNという順番で処理されます。PARSEは起動文字列をフラグと自由記述に分解するところで、RESOLVEはmanifestとrecipeとフラグとサイズ既定の順に設定を確定するところで、後の段が前の段を上書きします。COMPOSEはstepごとにpersonaやinstructionやpolicyを組み合わせてサブエージェント用のプロンプトを作るところで、RUNは実際に実行するところです。固定のワークフローではなくて毎回組み立てるという設計になっています。

recipeというのはstepの束で、stepというのは工程のことです。stepにはinstructionとかpatternとかpersonaとかpolicyとかoutput_contractとかを指定できます。recipeはproject、user、shippedの3つの階層から探されて、先に見つかったものが優先されます。なので、プロジェクト固有のrecipeを置くと同じ名前のものより優先されます。extendsを使うと継承もできます。

Rigで一番大事なのはacceptance-gateだと思います。AIの実行は毎回結果が変わってしまうのですが、acceptance-gateは受け入れ基準のリストを持っていて、その基準を満たすまで最大K回まで繰り返して収束させます。K回でも満たせなかったら人間にエスカレーションされます。基準というのは例えばbuildが成功するとかlintが0件とかレビューでREJECTがないとかで、recipeにacceptanceとして書きます。これによって、経路は毎回変わっても品質は同じところに収束するという考え方になっていて、determinism-by-gateと呼ばれています。

あとcontext-minimalというルールもあります。実装とかレビューとか調査とかの実作業は必ずサブエージェントに投げて、親はdispatchと集約とゲート判断だけをやります。親が長いdiffやログを読み込んでしまうとコンテキストが汚れてしまうので、それを避けるためです。サブエージェントにはoutput contractで決めたフォーマットで返させて、親は判定行だけ読みます。並列にできる観点は1メッセージで複数dispatchします。レビューはsecurityとdesignとtestの3観点を並列で回すのが基本です。

変更の規模によって重い工程を自動でオフにする仕組みもあります。既定では200行以下だとdesignとreviewとtddがオフになって、それを超えると推奨されるようになります。閾値はmanifestで変えられます。軽い変更を重く回さないための工夫だと思います。

使い方ですが、まず自然文でやりたいことを渡します。

```sh
rig-wb run bugfix
```

実行前に何をするか見たいときは、planを使うと構成を見せて止まります。

```sh
rig-wb plan bugfix --json
```

Claude Codeからだと `/rig:go` というコマンドで同じことができます。stepの一部だけ実行したいときは `--only` とか `--from` とか `--to` とか `--skip` が使えます。実装は隔離されたworktreeで行われるので、結果を見てからacceptかdiscardを選べます。複数のタスクを同時に走らせているときは board で全部の状態を見られます。

ということで、Rigは便利なツールだと思うので、興味がある人は使ってみるといいと思います。ただしAIが間違えることもあるので、最後は人間が確認したほうがいいです。
