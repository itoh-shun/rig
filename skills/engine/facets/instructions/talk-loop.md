# instruction: talk-loop

<NON-INTERACTIVE-STOP>
この instruction は**対話セッション専用**である。非対話の実行——`codex exec` / `claude -p` /
CI / `orchestrate.py` の provider 呼び出しなど、stdout を読んで答える人間がいない起動——と、
Task/Agent で特定タスクのために起動されたサブエージェントには**適用しない**。その場合は
以下の手順（とりわけ⑤の確認ガード）を実行せず、与えられたタスクに直行すること。答える相手が
いない場所で確認を求めると、run は何も行わないまま終わる。
</NON-INTERACTIVE-STOP>

話し言葉の発話を受け取り、意図を見極めて利用可能な rig コマンドや installed recipe へ橋渡しし、会話を継続する。talk は engine の**前段（自然言語→構造化された rig 起動）**と**会話の継続**だけを担う。実作業は委譲先と engine が行う。

## 手順（1ターン）

### ① 意図の見極め

発話が **(a) 雑談・質問** か **(b) rig アクション要求**（レビュー/実装/PR/マージ等）かを判定する。

- (a) なら `talk-assistant` の語り口で短く答え、⑥へ。
- (b) なら ② へ。
- **(c) どちらとも決められないなら、決めずに ⑤ へ進む**（「もう全部作り直して」のように、
  実装要求とも不満の吐露とも読める発話）。未決のまま ⑤ で実行意思を確かめ、
  回答で対象と意図が定まるまで起動文字列を作らない。定まったら (b) なら ② へ戻り、(a) なら ⑥ へ進む。

### ② 正規化

発話からフィラー（あー/えーと）・言い淀み・重複・口語崩れを落とし、要点（やりたいこと・対象・条件）を抽出する。
**依頼の解釈に関わる言葉は落とさない**——範囲を示す語（全部・とりあえず・もう）、実行意思の強さ、
緊急度は要点の一部である。「崩れた口語」と「解釈の手掛かり」を同じ層として捨てない。

### ③ ルーティング（動的列挙）

利用可能な `/rig:*` コマンドを**動的に列挙**し、各コマンドの description に照らして、発話の意図を最も合うドメインへ対応づける。

- 候補は固定で持たない。`commands/` 配下、現在のセッションで使える `/rig:*`、resolver が列挙する installed recipe を見て判断する。
- pack の command asset は install だけでホストの slash command に登録されるとは限らない。その場合は既存入口の `--recipe <installed-name>` として組み立てる。判別がつかなければ ⑤ で1問確認する。

### ④ 引数の抽出

対応づけたコマンド向けに、発話から flag / recipe / 対象を組み立てる。

- 例: 「今の変更だけレビューして」→ `/rig:dev --only review`。「installed recipe でこの資料を評価して」→ `/rig:dev --recipe <name> <パス>`。「まず構成だけ見せて」→ `--plan`。
- 対象（ファイル・Issue・入力資料）が発話に無ければ**捏造しない**。⑤ で訊く。

### ⑤ 解釈の確認（確認ガード）

確定した `/rig:*` 起動文字列を **1 行で表示**してから宣言/確認へ進む（#105）:

```
→ /rig:dev --only review
```

フォーマット: `→ ` プレフィックス＋モノスペース1行。リスクの高低・確認の有無に関わらず、**常に起動文字列を先に見せてから**宣言/確認する。意図・対象が曖昧で1問確認する場合は、回答で起動文字列が確定した**後に**表示してから実行する。

その後、実行内容を**一言で宣言**し、リスクに応じた確認ルール（以下の表）を適用する。

| アクション | 確認 |
|---|---|
| 情報取得・review・`--plan`・状態確認など低リスク | 「〜しますね」と宣言して即実行してよい |
| 書き込み・実装・push・merge・capture など影響あり | **必ず確認を取ってから実行**（「〜して push まで行きますが、いい?」） |
| 意図・対象が曖昧／確信度が低い | **1問だけ**訊いて確定させる（質問攻めにしない） |

**質問枠は会話全体で数える。** 一度確定した事項を訊き直さない。ユーザーが「質問は一度で済ませて」
のように質問回数を指定したら、その制約は以後のターンにも引き継ぐ——回答のたびに枠を復活させない。
制約が付いた場合は、対象・望む結果・許容範囲のうち**判断を左右する不足分だけ**を最初の一問にまとめる。

**訊けないまま必要事項が残ったら、範囲を狭めて止まる。** 未確定のまま変更を委譲しない。
確定済みの対象に対する情報取得・調査・レビューは委譲してよいが、**目的や採用方針は委譲先にも推測させない**。
差分から目的を復元したことにしない。

> **透明性の意義**：起動文字列を見せることで（1）意図と異なる実行を止める機会を確保し、（2）ユーザーが CLI 構文を自然に習得できる（native-first 精神）。`--plan` が「実行前に何をするか見せる」のと同じ透明性原則を talk の前段にも適用する。

### ⑥ 委譲と継続

- (b) の場合、確定した `/rig:*` 起動文字列を該当コマンド経由で通常 engine（PARSE→RESOLVE→COMPOSE→RUN）へ渡す。**talk は engine 規則（context-minimal 等）を再定義せず、委譲先にそのまま従わせる**。
- 実行後は結果を**短い話し言葉で報告**し、次の用件を受ける。長さの既定と、確認・正確さとの優先順位は `talk-assistant` が持つ（ここで文数を絶対規定にしない）。
- **報告は日本語で書く。** 成果物の言語と会話の言語は別物で、混同すると片方が他方に引きずられる——コード・コメント・コミットメッセージ・PR・Issue はリポジトリ規約どおり英語、ユーザーへの報告と確認は日本語。コード作業に深く入るほど英語の文脈が支配的になり、会話まで英語に流れる。それは委譲先の規約が正しく効いている証拠であって、会話の言語を変える理由にはならない。
- **委譲先の報告が不足していたら、報告のまま渡さず照会する。** 「全検査通過」の一行では成功を確定しない。
  検査名・対象の版・結果・根拠の参照先を委譲先へ照会する。**照合は報告した当人にさせない**——
  `policies/independent-verification`（採点者は生成者と別人）に従い、別の subagent へ dispatch するか、
  親が根拠の所在だけを有界に確認する。揃うまでは、取得できた証拠の範囲と出典を明示して報告する。
- 「もういい / exit / やめて」等で会話モードを終了する。

### ⑦ 要件すり合わせの構造化ログ（委譲先が workbench task を持つ場合・#292）

②〜⑤で「確定した要件」「確認した前提」「保留にした事項」が生じた場合（特に⑤で1問確認を挟んだとき）、委譲先が`workbench.py new`でtask-idを持つ時点で、それらを`.rig/runs/<task_id>/talk-log.md`として残す：

```markdown
## 決定事項
（②〜⑤で確定した要件・対象・flag）

## 確認した前提
（⑤で人に確認を取り、回答で確定した内容）

## 保留事項
（曖昧なまま残された事項。⑥で委譲先から取得できていない証拠——検査名・対象の版・根拠の所在のうち
欠けているもの——もここに書く。委譲後に判明する分は ⑥ の報告受領後に追記する。無ければ「なし」）
```

これは承認不要のログ（`diff.md`と同格・§6 run テレメトリ扱い）。後続のimplement/reviewが「なぜこの実装になったか」を`plan.md`/`diff.md`と合わせて追跡できるようにする——talk自体の役割（軽量な前段）は変えない。task-idがまだ無い（(a)雑談や`--plan`確認のみ等）場合はログを作らない。

## 原則

- talk 自身は重い処理を抱えない（長い diff・ログ・ファイル全文を会話 context に引き込まない）。重い処理は委譲先と engine が context-minimal で回す。
- engine（SKILL.md）と委譲先のフローは変更しない。talk は薄い前段である。
