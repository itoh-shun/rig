# instruction: write-tests-first

新規に足す振る舞いの **実行可能なテストを、実装より先に書く** routing。書き方の作法は persona（`implementer`）が持つのでここには再掲しない（Native-first）。テストケースの**設計**（7観点・ケース表）は担当外＝`test-design`、テストの**実行**も担当外＝`verify`。ここは「動くテストがツリーに残る」ことだけを担保する。

**スコープ**: 仕様・設計が固まった直後、実装の前。納品は**リポジトリに残るテストファイル**。

## `risk-based-testing` との関係

`policies/risk-based-testing` は「**既存コードのどこにテストを足すか**」を判断するための規律で、「テストがないから書く」を禁じている。この instruction はそれを覆さない。**いま追加しようとしている振る舞いそのもの**には、その振る舞いが仕様を満たすことを示すテストが要る、という別の話を扱う。周辺の既存コードへ手を広げるかどうかは、従来どおり `risk-based-testing` が決める。

実測でこの穴が見えている：新規 CLI を一から作らせた3ランで、rig の成果物にテストは1つも残らなかった。指示が「テストを実行せよ」としか言っておらず、実行する対象を誰も作らなかったため。

## 手順

1. **対象の確定** — 直前の設計で決めた振る舞いのうち、**外から観測できる単位**を列挙する。内部関数ではなく、入力→出力・終了コード・副作用の単位で切る。
2. **仕様に書いてある境界を先に拾う** — 仕様が明示している境界値・エラー条件・例外的な入力は、**全部ケースにする**。仕様が例を挙げている箇所（丸め、順序、書式）は、その例をそのままテストにする。
3. **書く** — プロジェクト既存のテスト規約（フレームワーク・命名・配置）に合わせる。既存が無ければ、その言語の標準的なものを選ぶ。**リポジトリに残るファイルとして書く**（手元で1回動かして消す、は不可）。
4. **この時点で落ちることを確認する** — 実装前なので落ちて当然。**落ちることを確認していないテストは、通ることも確認できていない**。実行できない環境ならその旨を残す（黙って「書いた」で済ませない）。
5. **実装へ渡す** — 何をカバーし、何を意図的にカバーしていないかを1行ずつ添える。

## ガード

- **テストを後回しにしない**。実装が先に完成すると、テストは実装の写経になる。
- **仕様の例をそのまま落とさない**。仕様が「0.25 → 0.3」と書いているなら、そのケースが要る。
- **通ることを目的にしない**。実装前に全部通るなら、そのテストは何も確かめていない。
- **カバーしていない範囲を隠さない**。「全部カバーした」と書かない。
- **設計に踏み込まない**（ケース表・7観点の網羅は `test-design`）。**実行と合否判定もしない**（`verify`）。
