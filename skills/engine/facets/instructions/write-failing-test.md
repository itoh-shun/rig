# instruction: write-failing-test

実装より先に、これから作る挙動を固定する**失敗するテスト**を書く（TDD の Red 段）。

`implement` の中でリスク評価の結果として TDD を選ぶ（`facets/instructions/implement` ①）のとは別で、こちらは
**基本フローの独立した step** である。目的は「TDD でやった」を自己申告でなく検証可能にすること——
テストは implement より前に存在し、その時点で**失敗していた**という証拠が残る。

## 手順

### ① 何を固定するかを決める

直前の step（feature なら `design`、bugfix なら `reproduce`/`plan`）で確定した AC・再現条件から、
**今回の変更で初めて通るようになるべき挙動**を1つ以上選ぶ。既存の挙動を書き写すのではない
（それは実装前から green になり、Red 段の意味がない）。

対象の選び方：

| 種類 | 固定するもの |
|---|---|
| feature | AC の中で最も本質的な入出力・境界条件。UI 微修正なら「表示される値」まで降ろす |
| bugfix | 再現条件そのもの。修正前に失敗し、修正後に通る回帰テスト1本 |

### ② テストを書く

プロジェクト既存のテスト規約（配置・命名・アサーション様式）に合わせる。新しいテスト基盤を
持ち込まない。1 step で書くのは**今回の変更に直結する分だけ**（`no_unrelated_diff` を守る）。

### ③ 失敗を確認して記録する

書いたテストを実行し、**失敗することを確認する**。この出力（テスト名と失敗理由の要点）を記録し、
`acceptance` step の `test_written_before_implementation_or_explained` の根拠として渡す。

- **期待どおり失敗した** → Red 確定。`implement` へ進む。
- **書いた直後に通ってしまった** → 固定対象が既存挙動になっている。①へ戻って対象を選び直す。
  それでも通るなら「変更が既に満たされている」ということなので、タスクのスコープ自体を intake へ差し戻す。
- **テスト基盤ごと落ちる**（収集エラー・環境不足） → 失敗の質が違う。テストが「アサーションで」
  失敗している状態まで持っていく。

### ④ テストを先に書けない場合（escape hatch）

先にテストを書くのが構造的に無理・無意味な変更はある。その場合は**テストを書かずに進んでよい**が、
理由を記録して `test_written_before_implementation_or_explained` を `warning` にする（`failed` ではない）。
黙って飛ばさない——判断が run log に残ることが条件。

先に書けないと認めてよい典型：

- ドキュメント・コメント・設定値のみの変更（実行される挙動が無い）
- 外部サービスの応答形状が実際に叩くまで確定しない探索的な実装
- テスト基盤自体の新設・移行（テストを書く土台がまだ無い）

「面倒」「急いでいる」は理由にならない。`--no-tdd` を明示すればこの step 自体が外れる（§3 flag）ので、
省きたい場合は gate で誤魔化さずフラグで意図を宣言する。

## 引き継ぎ

`implement` へ渡すもの：書いたテストのファイル・テスト名、失敗時の出力の要点、Red が確認できたか。
`implement` はこのテストを **green にする最小実装**を書く（`facets/instructions/implement` ③ の Green/Refactor に接続）。
