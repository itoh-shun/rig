# knowledge: quality-operating-system

**組織で AI 開発の品質を担保する**ときの観点カタログ（事実）。判断は `personas/governance-auditor` が持つ。ここは「個人向けの品質ハーネスを組織に載せると何が壊れるか・何を一級概念にすれば直るか」だけを並べる。`knowledge/harness-taxonomy`（自分のハーネスの健全性）が **1リポジトリの中**を見るのに対し、こちらは **リポジトリの上の層**（org / team / project）を見る。

## 個人ハーネスを組織に載せた瞬間に壊れる4つ

rig v1 の資産（acceptance-gate・isolated worktree・独立検証・force-proof accept）は**1人1リポジトリでは完成している**。壊れるのは、同じものをチーム A・B・C に配ったときだけ起きる次の4つ。

1. **基準が同期しない（policy drift）**。`.rig/gates.json` はリポジトリごとに独立なので、A が足した基準は B に届かない。「うちは共通ポリシーでやっています」が**主張**のままで、**測定**になっていない。
2. **権限が二値しかない**。「accept してよい人の名簿」は権限が1個のRBAC。force・承認・例外発行・ポリシー改定を**別々に**渡せないので、実務では「全員に渡す」か「1人に集中させる」の二択になる。
3. **承認が記録でなく会話**。「誰かがレビューした」は事後に検証できない。誰が・いつ・どのコミットに対して・どの資格で承認したかが残らないと、承認フローは**ゴム印**と区別がつかない。
4. **監査ログが編集できる**。追記型 JSONL はエディタで消せる。1人の作業メモとしては十分だが、「Q3 の override を全部見せて」への**証拠**にはならない。

## 一級概念にすると直る（v2 の6概念）

| 概念 | 何を解決するか | 決定的な性質 |
|---|---|---|
| **policy**（共通ポリシー） | 基準の同期 | **単調強化**＝下位層は上位層を**締めることしかできない**。緩めようとしたら層とフィールドを名指してエラー |
| **permission**（権限管理） | 二値RBACの限界 | 権限語彙を固定し、role→permission→actor で解決。**拒否は必ず「誰が持っているか」まで説明する** |
| **approval**（承認フロー） | 会話の非検証性 | quorum・資格ロール・**職務分離**（著者の承認は数えない）・**鮮度**（承認したコミットが動いたら失効） |
| **waiver**（例外） | force の無記名性 | 名前・理由・**期限**つき。恒久例外は「弱いポリシー」であって例外ではない＝ポリシーに書け |
| **ledger**（監査） | ログの可編集性 | ハッシュ連鎖＋署名。**編集・削除・並べ替え・偽造追記のすべてが検出される** |
| **conformance**（ガバナンス可視化） | 主張と実態の乖離 | ポリシーに対して**実測**し、チーム横断でロールアップする |

## 設計の原則（rig の既存思想の延長線上にあること）

- **加算のみ（additive-only）**。`.rig/gates.json` が組み込み基準を削除・緩和するキーを拒否するのと**同じ規律**を、層をまたいでも保つ。上位が床、下位は床の上にしか建てられない。「削除キーが無い」だけでなく「省略しても継承する」の両方で閉じる（片方だけだと省略で抜ける）。
- **既定で不活性（inert by default）**。`.rig/org.json` が無ければガバナンス層は何もしない。**個人開発者がガバナンスの税を払わない**こと＝v1 との互換契約そのもの。ガバナンスは「チームが入れるもの」であって「インストールしたら付いてくるもの」ではない。
- **チョークポイントを増やさない**。accept は v1 の時点で唯一の関門だった。v2 は**2つ目の関門を作らず**、その1つを governed にする。関門が2つあるハーネスは、片方だけ通る抜け道が必ず生まれる。
- **壊れた設定は fail-closed**。v1 の `.rig/access.json` は壊れていたら「無制限」に落ちた（1人なら安全側）。ポリシー層は逆に**止める**。カンマ1個で組織の規則が静かに消えるのが、この層で唯一許されない失敗。
- **拒否は次の一手まで書く**。「権限がありません」で終わるシステムは迂回される。「あなたは developer、この権限は quality-owner が持っている、頼むコマンドはこれ」まで出す。

## 測るときに効く指標（conformance が出すもの）

- **force 率**（override された accept / 全 accept）。**この層で最も情報量が多い1数字**。ゲートが「満たされている」のか「回避されている」のかを一撃で分ける。25% を超えたらゲートは機能していない。
- **ポリシー到達率**（org 層が届いているリポジトリ / 全リポジトリ）。届いていないリポジトリは、良し悪し以前に**比較対象が無い**。
- **必須基準の実装率**（ポリシーが要求した criterion を実際に持って accept された run の割合）。要求と実行の差はここに出る。
- **例外の滞留**（live waiver 数と最古の発行日）。恒久化した例外はポリシーの改定サイン。
- **台帳の完全性**（連鎖検証の可否）。これが落ちている組織では、上の4指標はすべて信用できない。

## よくある誤り

- **ロールを増やして解決しようとする**。権限は語彙が固定されているから比較できる。ロールを増やすのは正しいが、**権限語彙を増やすのは最後の手段**。
- **承認の quorum を上げて品質を買おうとする**。quorum 3 は「3人が同じ画面をスクロールした」以上を意味しない。効くのは quorum ではなく**職務分離と鮮度**（著者を数えない・ブランチが動いたら失効）。
- **監査を「ログを取ること」だと思う**。取ることではなく**消せないこと**が監査。追記だけなら v1 でもやっていた。
- **ガバナンスをゲートの代わりにする**。承認は acceptance-gate の**代替ではなく上乗せ**。人間の承認で機械の検証を置き換えたら、`determinism-by-gate` を捨てたことになる。
