`asyncio.gather` と `asyncio.wait` は「複数の非同期処理を待つ」点は同じですが、**戻り値の形・例外の扱い・部分的な待ち方**が根本的に違います。

## 1. 戻り値の形

**gather**: 結果の**リスト**を、渡した順序どおりに返す。

```python
r1, r2, r3 = await asyncio.gather(f(1), f(2), f(3))
# 完了した順ではなく、引数の順に並ぶ
```

**wait**: `(done, pending)` という**2つの set** を返す。結果は自分で取り出す。

```python
tasks = [asyncio.create_task(f(i)) for i in range(3)]
done, pending = await asyncio.wait(tasks)
for t in done:
    print(t.result())   # setなので順序は保証されない
```

順序を保ちたければ、自分で `task -> 元の入力` の対応を持つ必要があります。

## 2. 例外の扱い（ここが一番の違い）

**gather** はデフォルト（`return_exceptions=False`）で、**最初の例外を呼び出し側に即座に送出**します。

```python
await asyncio.gather(ok(), fails(), slow())   # fails() の例外がここで raise される
```

重要な落とし穴として、**このとき残りのタスクはキャンセルされず、裏で走り続けます**。誰も結果を回収しないまま終わると `Task exception was never retrieved` の警告が出ることがあります。

`return_exceptions=True` にすると、例外は送出されず結果リストの要素として返ります。

```python
results = await asyncio.gather(*aws, return_exceptions=True)
# [値, ValueError(...), 値] のように混在する → isinstance で判定が必要
```

**wait** は**例外を一切送出しません**。失敗したタスクも「完了した」として `done` に入るだけで、`t.result()` を呼んだ時点で初めて例外が出ます。つまりエラー検知は完全に自分の責任です。

## 3. 部分的に待つ（wait の存在意義）

`wait` には `timeout` と `return_when` があります。

```python
done, pending = await asyncio.wait(
    tasks,
    timeout=5,
    return_when=asyncio.FIRST_COMPLETED,   # 他に FIRST_EXCEPTION / ALL_COMPLETED
)
```

- 「どれか1つ終わったら先に進む」「5秒だけ待って、残りは後で見る」といった制御ができる
- **timeout しても pending のタスクはキャンセルされません**。放置せず自分で `cancel()` するのが定石です

```python
for t in pending:
    t.cancel()
await asyncio.gather(*pending, return_exceptions=True)  # キャンセル完了まで待つ
```

`gather` にタイムアウトはありません。全体に時間制限をかけたい場合は `asyncio.timeout()`（3.11+）や `asyncio.wait_for()` で囲みます。`gather` 全体をキャンセルすると、配下の未完了タスクはすべてキャンセルされます。

## 4. 渡せるもの

- **gather**: コルーチンをそのまま渡せる（内部で自動的に Task にラップされる）
- **wait**: **Task / Future のみ**。Python 3.11 でコルーチンの直渡しは禁止され、`TypeError` になります（3.8 から非推奨でした）。必ず `create_task()` 経由で渡してください

また、空を渡したときの挙動も違います。`gather()` は空リストを即返しますが、`wait(set())` は `ValueError` を投げます。

## 使い分けの指針

| 用途 | 選ぶもの |
|---|---|
| 全部の結果が順序付きで欲しい | `gather` |
| 1つ失敗したら全体を中断したい | **`asyncio.TaskGroup`**（3.11+） |
| 先に終わったものから処理したい | `asyncio.as_completed` |
| 「どれか1つ」「N秒だけ」など細かい制御 | `wait` |

補足として、Python 3.11 以降の新規コードでは `gather` よりも **`asyncio.TaskGroup` が推奨**です。`gather` と違い、いずれかが失敗した時点で兄弟タスクを確実にキャンセルし、`ExceptionGroup` としてまとめて送出してくれるため、孤児タスクが残りません。

```python
async with asyncio.TaskGroup() as tg:
    t1 = tg.create_task(f(1))
    t2 = tg.create_task(f(2))
# ブロックを抜けた時点で全部完了。結果は t1.result() で取る
```

ざっくり言えば、**`gather` は「全部まとめて、結果を順番に」、`wait` は「待ち方を自分で制御する低レベルAPI」**です。`wait` は便利さより柔軟性を取ったAPIなので、エラー処理とキャンセルを自分で書く覚悟がないときは `gather` か `TaskGroup` を使うのが安全です。

| 引数の渡し方 | 可変長引数 `gather(a, b, c)` | イテラブル1つ `wait({t1, t2})` |
| コルーチンを直接渡せるか | 可（自動で Task 化） | **不可**（3.11 で禁止。Task/Future のみ） |
| 戻り値 | 結果の**リスト**（引数と同じ順序） | `(done, pending)` の**集合タプル** |
| 結果の取り出し | そのまま使える | 自分で `task.result()` を呼ぶ |
| 例外 | デフォルトで**そのまま送出** | **送出されない**（Task 内に保持される） |
| タイムアウト | なし | `timeout=` あり |
| 部分完了で戻る | 不可（全完了まで待つ） | `return_when=` で制御可 |

## 例外の扱いが最大の差

```python
# gather: 最初の例外がそのまま呼び出し側に飛ぶ
try:
    results = await asyncio.gather(a(), b(), c())
except ValueError:
    ...  # どのタスクの例外かは分からない

# gather: 例外も「結果」として受け取る
results = await asyncio.gather(a(), b(), c(), return_exceptions=True)
# -> [1, ValueError(...), 3]  順序は保証される

# wait: 例外は送出されない。自分で掘り出す
done, pending = await asyncio.wait(tasks)
for t in done:
    if t.exception():   # ここで確認しないと例外を握りつぶす
        ...
```

`wait` は例外を投げないので、`done` の各 Task を検査し忘れると「Task exception was never retrieved」の警告だけ出て静かに消えます。

## よくある落とし穴

**1. `gather` は例外時に残りをキャンセルしない**

`return_exceptions=False`（デフォルト）で1つが失敗すると、その例外はすぐ上がりますが、**他のタスクはバックグラウンドで走り続けます**。「全部止まった」と思い込むとリソースリークになります。

**2. `wait` のタイムアウトはタスクをキャンセルしない**

```python
done, pending = await asyncio.wait(tasks, timeout=5)
for t in pending:
    t.cancel()          # 自分で後始末が必要
```

**3. `wait` は順序を保存しない**

`done` / `pending` は `set` です。入力順に結果を並べたいなら `gather` を使うか、Task と入力の対応を辞書で持つ必要があります。

## 使い分け

- **全部の結果が順序付きで欲しい** → `gather`
- **どれか1つ終わったら先に進みたい** → `wait(..., return_when=FIRST_COMPLETED)`
- **タイムアウト付きで一部だけ回収したい** → `wait(..., timeout=...)`
- **終わった順に逐次処理したい** → `wait` ではなく `asyncio.as_completed`

## 補足：Python 3.11 以降なら `TaskGroup`

新規コードでは `gather` より `asyncio.TaskGroup` が推奨されます。構造化並行性により、**どれか1つが失敗したら残りを自動でキャンセル**し、まとめて `ExceptionGroup` として送出するため、上の落とし穴1が原理的に起きません。

```python
async with asyncio.TaskGroup() as tg:
    t1 = tg.create_task(a())
    t2 = tg.create_task(b())
# ブロックを抜けた時点で全完了。結果は t1.result() で取得
```

タイムアウトも `async with asyncio.timeout(5):` と組み合わせれば `wait` の `timeout=` より安全に書けます。`gather` / `wait` は既存コードの読解や、`return_exceptions=True` で「失敗しても続行」が欲しい場面で使う、という位置づけになってきています。

`git rebase --onto <newbase> <upstream> <branch>` の3つです。

| 引数 | 意味 |
|---|---|
| `<newbase>` | **移植先**。取り出したコミット群をこの上に積み直す |
| `<upstream>` | **切り取りの起点（除外側）**。ここまでのコミットは移植しない |
| `<branch>` | **切り取りの終点**。ここまでのコミットを移植し、最後にこのブランチが移植先を指す |

## 動く範囲

移植されるのは `<upstream>..<branch>`、つまり「branch から辿れるが upstream からは辿れない」コミットです。`<upstream>` 自身は**含まれません**（除外境界）。

```
      A---B---C  topic      ← branch = topic
     /
D---E---F---G  main
    ↑
  upstream に E を指定すると A,B,C が対象
```

ここで `git rebase --onto main E topic` とすると:

```
              A'--B'--C'  topic
             /
D---E---F---G  main        ← newbase
```

## 補足

- `<branch>` を省略すると現在のブランチが使われます（`git rebase --onto main E` = 今いるブランチが対象）
- `<newbase>` と `<upstream>` に同じものを指定すると、通常の `git rebase <upstream>` と同じ動きになります
- 3つとも「コミットを指せるもの」なら何でも可 — ブランチ名、タグ、SHA、`HEAD~3` などの相対指定

要するに **「どこからどこまでを（upstream..branch）、どこへ移すか（newbase）」** を明示するための形です。通常の `git rebase` は移植先と除外境界が同じになってしまうので、それを分離したいときに `--onto` を使います。

## それぞれの意味

| 引数 | 意味 |
|---|---|
| `<newbase>` | **移植先**。コミット列を新しく載せる土台。 |
| `<upstream>` | **移植しないコミットの終端**。ここより後（`<upstream>` に含まれないコミット）だけが移植対象。 |
| `<branch>` | **移植するコミット列の先端**。省略すると現在のブランチ。 |

移植されるコミットの範囲は `<upstream>..<branch>` です。つまり「`<branch>` から到達できるが `<upstream>` からは到達できない」コミットが、`<newbase>` の上に順に付け替えられます。完了後は `<branch>` が新しい列の先端を指すよう移動します（`<branch>` を指定した場合はそのブランチがチェックアウトされます）。

## 例

```
A---B---C          main
     \
      D---E        feature-1
           \
            F---G  feature-2
```

`git rebase --onto main feature-1 feature-2` とすると:

- `newbase` = `main` → `C` の上に載せる
- `upstream` = `feature-1` → `E` までは移植しない（`D`, `E` を除外）
- `branch` = `feature-2` → 先端は `G`

移植されるのは `feature-1..feature-2` = `F`, `G` の2つで、結果はこうなります:

```
A---B---C---F'---G'   feature-2
     \
      D---E           feature-1
```

## よく使うパターン

- **親ブランチを切り替える**: 上の例のとおり、間違った土台から切ってしまったブランチを付け替える。
- **コミットを捨てる**: `git rebase --onto HEAD~3 HEAD~2` で、`HEAD~2` のコミット1つだけを履歴から落とす（`newbase` と `upstream` の間のコミットが消える）。

引数2つの通常の `git rebase <upstream>` は `--onto <upstream> <upstream>` と同じ、つまり「移植先」と「除外の基準」が同一である特殊形、と考えると覚えやすいです。`--onto` はこの2つを分離できるのが本質です。
