`asyncio.gather` と `asyncio.wait` は「複数の待機可能オブジェクトをまとめて待つ」点は同じですが、**返すもの・例外の扱い・キャンセルの責任**が別物です。

## 一言でいうと

- **gather**: 結果の**リスト**が欲しいとき。引数の順序で値が返り、例外はその場で送出される。
- **wait**: **タスクの集合**（done / pending）が欲しいとき。タイムアウトや「最初の1つが終わったら」といった制御が主目的で、結果の取り出しは自分でやる。

## 比較

| | `gather` | `wait` |
|---|---|---|
| 引数の渡し方 | 可変長 `gather(a, b, c)` | イテラブル `wait({t1, t2})` |
| コルーチンを直接渡せるか | ○（自動で Task 化） | **×**（Python 3.11 で禁止・`TypeError`。3.8 で非推奨化）。`asyncio.create_task()` で包む必要あり |
| 戻り値 | 結果の **list**（引数と同じ順序） | `(done, pending)` の **2つの set**（順序なし、中身は Task 本体） |
| 結果の取り出し | そのまま値 | `task.result()` / `task.exception()` を自分で呼ぶ |
| 例外 | `return_exceptions=False`（既定）なら**即座に送出**。`True` なら例外オブジェクトが結果リストに混ざる | **送出しない**。例外は Task の中に保持されたまま |
| `timeout` | なし（`asyncio.timeout` / `wait_for` と組み合わせる） | あり |
| 途中で打ち切る条件 | なし（全完了まで） | `return_when=FIRST_COMPLETED` / `FIRST_EXCEPTION` / `ALL_COMPLETED` |
| 打ち切り時の残りタスク | — | **キャンセルされない**。自分で `.cancel()` する責任がある |

## 落とし穴になりやすい2点

**1. gather は例外時に兄弟タスクをキャンセルしない**

`return_exceptions=False` で1つが失敗すると、`gather` の呼び出し側には直ちに例外が飛びますが、**他のタスクは裏で走り続けます**。放置すると "Task exception was never retrieved" 警告や、やりかけの処理が残ります。
（逆に、`gather` が返す future 自体をキャンセルした場合は、未完了の子タスクすべてがキャンセルされます。）

**2. wait はタイムアウトしても pending を片付けてくれない**

```python
tasks = [asyncio.create_task(f()) for f in funcs]
done, pending = await asyncio.wait(tasks, timeout=5)
for t in pending:
    t.cancel()                      # ← これを忘れるとリークする
for t in done:
    if exc := t.exception():        # ← wait は例外を投げないので自分で確認
        log.error("failed: %r", exc)
    else:
        use(t.result())
```

## 使い分けの指針

- **全部の結果を順番どおりに欲しい** → `gather`
- **タイムアウト付き / 最初の1件だけ欲しい / 完了と未完了を区別したい** → `wait`
- **完了した順に逐次処理したい** → `asyncio.as_completed`
- **Python 3.11+ で新規に書くなら** → `asyncio.TaskGroup` を第一候補に。1つ失敗すれば兄弟を自動でキャンセルし、`ExceptionGroup` でまとめて上げてくれるので、gather の落とし穴1がそもそも起きません。

```python
async with asyncio.TaskGroup() as tg:      # 3.11+
    t1 = tg.create_task(fetch(url1))
    t2 = tg.create_task(fetch(url2))
# ブロックを抜けた時点で両方完了。どちらか失敗なら他方はキャンセル済み
r1, r2 = t1.result(), t2.result()
```

`gather` が不要になったわけではなく、「結果をリストで受けたいだけ」の素直なケースでは今も最短で読みやすい選択です。

`asyncio.gather` と `asyncio.wait` は「複数の待機可能オブジェクトを並行実行する」点は同じですが、**用途が違います**。gather は「全部の結果がほしい」、wait は「完了状況を観測したい」ためのものです。

## 一覧

| | `gather` | `wait` |
|---|---|---|
| 引数 | 可変長 `*aws`（コルーチン可） | イテラブル1つ。**3.11+ はコルーチン不可**（Task/Future のみ） |
| 戻り値 | 結果の**リスト（渡した順）** | `(done, pending)` の **set**（順不同、中身は Task） |
| 例外 | 既定で**呼び出し元に即伝播** | **伝播しない**。`task.result()` で初めて上がる |
| timeout | なし | あり（時間切れでも `TimeoutError` は上げない） |
| 部分待ち | 不可（常に全件） | `return_when=FIRST_COMPLETED` などで可 |
| キャンセル伝播 | gather をキャンセル → **子も全部キャンセル** | wait をキャンセルしても**子は生き残る** |

## 1. 戻り値の形

```python
results = await asyncio.gather(f(1), f(2), f(3))
# [r1, r2, r3] — 完了順ではなく引数順。インデックスで対応づけできる

done, pending = await asyncio.wait({t1, t2, t3})
# set なので順序なし。値は自分で取り出す:
for t in done:
    t.result()   # ここで例外が上がりうる
```

対応関係を保ちたいなら gather、どのタスクが終わったかを見たいなら wait です。

## 2. 例外の扱い（一番の落とし穴）

`gather` は既定（`return_exceptions=False`）で**最初の例外をその場で送出**しますが、**残りのタスクはキャンセルされず走り続けます**。孤児タスクになり "Task exception was never retrieved" 警告の原因になりがちです。

```python
await asyncio.gather(a(), b(), c())              # b が失敗 → 即 raise、a と c は継続
await asyncio.gather(a(), b(), c(), return_exceptions=True)
# → [r_a, Exception インスタンス, r_c] 全件待つ。呼び出し側で isinstance 判定が必要
```

`wait` は例外を一切送出しません。失敗タスクも単に `done` に入るだけなので、`result()` を呼び忘れると**エラーが黙って消えます**。

## 3. タイムアウト

`gather` に `timeout` はありません。`asyncio.timeout`（3.11+）や `wait_for` と組み合わせます。

```python
async with asyncio.timeout(5):
    await asyncio.gather(*tasks)   # 時間切れで全タスクがキャンセルされる
```

`wait` の `timeout` は**タスクをキャンセルしません**。未完了は `pending` に返ってくるだけなので、自分で後始末が要ります。

```python
done, pending = await asyncio.wait(tasks, timeout=5)
for t in pending:
    t.cancel()
```

## 4. 部分的な待機

`wait` だけができることです。

```python
done, pending = await asyncio.wait(tasks, return_when=asyncio.FIRST_COMPLETED)
```

「最初の1つが返ったら他は捨てる」（速い方を採用するレース）や、`FIRST_EXCEPTION` で早期中断したいときに使います。

## 5. 3.11 以降の変更点

`asyncio.wait` にコルーチンを直接渡すのは 3.8 で非推奨、**3.11 で `TypeError`** になりました。明示的にラップしてください。

```python
tasks = [asyncio.create_task(f(i)) for i in range(3)]
```

`git rebase --onto <newbase> <upstream> [<branch>]` の3つです。

## それぞれの意味

**1. `<newbase>` — 移植先**
コミット列を新たに接ぎ木する先。ここの上に、選ばれたコミットが積み直されます。

**2. `<upstream>` — 「ここまでは要らない」の境界**
移植するコミットの**範囲の下限**を決めます。正確には `<upstream>..<branch>` の範囲、つまり「`<branch>` から辿れて、かつ `<upstream>` から辿れないコミット」だけが移植対象。`<upstream>` 自身とその祖先は移植されません。

**3. `<branch>` — 移植するコミット列の先端（省略可）**
範囲の**上限**。省略すると現在の HEAD が使われます。明示した場合は、最初に `git checkout <branch>` したのと同じ挙動になり、処理後はそのブランチが新しい位置を指します。
