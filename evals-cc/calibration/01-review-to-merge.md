## レビュー観点のレーン（ここが本題ですよね）

**既定の4本** — security / design / test / behavioral-correctness（状態遷移・非同期・単位と意味・境界値）

**変更内容に応じて足す** — performance / observability（失敗が見えるか・切り戻せるか）/ docs（diff が嘘にした記述）/ api-compat（破壊的変更・semver）/ migration（戻り道・ロック時間）

**敵対レビュー（`--adversarial`）** — lazy-senior（消せるコード・稼いでいないコメント・将来の負債）/ cognitive-economist（命名・素直に読めるか・局所性）

観点の抜けが怖いとのことなので、**追加レンズは変更の中身を見てから提案します**（マイグレーションが無いのに migration レーンを回しても票が薄くなるだけなので）。さらに `rig:drill` を使えば「どのレビュアーが実際に何を捕まえたか」を検出率として数値で出せます — 観点の網羅を主観でなく数字で確認したい場合はこちらです。

## 手順

**1. レビュー対象の確定**
どの差分を見るかを最初に固定します（`main...feature-x` なのか、特定コミットなのか、作業ツリーの未コミット分なのか）。ここが曖昧なまま進むと、後で「その変更は見てなかった」が起きます。合わせて、変更の意図・非スコープ（今回あえて直さない部分）も一言もらえると、指摘のノイズが減ります。

**2. 観点の明示（抜け対策の本体）**
レビュー前に観点表を出して、今回どこを重点的に見るかを合意します。デフォルトの観点は:

- 正確性: 境界値、null/空、オフバイワン、エラー処理と復旧、例外の握り潰し
- 状態と並行性: 競合、再入、部分的失敗時の一貫性、冪等性
- 互換性: API/スキーマ/設定の破壊的変更、マイグレーション、ロールバック可否
- テスト: 新規パスがテストされているか、失敗系があるか、テストが実装をなぞってるだけでないか
- セキュリティ: 入力検証、認可の抜け、機微情報のログ出力、インジェクション
- 設計・可読性: 既存ユーティリティの再利用、重複、抽象度のズレ、命名
- 運用: ログ/メトリクス、性能上のホットパス、外部呼び出しのタイムアウト・リトライ

**3. 自動レビューの実行**
`/code-review`（effort は high 推奨、広めに拾う）で差分をレビュー。変更が認証・入力処理・外部通信に触れるなら `/security-review` も別途かけます。両者は目的が違うので重ねる価値があります。

**4. 指摘のトリアージ**
出てきた指摘を「マージブロッカー / 今回直す / 別チケット」に仕分けして提示します。自動レビューは誤検知も出すので、私の方で根拠を確認してから分類し、判断が割れそうなものは理由付きで並べます。採否はそちらで決めてください。

**5. 修正と再確認**
合意した分を修正し、変更箇所に対して再レビュー。修正で新しく壊れていないかを差分ベースで確認します。

**6. 検証**
テスト・リント・ビルド・型チェックを実行して結果を確認。ここは実行環境が必要なので、コマンドを提示するか、Bash 許可があればこちらで回して結果をそのまま報告します。落ちたら落ちたと出します。

**7. PR 整備**
PR タイトル・説明（背景 / 変更内容 / 検証方法 / レビューで見てほしい点）を作成。人間レビュアーが迷いやすい箇所には、こちらから先にコメントを置いておくと往復が減ります。

**8. マージ**
CI グリーン・必要な承認を確認してからマージ。マージ方式（squash / merge commit）とブランチ削除、マージ後の確認事項（デプロイ、マイグレーション実行など）を事前に決めておきます。**マージは戻しにくい操作なので、実行前に必ず確認を取ります。**

### この組み方の意図（あなたの不安に対する答え）

1. **並列ファンアウト**で観点を分担させます。1人のレビュアーに全部見させると必ず抜けるので、観点ごとに独立した subagent を立てて構造的に埋める。
2. **追加レンズは「足りるか」でなく「対象に該当するか」で選ぶ**。API を触っていれば api-compat、移行があれば migration、という足し方です。該当しないレンズを足すと指摘の質が薄まります。
3. **`--verify-findings` を入れています。** レビュアーを増やすと偽陽性も増えるので、REJECT の根拠を反証役（finding-verifier）に1件ずつ潰させ、生き残った指摘だけをゲートに通します。増やす副作用への手当てです。
4. **push/PR より前にレビューが来ます**（pr-hygiene）。マージは全ゲート通過後の最後の step です。

## 進め方

**1. レビュー対象の確定**
未コミットの差分 / ブランチ / PR番号 のどれを見るかを決めます。ここが曖昧なまま走ると「見たつもりで見ていない差分」が出るので最初に固定します。

**2. 自己レビューの下ごしらえ**
差分を通読して、変更の意図とコードが一致しているか、意図せず混入したファイルがないかを確認。ここでノイズ（デバッグ出力、コメントアウト、無関係な整形）を落としておくと、以降の指摘が本質的なものだけになります。

**3. 観点別のレビュー（ここが抜け対策の本体）**
この環境には観点の異なるレビューが3つ用意されているので、重ねがけします。

| 観点 | 手段 | 見るもの |
|---|---|---|
| 正しさ・バグ | `/code-review` | ロジック誤り、境界条件、エラー処理、既存コードとの整合 |
| セキュリティ | `/security-review` | 入力検証、認証・認可、機密情報の漏れ、危険なAPI利用 |
| 品質・重複 | `/simplify` | 再利用漏れ、冗長さ、非効率、抽象度のズレ |

`/code-review` は effort を low〜max で指定できます。抜けが怖いということなので **high** を推奨します（指摘数は増え、確度の低いものも混じりますが、取捨は一緒に判断できます）。`--comment` でPRインラインコメント化、`--fix` で作業ツリーに直接適用も可能です。

**4. 指摘のトリアージ**
出てきた指摘を「直す / 今回は見送る（理由付き） / 誤検知」に仕分けます。全部直すのが正解とは限らないので、ここは判断を並べて確認します。

**5. 修正とテスト**
直すと決めたものを反映し、テストを実行。テストが通らなければその出力ごと報告します。

**6. マージまで**
コミット整理 → プッシュ → PR作成/更新 → CI確認 → マージ。PR作成やマージは外向きの操作なので、実行前に必ず確認を取ります。
