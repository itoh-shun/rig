# rig を claude plugin eval で測った結果（2026-09-16）

## 結論

**出荷時の SessionStart フックは、説明だけを求める依頼にも rig を起動していた。**
文面を直した結果、作業依頼の発火は 6/6、説明依頼の過剰発火は 0/2 になった。
修正は同じブランチ系列の hook PR に入っている。

| フック文面 | 作業依頼で発火 | 説明依頼で過剰発火 |
|---|:-:|:-:|
| 出荷時（全ターンを rig:talk に通せ） | 5 / 5 | **2 / 2** |
| フック除去 | **0 / 5** | 0 / 2 |
| 初版の絞り込み | 5 / 6 | 0 / 2 |
| **修正版（作業を名指しするターンを通す）** | **6 / 6** | **0 / 2** |

この表の数字はすべて `tool_used` grader によるもので、judge モデルを通らない。
llm grader の Δ は runs: 1 で 0.33 程度揺れ、比較には使えなかった（§3）。
以下の §1〜§5 は、修正に至るまでの経緯と各段階の根拠である。


スイート: `evals-cc/`（fire 5 / no-fire 2 / probe 1）。judge は sonnet。
実行は4回、いずれも Claude Max サブスクリプションの枠内（追加課金なし）。

## 1. 確かなこと — 機械測定、judge を通さない

`hooks/hooks.json` の SessionStart から `inject-talk-mode.sh` を外した1ファイルだけが
違う2本のブランチで、同じスイートを走らせた。

| | A: 出荷形態 | B: フック除去 |
|---|:-:|:-:|
| fire 5件で rig の skill が発火 | **5 / 5** | **0 / 5** |
| negative 2件で過剰発火 | **2 / 2** | **0 / 2** |
| probe（命令形）で発火 | 未測定 | **0 / 1** |
| with-arm の turn 数（01 / 03 / 05） | 16 / 9 / 7 | 3 / 3 / 3 |

`fires-engine` と `no-rig-fires` は `tool_used` grader であり judge を通らない。
この反転は採点のブレではない。

**出荷形態で routing しているのはフックである。** A 側のトレースに残った引数が
その指紋を持つ。

    {"skill": "rig:go", "args": "talk: git rebase --onto の3引数の意味を知りたい（説明のみ、操作不要）"}

`talk:` はフック文面の語彙で、依頼文には無い。

対照群でも rig の skill 43件はすべてモデルに提示されていた（トレースで確認済み）。
見えていて呼ばれなかったのであって、ハーネスの取りこぼしではない。

## 2. 残る交絡 — ここを読み違えないこと

**8ケースすべてで sandbox の作業ディレクトリが空だった。** 対象コードが存在しない。

probe 08 の応答は「コードが見つからないので直せません」で終わっており、
どう進めるかを決める段階に到達していない。**空のディレクトリを相手に
オーケストレーションを始めないのは、ルータとして正しい判断でありうる。**

したがって「description は routing しない」は、**この条件下では**としか言えない。
確定させるには実際のコードを持つケースが要る（`context.add_dirs` か scaffold。
どちらも `prompt.md` では書けず `case.yaml` 形式になる）。

ただし**どちらの読みでも変わらない事実**がある。出荷形態では、
発火はフックが起こしている。そしてフックは説明だけを求める依頼にも発火する。

## 3. 雑音 — 信用してはいけない層

**runs: 1 の judged Δ は 0.33 程度動く。** 証拠は 02 の without-arm——
プラグインを読み込まない側なので2実行で条件は同一なのに、0.00 と 0.33 が出た。
meanDelta 0.00 → +0.048 の変化はこの雑音の内側にある。

## 4. 副産物として出た所見

- **02 で skill は発火した後、ハーネスが迂回された。** 応答は直接的な技術助言で、
  隔離・ゲート・fan-out は末尾の「rig でちゃんと回しますか？」という条件付きの
  申し出にしか出てこない。SKILL.md §9 が red flag として名指ししている形。
- **ゲートの不合格分岐は、レビュー形の依頼でしか書かれない。** 03 と 05 は
  ゲートに触れるが、通らなかったら何が起きるかを書いていない。
- **04 は両 arm 1.00 で差が出なかった。** 依頼文が要件を運んでいるので当然であり、
  予測どおり。全ケースがプラグイン有利に出るスイートは測定ではない。

## 5. 採点基準について

28 judge 判定のうち 27 が全会一致。割れたのは 03 の gate のみ。

grader は3回書き直している。最初の2回は1つの grader に条件を4つ詰めた結果、
どれか1つが誤反応すると良い応答を 0 点にした。**1 grader 1主張**に割ってから
安定した。採点の証拠は `calibration/` に全実行ぶん残してあるので、
rubric を直すたびに枠を使い直す必要はない。

## 6. 修正に至るまで

- **初版の絞り込み**（「作業を求めるターンは通し、教えてほしいだけのターンは直接答えよ」）で
  過剰発火は 0/2 に消えたが、02 が発火しなくなった。1/6 は雑音の可能性があったので
  02 だけを 3 runs 回し、**0/3** で雑音ではないと確定した。
- 原因は末尾の疑問形。02 は "I want this fixed properly ... How would you go about it?"
  と直すべき欠陥を名指ししているのに、疑問形で終わるため「教えてほしいだけ」と読まれた。
  同じ内容を命令形で書いた 08 は発火していた。
- 除外節に停止点を書き込んだ。**作業を名指しするターンは、疑問形で終わっても作業である。**
  説明依頼の2件はどちらも「何も変えない」と明言しており、この線の外側に残る。
- 修正版で 6/6・0/2。緩める修正で過剰発火が戻っていないことを同じ実行で確かめた。

## 7. judged grader について — 道具を疑う

この実験で llm grader が応答の質より厳しく採点したのは5回。最後は 05 で、
振る舞いを特性テストで固定してから新旧実装の等価性をレビューさせる応答が、
割れ票 PFF で 0 点になった。3回を超えた時点で個々の rubric ではなく道具立てを疑うべきで、
6回目の rubric 修正はしていない。応答の質の差を測りたいなら、rubric を直すのではなく
runs を 5 程度に上げて平均を取るのが正しい道具である。
