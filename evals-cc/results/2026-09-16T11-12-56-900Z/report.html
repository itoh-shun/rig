asyncio.gather と asyncio.wait は「どちらも複数の待ち合わせ」ですが、**返すもの・例外の扱い・キャンセルの後始末**が根本的に違います。

## 一覧

| | `gather` | `wait` |
|---|---|---|
| 戻り値 | 結果のリスト（**渡した順**） | `(done, pending)` の**タスクの集合**（順序なし） |
| 引数 | awaitable（コルーチンは自動で Task 化） | **Task/Future のみ**（3.11 でコルーチン渡しは廃止） |
| 種別 | Future を返す普通の関数 | コルーチン |
| 例外 | 既定で**即座に呼び出し側へ伝播** | **伝播しない**。Task に格納されるので自分で取り出す |
| timeout | なし | `timeout=` あり |
| 途中で返す | 不可（全部待つ） | `return_when=FIRST_COMPLETED / FIRST_EXCEPTION / ALL_COMPLETED` |
| 重複 | そのまま保持 | set なので**重複が消える** |

## 実際に効いてくる差

**1. 結果の受け取り方**

```python
r1, r2 = await asyncio.gather(fetch(a), fetch(b))   # 値がそのまま、順序保証

done, pending = await asyncio.wait({t1, t2})
for t in done:
    t.result()   # ← 自分で取り出す。順序は完了順ですらなく不定
```

`gather` の順序は「完了順」ではなく「引数の順」です。ここは取り違えやすいところ。

**2. 例外**

`gather` は既定（`return_exceptions=False`）で最初の例外をその場で送出します。ただし**残りのタスクはキャンセルされず走り続ける**のが落とし穴。`return_exceptions=True` にすると例外オブジェクトが結果リストに混ざって返ります。

`wait` は子の例外を一切送出しません。`t.result()` を呼ばないと `Task exception was never retrieved` の警告だけが後から出ます。

**3. タイムアウト時の後始末**

```python
done, pending = await asyncio.wait(tasks, timeout=5)
# pending のタスクは "まだ走っている"。自分で cancel しないと放置される
for t in pending:
    t.cancel()
```

対して `gather` が返す Future をキャンセルすると、未完了の子タスクにキャンセルが伝播します。`asyncio.timeout()` / `wait_for` と組み合わせるならこちらの挙動のほうが素直です。

## 使い分け

- **全部の結果が順番に欲しい** → `gather`
- **「最初の1つが終わったら」「5秒だけ待つ」など待ち方を制御したい** → `wait`
- **完了した端から処理したい** → どちらでもなく `asyncio.as_completed`
- **失敗したら兄弟も確実に止めたい（3.11+）** → `asyncio.TaskGroup`

新規コードでは、失敗時に兄弟タスクを自動キャンセルして `ExceptionGroup` で上げてくれる `TaskGroup` が既定の選択肢になりつつあります。`gather` の「例外は上がるがタスクは生き残る」挙動がリークの原因になりやすいためです。

# `asyncio.gather` と `asyncio.wait` の違い

一言でいうと、**`gather` は「全部の結果を順番どおりに欲しい」ための高水準 API**、**`wait` は「完了状況を見て自分で制御したい」ための低水準 API**です。

## 1. 戻り値

```python
# gather: 引数の順序どおりの結果リスト
results = await asyncio.gather(f(1), f(2), f(3))
# → [r1, r2, r3]  完了順ではなく引数順

# wait: (done, pending) の Task の「集合」
done, pending = await asyncio.wait(tasks)
# → set なので順序なし。値は自分で task.result() で取り出す
```

`wait` は結果を返さず Task を返すので、値が欲しければ `t.result()` を呼ぶ必要があり、しかも `set` なので元の順序との対応は自分で管理します（`dict` で `task -> 識別子` を持つのが定番）。

## 2. 受け付ける引数

- `gather`: コルーチンでも Future でも OK。コルーチンは自動で Task にラップされる。
- `wait`: **Task / Future のみ**。コルーチンを直接渡すのは 3.8 で非推奨、3.12 で `TypeError` になりました。`asyncio.create_task()` で包んでから渡します。

## 3. 例外の扱い（ここが最大の実務上の差）

```python
# gather（デフォルト return_exceptions=False）
await asyncio.gather(ok(), fail(), ok())   # 最初の例外がそのまま送出される
```

注意点: 例外が上がっても**残りのタスクはキャンセルされず走り続けます**。回収されない例外が "Task exception was never retrieved" として後から警告になることがあります。

```python
# 例外も値として受け取る
results = await asyncio.gather(*coros, return_exceptions=True)
# → [r1, ValueError(...), r3]
```

一方 `wait` は**例外を一切送出しません**。失敗したタスクも単に `done` に入るので、`t.exception()` / `t.result()` で自分で確認します。

## 4. 待ち方の制御

`wait` だけが持つもの:

```python
done, pending = await asyncio.wait(
    tasks,
    timeout=5,
    return_when=asyncio.FIRST_COMPLETED,  # / FIRST_EXCEPTION / ALL_COMPLETED
)
```

`gather` にタイムアウトはないので、`asyncio.timeout()`（3.11+）や `asyncio.wait_for()` で外から包みます。

## 5. キャンセル時の挙動

- `gather` が返す Future をキャンセルすると、**未完了の子タスクも全部キャンセル**されます。
- `wait` はタイムアウトしても `pending` のタスクを**キャンセルしません**。走りっぱなしになるので、自分で後始末が必要です:

```python
for t in pending:
    t.cancel()
await asyncio.gather(*pending, return_exceptions=True)
```

## 使い分け

| やりたいこと | 使うもの |
|---|---|
| 全部の結果を順序どおり集める | `gather` |
| 一つでも終わったら先に進む / タイムアウト付き | `wait` |
| 終わった順に逐次処理したい | `as_completed` |
| エラー時に兄弟タスクも確実に畳みたい | **`TaskGroup`**（3.11+） |

## 補足: 3.11 以降は `TaskGroup` が第一候補

```python
async with asyncio.TaskGroup() as tg:
    t1 = tg.create_task(f(1))
    t2 = tg.create_task(f(2))
# ブロックを抜けた時点で全完了。t1.result() で値を取得
```

`gather` と違い、どれかが失敗すると**残りを自動でキャンセル**してから `ExceptionGroup` を送出します。リークするタスクが構造的に発生しないので、新規コードで「全部待つ」場合は `gather` より `TaskGroup` が推奨されます。`gather` が今も有利なのは、`return_exceptions=True` で「失敗も含めた結果をフラットなリストで受けたい」ケースです。
