The working directory is empty — no source files, just a `.git` dir. So I can't point at your actual checkout code yet. Here's how I'd approach it, and where I'd need you to point me.

## Diagnosis first, not a fix

`NaN` is a propagating value: it's produced once and then contaminates everything downstream. The render site is where you *see* it, which is almost never where it's *made*. So step one is finding the origin, not the symptom.

The usual origins for an empty-cart total, roughly in order of likelihood:

- **A division with zero denominator** — `discount / items.length`, or a weighted/proportional allocation across line items. `0/0` is `NaN`, and only on the empty case. This is the classic one, because it passes every non-empty test.
- **`undefined` entering arithmetic** — `subtotal + tax` where `subtotal` came from `items[0].price` or a lookup that returns `undefined` for an empty collection. `undefined + 5` is `NaN`.
- **A parse of nothing** — `parseFloat('')`, `Number(undefined)`, often at a form/API boundary that's empty rather than absent.

(A `reduce` without a seed is the other famous empty-collection bug, but that throws a `TypeError` rather than yielding `NaN`, so your symptom rules it out.)

I'd find which by tracing backward from the render: log or breakpoint on the total, then each input to it, until you find the first value that's `NaN` — the operation that made it is the bug.

## What "properly" means here

The patch-over version is `isNaN(total) ? 0 : total` or `total || 0` at the render site. That's bad not because guards are bad, but because it makes the display correct while the domain layer still computes a meaningless number — and anything else consuming that total (analytics, payment payload, order record) keeps getting `NaN`.

The proper fix has two parts:

1. **Fix it at the layer that owns the invariant.** Money totals are a sum, and a sum over an empty collection is defined: it's the identity element, `0`. Whatever function computes the total should be *total* in the mathematical sense — defined for every valid input including the empty one — rather than defined for non-empty input and guarded at the edges. Concretely, if it's the division case, the fix is the empty/zero-denominator branch inside the allocation function, returning zero allocations. If it's `undefined` propagation, the fix is making the source return `0` for an empty cart rather than `undefined`.

2. **Make the class of bug non-recurring.** Add a `Number.isFinite` assertion where money values are constructed or leave the domain layer. `NaN` should fail loudly at its origin instead of silently traveling to the UI. That's what converts "we fixed this instance" into "this shape of bug can't reach the user again."

## The test that would have caught it

The honest version is a test at the **calculation** layer, not the render layer:

```
totalFor(emptyCart) === 0
```

But I'd argue for slightly more than the one regression case, because the bug is really *"the empty case was never considered"*:

- An empty-input case for **each** aggregate in checkout — subtotal, tax, shipping, discount — not just the top-level total. The bug lives in one of them; the others have the same gap.
- A test that the total is a finite number, not just that it equals a value. `expect(Number.isFinite(total))` catches `NaN` and `Infinity` in cases where you don't want to hardcode the expected figure.
- If you have property-based testing available, `total(a.concat(b)) === total(a) + total(b)` catches this structurally — the empty cart falls out as a free case, and so do several neighboring bugs.

I'd also add one render-level test asserting the displayed string is `$0.00`, since that's the reported symptom and it pins the formatting path too. But the calculation test is the one that matters; the render test alone would tempt the next person into the guard-at-the-edge fix.
