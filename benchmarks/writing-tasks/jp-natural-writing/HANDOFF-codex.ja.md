日本語生成ベンチマークの検証を依頼したい。前任の別エージェントが約1700回の判定を回して
**「何をやっても効果がゼロ」という結論に到達している**。その結論が正しいのか、それとも
測定器が壊れているのかを、独立に確かめてほしい。前任の仮説をなぞる必要はない。むしろ疑ってほしい。

## 対象

- リポジトリ: `itoh-shun/rig`、ブランチ `claude/harness-japanese-humanity-c6k0ex`
- 作業場所: `benchmarks/writing-tasks/jp-natural-writing/`
- 最初に読む: `README.md`（測定の全記録）→ `docs/jp-humanness-redefinition.ja.md`（前任の定義と、その否定）

## 何を測っているか

各アーム（ハーネス構成）に日本語の技術記事を書かせ、実在の2023年以前 Qiita 記事と並べて、
別プロセスの判定役に「どちらが人間か」を両順序で判定させる。50% なら見分けがつかない、
100% なら常に見破られる。判定役は read-only ツールに固定され、どちらが生成物かを知らされない。

現状は最良アームで 92〜95%。目標は 50%。

## 確定していること（数字は `results/` に全部ある）

1. **表層の変異は全部ゼロ。** 接続詞削除・内省の締め削除・文長分割・丁寧体変換
   （人間 65.2% 対 生成 0.0% という最大の特徴量差を機械的に 67.8% まで閉じた）。
   すべて帰無対照（バイト同一テキストの再判定）の床を超えない。
2. **素材が実在する必要はない。** コミットハッシュと16桁の浮動小数を同形の非実在値へ
   一貫置換しても、騙せた試行は 10/62 対 10/62 で集計値まで完全一致。
3. **講評は判定の原因ではない。** 判定役が根拠として名指しする特徴を機械的に解消しても
   判定は動かない。リンク（負け講評 16/24 で名指し・因果ゼロ）と丁寧体で2例確認済み。
   **この罠には前任も2回はまっている。**
4. **判定役は規範を持っている。** 人間記事40本の講評と生成記事の勝ち講評95件を同じ物差しで
   数えると、経路がほぼ交わらない（実在の識別子: 人間 2% 対 生成 81%／誤字・崩れ: 人間 44%
   対 生成 10%）。「未解決で終わる」は勝ち講評の 34/47 で挙がるが、人間記事は 0/139 本しか
   そうしない。
5. **測定器に欠陥が4件あった。** 分析器が markdown の画像行・箇条書きを1文として数えていた
   （「人間は文長分散が大きい」は artifact だった）、台帳プローブが pytest 不在を黙殺していた、
   実行記録が使っていない台帳の指紋を書いていた、判別が対戦相手1本で回っていた。

## 本題

**この測定器に陽性対照が無い。**

帰無対照（何も変えずに再判定 → 1ペア動く）は取ってある。だが逆側、
**「効くと分かっている操作を入れたら実際に判別が動くか」を一度も確かめていない。**

したがって上記のゼロは、原理的に2通りに読める。

- 介入に効果が無い
- **この測定器では、その大きさの効果を検出できない**

前任は後者を排除できていない。1条件62試行という規模を考えると、実際かなり怪しい。

依頼したいのは、**この測定器の最小検出可能効果（MDE）を実測すること**。

具体的には、効果の大きさが既知の操作を段階的に作り、判別が単調に応答するかを見てほしい。
たとえば「生成記事の文の X% を bare アーム（判別 100%・明らかに AI）の文で置き換える」を
X = 0/10/25/50/75/100 と振れば、0% と 100% の判別率は既知なので、
その間の応答曲線がそのまま測定器の分解能になる。設計は任せる。

判明してほしいこと:

- **何ポイントの差なら、この設計（31ペア・両順序・62試行）で検出できるのか**
- その MDE は、前任が測ったゼロたちより大きいのか小さいのか
- 大きいなら、**17回ぶんのゼロは「効果がない」ではなく「測れていない」だった**ことになる。
  そのときは、必要な試行数か、代替の指標を提案してほしい

## 守ってほしい測定規律

前任が高い授業料を払って得たもの。破ると同じ穴に落ちる。

- **帰無対照を必ず同一バッチ内に置く。** バイト同一のテキストを別アームとして混ぜる。
  これが無いと、1〜2ペアの移動を効果と読み違える。
- **対応ありペアで見る。** 集計値だけだと、同数の増減が打ち消し合って「不動」に見える。
  `discriminate.py` は `pair_id` を持っているので、ペア単位の増減が出る。
- **講評から拾った仮説を、対照実験なしで採用しない。** 上記3の通り2回外している。
- **`writer` 系アームを比較するときは台帳の sha1 を一致させる。** 台帳は `git log` から
  作られるので、ピン止め（`--ledger-pin`）しないとリポジトリが動くたびに中身が入れ替わる。
  過去に実行1本がこれで比較不能になっている。
- **操作が効いたかを、結果を見る前に検証する。** 前任はジャンル統制で失敗した
  （検索語で引き直したつもりが、文書の型が変わっていなかった）。

## 再提案しなくてよい設計（すべて実測で否定済み）

数量ノルマ基準／自己推敲ループ／形態素 lint のゲート化／記事全体の秘匿（relay）／
段落末の後処理除去／生成器の異質化／骨格の除去・人間骨格の移植／リンク注入／
主観表現の禁止／丁寧体変換／文長分割／接続詞削除／末尾切断／誤字注入（ただし仮名置換3箇所
という狭い形でしか試していない）／素材の著者分割／素材の余剰量（0/2/12件）／経歴ペルソナ。

## 実行方法

```bash
cd benchmarks/writing-tasks/jp-natural-writing
python fetch_human_corpus.py --out /tmp/human_corpus --per-topic 12 --min-stocks 3
python discriminate.py --run results/2026-07-31-provenance-arms.json \
    --corpus /tmp/human_corpus --opponents 4 --parallel 6 --json-out /tmp/out.json
```

- 判定1回あたり約8秒。1条件62試行なので、条件を増やすとコストは線形に伸びる。
- 生成を伴う実験は1アーム約20分。`--checkpoint <path>` を付けること
  （前任は付けずに live 実行を2回失っている）。
- **人間コーパスの本文はリポジトリに置かないこと。** 第三者の著作物であり、
  `fetch_human_corpus.py` はローカルにのみ書き出す。派生した数値だけが記録に残せる。
